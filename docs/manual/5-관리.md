# 5. 관리

이 장은 관리자가 읽는다. 날마다 할 일은 없다 — 작업 스케줄러의 serve 가 접수·처리·엑셀·통합 DB 를 알아서 한다.
이 장은 가끔 하는 일을 적는다.

- [백업](#백업) — 무엇을 백업하고, 무엇은 다시 만드는가
- [로그 읽기](#로그-읽기)
- [다시 처리](#다시-처리) — `watch --once`, `run --skip-existing`, `run --fresh`
- [현황 보기](#현황-보기) — `report`, `report --by-month`, `pages`
- [회귀 검사](#회귀-검사) — `regress`
- [통합 DB 관리](#통합-db-관리) — `publish --check`, `publish --rebuild`
- [사이트 이름을 바꿀 때](#사이트-이름을-바꿀-때)

명령은 새 PowerShell 창에서 친다.

## serve 를 멈추고 하는 명령

작업 폴더 하나에는 처리하는 프로그램이 하나만 돈다. 작업 스케줄러의 serve 가 도는 동안 처리하는 명령(`run`, `watch`, `export excel`,
`publish`)을 치면 "다른 파이프라인(run·watch·serve)이 이미 돌고 있습니다 — 작업 폴더 하나에 하나만: …"으로 끝난다.
그런 명령은 작업을 멈추고 돌린 뒤 다시 켠다.

<!-- 시험: 돌리지 않음 -->
```powershell
Stop-ScheduledTask -TaskName minedocscan-serve
minedocscan run --fresh                              # 보기 — 처리하는 명령
Start-ScheduledTask -TaskName minedocscan-serve
```

읽기만 하는 명령은 serve 가 돌고 있어도 된다 — `info`, `report`, `pages`, `doc list`, `review stats`, `publish --check`, `regress`.
`doc date`·`doc discard` 같은 결정도 된다 (기록만 남기고 처리는 serve 가 한다).

## 백업

### 백업할 것

| 무엇 | 자리 | 까닭 |
|---|---|---|
| **검수 기록** `reviews.jsonl`, **결정 기록** `decisions.jsonl` | 사이트 팩의 `reviews\` (설정에 `[paths] reviews` 를 적었으면 그 파일과 같은 폴더) | 사람이 넣은 값과 정한 것(날짜·버리기·되살리기·다른 종이). **다시 만들 수 없다** |
| **보관 폴더** | `[paths] archive_root` (보기 `D:\minedocscan\archive`) | 스캔 원본. **다시 만들 수 없다** |
| 사이트 팩의 나머지 | `[paths] site` (보기 `D:\minedocscan\site`) | 템플릿·기준 이미지·인쇄 층([7장](7-새-양식-더하기.md#인쇄-층)), `site.toml`, 학습한 모델(`models\`), 회귀 기준(`expected\`). 만드는 데 품이 든다 |
| 설정 파일 | `%APPDATA%\minedocscan\minedocscan.toml` | 작다. 손으로 고쳤으면 백업한다 |

간단히는 **사이트 팩 폴더 전체와 보관 폴더 전체**를 백업한다. 검수·결정 기록은 사이트 팩 안에 있다.

두 기록 파일의 자리는 `info` 와 `review stats` 가 알려 준다.

```powershell
minedocscan info                # "결정 기록: …\reviews\decisions.jsonl (N줄)"
minedocscan review stats        # "검수 파일: …\reviews\reviews.jsonl — 기록 N건 (깨진 줄 0개)"
```

- 두 기록 파일은 **줄을 더하기만** 한다. 프로그램은 지우거나 고쳐 쓰지 않는다. 사람도 메모장으로 고치지 않는다.
  잘못 넣은 값이나 결정은 화면에서 다시 넣는다 — 뒤의 줄이 이긴다.
- serve 가 도는 동안 복사해도 된다. 다만 복사하는 순간에 쓰던 마지막 한 줄은 반쯤 복사될 수 있다. 그 줄은 다시 읽을 때 "깨진 줄"로 건너뛴다.
  확실히 하려면 작업을 멈춘 사이에 복사한다.
- 보관 폴더는 커지기만 한다. 프로그램은 그 안의 `intake\` 아래에 더하기만 하고 아무것도 지우지 않는다. 사람도 지우지 않는다.
  백업도 원본에서 사라진 파일을 백업에서 지우지 않는 방식으로 한다.
- 접수 폴더의 `_failed` 폴더에 있는 파일은 보관 폴더에 없다 (읽지 못해 옮겨 둔 것). 사람이 살펴볼 때까지 같이 백업한다 ([6장](6-문제-해결.md#그-밖의-문제)).
- 통합 DB 의 비밀번호 파일(`pgpass.conf`)은 백업에 넣지 않는다. 잃으면 통합 DB 관리자에게 다시 받는다.
- 백업도 현장 데이터다 (이름·서명·차량번호). 현장 밖의 곳에 올리거나 메일로 보내지 않는다.

### 다시 만들 수 있는 것

| 무엇 | 다시 만드는 법 |
|---|---|
| 작업 폴더 — 작업 DB `minedocscan.db`, 정합 그림 | `minedocscan run --fresh` — 보관 폴더와 사이트 팩(검수·결정 기록)에서 ([아래](#다시-처리)) |
| 엑셀 폴더 | serve 가 다시 쓴다. 한 번에 쓰려면 `minedocscan export excel` |
| 통합 DB 의 표 | serve 가 다시 싣는다. 한 번에 실으려면 `minedocscan publish` |
| 설치 폴더 (`python\`, `logs\`) | 묶음으로 다시 설치한다 ([2장](2-설치.md)). 로그는 어차피 30일만 남는다 |

같은 스캔·검수·결정이면 작업 DB 를 몇 번을 다시 만들어도 같은 DB 가 된다 (예외 하나: 버렸던 실패 문서 — [run --fresh](#run---fresh)). 문서를 받은 순서도 보관 폴더의 폴더 이름(받은 시각)에서 다시 나온다.

### 백업에서 되살리기

PC 를 바꿀 때도 같다. 아래 1–4 의 순서로 한다.

**통합 DB 에 싣는 현장이면** 3 을 마치기 전에 serve 가 싣지 않게 한다. 작업 DB 가 빈 채로 serve 가 실으면 대상의 행이 지워진다
(3 뒤에 다시 실리지만, 그동안 통합 DB 를 읽는 쪽에는 비어 보인다). 엑셀 폴더는 괜찮다 — 쪽이 없는 작업 DB 로는 파일을 지우지 않는다.

- 새 PC 라면 환경 변수 `MINEDOCSCAN_PUBLISH_URL` ([2장](2-설치.md#통합-db-의-비밀번호))을 3 을 마친 뒤에 둔다.
- 환경 변수가 이미 있는 PC 라면 2 전에 설정 파일의 `[publish]` 표에 `enabled = false` 를 적어 두고, 3 을 마친 뒤 그 줄을 지우고 작업을 켠다.

1. 사이트 팩과 보관 폴더를 제자리에 놓는다. 설정 파일이 가리키는 경로와 같게 놓거나, 설정 파일의 경로를 고친다.
2. 프로그램을 설치한다 ([2장](2-설치.md)). 백업한 설정 파일이 있으면 `-Config` 로 준다.
3. 작업을 멈추고 작업 DB 를 다시 만든 뒤 작업을 켠다.

<!-- 시험: 돌리지 않음 -->
```powershell
Stop-ScheduledTask -TaskName minedocscan-serve
minedocscan run --fresh
Start-ScheduledTask -TaskName minedocscan-serve
```

4. `minedocscan info` 의 "결정 기록: … (N줄)"과 `minedocscan report` 의 문서·쪽 수를 본다. 엑셀 폴더와 통합 DB 는 serve 가 따라잡는다.
   내용이 같은 엑셀 파일은 다시 쓰지 않는다.

## 로그 읽기

serve 의 로그는 `%LOCALAPPDATA%\minedocscan\logs\serve-YYYYMMDD.log` 에 있다 (설치 폴더를 바꿨으면 `<설치 폴더>\logs`).
자리와 남기는 기간은 [2장의 "로그"](2-설치.md#로그)에도 있다.

- 날마다 새 파일이다. 줄에는 시각이 없고, 파일 이름의 날짜가 그날이다.
- UTF-8 이라 메모장으로 열린다.
- **30일** 지난 파일은 serve 가 지운다. 오래 남기려면 다른 곳에 옮긴다. 지우기(`uninstall.ps1`)도 `logs\` 를 지운다.
- 창에서 띄운 `watch` 와 `--log-dir` 없이 띄운 `serve` 는 같은 줄을 그 창에 찍는다 (파일은 없다).

합성 데모의 보기:

<!-- 시험: 돌리지 않음 -->
```text
운영 화면: http://127.0.0.1:8765/  (검수자 jp) — Ctrl+C 로 끝냅니다
처리한 문서 6건, 받은 문서 6건 (d6181d052a91d36c, 18626b5c93809fe3, 0d598d869e5ef3b6, c7ae7ab81a630355, 2e0c2af448f7a622, dd8aa03280baecfa), 이미 있는 파일(_already) 1, 다시 스캔 의심 쪽 2, 날짜를 정할 문서 1건 (c7ae7ab81a630355), 실패한 문서 1건 (339db43aff2eaccb), 엑셀: 쓴 파일 4, 지운 파일 0 — 기록 파일이 없어 다시 쓴다
GET /api/home 200
GET /doc 200
```

| 줄 | 뜻 |
|---|---|
| "운영 화면: http://127.0.0.1:8765/ (검수자 …)" | serve 가 켜졌다. 켜질 때마다 한 줄 |
| "처리한 문서 N건, …" | 작업 한 바퀴의 요약. 무엇이 있었을 때만 찍는다. 수와 문서 ID 만 — 파일명·날짜·값은 없다 |
| "GET /api/home 200" | 화면이 받은 요청 (경로와 상태 코드만). 홈을 열어 두면 5초마다 한 줄 |
| "엑셀 자동 내보내기를 켜지 않습니다: …", "… 통합 DB 싣기를 끕니다 …" | 시작할 때 켜지 못한 일과 그 까닭 |
| 맨 끝의 오류 줄 (보기: "설정 오류: …") | serve 가 멈춘 까닭 — [6장](6-문제-해결.md#serve-가-켜지지-않을-때) |

문서 ID 로 그 문서를 보려면 브라우저에서 `http://127.0.0.1:8765/doc?id=<문서 ID>` 를 연다. 문서 ID 와 파일명의 짝은 `minedocscan doc list` 가 보여 준다.

로그에는 이름·차량번호·값이 없지만, 설정 오류의 줄에는 폴더의 경로가 들어갈 수 있다. 밖으로 보낼 때는 필요한 줄만, 경로를 지우고 보낸다.

## 다시 처리

보통은 손댈 것이 없다.

- 새 스캔은 serve 가 받아서 처리한다.
- 날짜·버리기·되살리기·다른 종이를 정하면 그 문서가 "다시 처리 대기"가 되고, serve 가 다음 바퀴에 그 문서를 지우고 다시 만든다.
- 검수로 넣은 값은 그 자리에서 업무 표에 들어간다.

손으로 다시 처리하는 때는 이렇다.

| 언제 | 명령 |
|---|---|
| serve 를 띄우지 않는 PC(`-NoTask`)에서 접수와 대기 중인 문서를 처리한다 | `minedocscan watch --once` |
| 템플릿, `site.toml`(장비명 대응표 …), 인식기·모델 설정을 바꿨다. 템플릿의 `title`·`display`(보이는 이름)만 바꿨으면 다시 처리하지 않는다 — serve 를 다시 켜면 된다 | `minedocscan run --fresh` |
| 올린 판의 작업 DB 스키마가 바뀌었다 ([2장](2-설치.md#작업-db-의-스키마가-바뀌는-판)) | `minedocscan run --fresh` |
| 오류 난 쪽·실패한 문서를 다시 해 본다, `[pipeline] damaged_pdf` 를 바꿨다 | `minedocscan run --skip-existing` |
| 보관 폴더에 직접 넣은 스캔 묶음(보기: 지난 스캔)을 처리한다 | `minedocscan run <그 폴더> --skip-existing` |

### watch --once

접수 폴더를 한 번 훑고, 대기 중인 문서를 처리하고, 엑셀·통합 DB 를 한 번 쓰고 끝난다. 끝에 그 바퀴의 요약이 나온다.
serve 가 돌고 있으면 쓰지 않는다 (serve 가 같은 일을 한다).

```powershell
minedocscan watch --once
```

### run --fresh

<!-- 시험: 돌리지 않음 -->
```powershell
Stop-ScheduledTask -TaskName minedocscan-serve
minedocscan run --fresh
Start-ScheduledTask -TaskName minedocscan-serve
```

- 작업 DB 를 지우고 보관 폴더의 스캔 **전부**를 처음부터 다시 처리한다. 검수·결정 기록은 사이트 팩에 있어 그대로 다시 붙는다.
- 오래 걸린다. 실제 일보로는 쪽마다 1–2초쯤이었다. 창에 파일마다 "[3/120] … · 14쪽 · 지난 0:41 · 남은 약 26:10" 꼴로 나온다.
- 끝에 "이번 실행: 문서 N건, 페이지 N장, …"과 DB 현황이 나온다. 실패한 문서가 있으면 그 목록이 나오고 종료 코드가 1 이다
  (잘린 PDF 처럼 늘 실패하는 파일이 보관 폴더에 있으면 늘 1 이다 — [6장](6-문제-해결.md#실패한-문서)).
- 버렸던 실패 문서가 다시 "실패"로 나올 수 있다. 문서 화면에는 "문서 되살리기"만 보이므로 명령으로 다시 버린다:
  `minedocscan doc discard <문서 ID> --reviewer <검수자>` (serve 가 다음 바퀴에 "버림"으로 바꾼다).
- `run` 은 엑셀·통합 DB 에 쓰지 않는다 ("엑셀 폴더가 설정되어 있지만 run 은 내보내지 않습니다 — minedocscan export excel" 줄이 나온다).
  작업을 다시 켜면 serve 가 바뀐 것만 따라잡는다.
- 검수 화면(`review serve`) 창이 열려 있으면 "DB 를 지울 수 없습니다 — 다른 프로그램(serve, review serve)이 쓰고 있습니다"로 멈춘다. 그 창도 닫는다.
- 템플릿의 표·열·행 이름을 바꾸면 그 칸에 넣은 검수가 붙지 않는다 (검수는 칸의 이름으로 붙는다). 다시 만든 뒤 `minedocscan review stats` 의
  마지막 줄 "템플릿 좌표가 달라진 기록 N개, 이 DB 에 없는 필드 N개"를 본다. 템플릿을 고치는 법은 [7장](7-새-양식-더하기.md#4-칸-채우기)과 [SITE_PACK.md](../SITE_PACK.md).

### run --skip-existing

<!-- 시험: 돌리지 않음 -->
```powershell
Stop-ScheduledTask -TaskName minedocscan-serve
minedocscan run --skip-existing
Start-ScheduledTask -TaskName minedocscan-serve
```

- 보관 폴더 전체를 훑되, 끝까지 처리된 문서와 버린 문서는 건너뛴다. 실패한 문서, 오류 난 쪽이 있는 문서, 아직 처리하지 않은 문서는 다시 한다.
- 템플릿이나 인식기를 바꾼 뒤에는 쓰지 않는다. 건너뛴 문서는 옛 템플릿으로 처리된 채 남는다 — 그때는 `--fresh`.
- 경로를 주면 그것만 본다. 경로는 보관 폴더 기준으로도 찾는다. 문서 하나만 다시 하려면 보관 폴더의 그 문서 폴더(`intake\<받은 해-달>\<받은 시각>-<문서 ID>`)를 준다.

<!-- 시험: 돌리지 않음 -->
```powershell
minedocscan run intake\2030-01\20300107T010203456Z-1582ec6d99d57ca4
```

보관 폴더에 직접 넣은 파일은 접수 폴더를 거치지 않았으므로 `run` 으로만 처리된다. 파일명으로 날짜를 알 수 없으면 "날짜를 정할 문서"가 된다.

## 현황 보기

### report

작업 DB 의 현황을 수로 보여 준다. 아무것도 바꾸지 않는다.

```powershell
minedocscan report
```

- 문서의 상태별 수 (`needs_date`·`needs_review`·`failed` …), 쪽의 상태별 수 (`loaded`·`blank`·`duplicate`·`unknown_form`·`align_failed` …).
- 양식별 정합: "synth_haul_log: 13/13 통과, 인라이어 최소 658, 괘선 오차 최대 0.0 px" 꼴. "인라이어"는 쪽과 기준 이미지에서 서로
  맞아떨어진 점의 수(많을수록 잘 맞았다), "괘선 오차"는 편 쪽의 괘선이 템플릿의 괘선에서 벗어난 화소(0 에 가까울수록 좋다)다.
  통과가 줄었거나 괘선 오차가 커진 양식은 템플릿을 본다.
- 날짜를 정할 문서, 돌아서 들어와 세운 쪽, 빈 쪽, 다시 스캔 의심 쪽의 수와 그것을 보는 명령.
- 필드 수와 검수 대기, 교차검증(일치·불일치), 가동 일보의 검산, 날짜별 교차검증.

결과에는 수와 양식 이름만 있다 (이름·차량번호·파일명이 없다). 물어볼 때 보내도 된다.

### report --by-month

양식 × 달로 쪽 수, 적재, 정합 실패, 오류, 인라이어 최소, 괘선 오차(중앙·최대), 분류 여유가 낮은 쪽을 보여 준다.

```powershell
minedocscan report --by-month
```

어느 달부터 한 양식의 정합 실패가 늘거나 괘선 오차가 커지면, 그달부터 인쇄 판이 바뀌었을 수 있다 (개정판). 템플릿의 판을 나누는 법은
[SITE_PACK.md](../SITE_PACK.md)의 `family`·`valid_from`·`valid_to` 와 "같은 날 섞여 쓰이는 판"에 있다.

### pages

쪽의 목록이다. 상태·양식으로 거른다.

```powershell
minedocscan pages --status unknown_form
minedocscan pages --status align_failed
```

| 선택 | 거르는 것 |
|---|---|
| `--status <상태>` | `unknown_form`(양식 없음), `blank`(빈 쪽), `align_failed`(정합 실패), `duplicate`(다시 스캔 의심), `error`(오류), `loaded`(적재), `discarded`(버림), `classified_only`(분류만) |
| `--template <양식>` | 그 양식만 |
| `--low-margin` | 양식을 가르는 여유(가장 닮은 양식과 그다음 양식의 점수 비율)가 `[pipeline] classify_min_margin`(1.5)보다 낮은 쪽 — 양식을 잘못 알아봤을 수 있다 |
| `--rotated` | 돌아서 들어와 세운 쪽 |
| `--thumbs` | 목록의 쪽을 1/4 로 줄인 그림으로 `<작업 폴더>\thumbs\<상태>\` 에 쓴다 |

출처 열(`파일명#쪽`)은 원래 파일명이다. 밖으로 보낼 때는 지운다. 모든 선택은 [부록 — 명령 목록](명령.md)에 있다.

실패한 문서는 `doc list` 로 본다.

```powershell
minedocscan doc list --status failed
```

## 회귀 검사

회귀 검사는 **실제 스캔 묶음을 지금의 프로그램과 사이트 팩으로 다시 처리해, 저장해 둔 기준 수치와 견준다.** 새 판으로 올린 뒤,
템플릿이나 `site.toml` 을 고친 뒤에 돌린다. 수치가 달라졌으면 좋아진 것인지 망가진 것인지 사람이 정한다.

- 기준 파일: `<사이트 팩>\expected\regression.json` — 입력(보관 폴더 기준 경로), 인식기, 리포트의 수치.
- 임시 폴더에서 처리한다. 작업 DB·엑셀·통합 DB 를 건드리지 않는다. serve 가 돌고 있어도 된다 (CPU 를 많이 쓴다).
- 검수 기록은 읽지 않는다 (검수가 쌓이면 코드가 같아도 수가 바뀌기 때문이다). 결정 기록은 읽는다.

**처음 한 번** — 기준을 만든다. `--inputs` 에는 기준으로 삼을 묶음을 보관 폴더 기준 경로로 준다 (여럿 줄 수 있다).
며칠치, 양식이 다 들어 있는 묶음이 좋다. **더 늘지 않는 폴더**를 준다 — 지난달에 받은 것(`intake\<받은 해-달>`)처럼.
파일이 늘면 프로그램이 같아도 수치가 달라진다.

<!-- 시험: 돌리지 않음 -->
```powershell
minedocscan regress --update --inputs intake\2030-01
```

**그다음부터**:

<!-- 시험: 돌리지 않음 -->
```powershell
minedocscan regress
```

| 결과 | 종료 코드 | 할 일 |
|---|---|---|
| "기준과 같습니다." | 0 | 없다 |
| "기준과 다른 항목 N개 (…):" 와 "키: 기준 A → 지금 B" 줄들 | 1 | 아래 |
| "기준에 없던 새 항목 N개 (어긋남으로 치지 않는다 — --update 로 기준에 넣는다)" | 0 | 새 판이 리포트에 더한 수치다. `--update` 로 기준에 넣는다 |
| 오류의 마지막 줄 "기준 파일이 없거나 inputs 가 비었습니다: … (처음에는 --update --inputs … 로 만듭니다)" | 1 | 처음 한 번을 한다 |

수치가 달라졌을 때:

1. **왜 달라졌는지 안다.** 새 판의 변경 내용(저장소의 `CHANGELOG.md` — 묶음에는 없다)이나 템플릿을 고친 것으로 설명이 되는가.
   보기: 1.0.0 은 PDF 를 읽는 부품을 바꿨다. 실제 3일치 83쪽에서 쪽의 크기와 적재는 같았고, 값 유무가 바뀐 칸이 10,274개 중 19개였다.
2. **좋아졌거나 받아들일 만하면** 기준을 갱신한다: `minedocscan regress --update`.
3. **무엇이 왜 바뀌었는지 적어 둔다.** 저장소의 코드를 고쳐서 바뀐 것이면 그 커밋 메시지에 적는다 — 수치가 달라졌는데 설명이 없으면 안 된다
   (저장소의 `CLAUDE.md` 의 "작업 규칙"). 사이트 팩을 고쳐서 바뀐 것이면 언제 무엇을 고쳤는지 같이 적어 둔다
   (사이트 팩을 버전 관리하면 그 커밋 메시지에).
4. **설명이 안 되면** 갱신하지 않는다. 다른 항목의 이름과 두 수(이름·값이 없다)를 개발자에게 보낸다.

- 기준은 **비교할 PC 에서** 잡는다. 윈도우와 리눅스는 같은 그림을 조금 다르게 정합한다 (괘선 오차 0.0 → 1.0 px 같은 차이). 현장 PC 의 기준은 현장 PC 에서 만든다.
- 회귀 검사의 인식기는 기준 파일에 적힌 것이다 (처음 만들 때의 `null` — 손글씨를 읽지 않는다). 숫자 인식기의 정확도는 `eval` 로 따로 잰다 ([DATA.md](../DATA.md)).

## 통합 DB 관리

통합 DB 에 싣지 않는 현장이면 이 절을 건너뛴다. 설정은 [2장의 "통합 DB 의 비밀번호"](2-설치.md#통합-db-의-비밀번호)에 있다.

이 절의 말: **대상**은 실을 곳, 곧 통합 DB 의 그 스키마다. 싣는 단위는 **범위**다 — 문서 하나(그 문서의 쪽·칸과 업무 표의 행),
날짜 하나(그날의 운반 교차검증·배차), 통째(장비 목록). 범위마다 내용의 **지문**(해시)을 대상에 적어 두고, 지문이 다른 범위만
한 트랜잭션으로 갈아 끼운다. 홈의 "밀린 범위 N"도 이 범위의 수다.

### publish --check

대상과 작업 DB 를 견주기만 한다. 아무것도 쓰지 않고 잠금도 잡지 않는다 — serve 가 돌고 있어도 된다.

<!-- 시험: 돌리지 않음 -->
```powershell
minedocscan publish --check
echo $LASTEXITCODE
```

<!-- 시험: 돌리지 않음 -->
```text
통합 DB db-server:5432/mine 스키마 minedocscan: 다른 범위 — 문서 0, 날짜 0, 통째 0; 대상에만 있는 범위 — 문서 0, 날짜 0 (견준 범위 52)
```

| 종료 코드 | 뜻 |
|---|---|
| 0 | 대상이 작업 DB 와 같다 |
| 1 | 다른 범위가 있다 — serve 가 아직 싣지 않았다 (방금 처리했다, 처음 싣는 중이다, 싣기가 실패하고 있다), 대상에 표가 아직 없다 |
| 2 | 싣지 못하는 상태다 — 서버에 닿지 못했다, 설정이 틀렸다(`MINEDOCSCAN_PUBLISH_URL` 이 없다, `[site] name` 이 없다, 작업 DB 가 없다 …), 다른 사이트의 대상, 판이 다르다, 이 프로그램이 만들지 않은 표. 까닭이 한 줄 나온다 |

- 견주는 것은 실을 때 적어 둔 지문이다. 누가 대상의 표를 손으로 고쳤으면 `--check` 도 모른다. 실은 표에는 이 프로그램만 쓴다.
- serve 의 처음 싣기는 달마다 한 조각씩 간다 (홈: "처음 훑는 중 3/14"). 다 돌 때까지 대상에는 앞의 달만 있다. 한 번에 다 실으려면 작업을 멈추고
  `minedocscan publish` 를 돌린다 (늘 전부를 한 트랜잭션으로).

### publish --rebuild

이 프로그램이 대상에 만든 표를 지우고, 다시 만들고, 전부 싣는다. 한 트랜잭션이라 실패하면 대상은 그 전 그대로이고, 읽는 쪽은 빈 표를 보지 않는다.

이럴 때 쓴다:

- 홈에 "싣지 못함 (판이 다름 — publish --rebuild, …)", 명령에 "대상의 싣기의 판 이(가) 이 프로그램과 다릅니다 — minedocscan publish --rebuild"
  (또는 "대상의 스키마 버전 이(가) …")가 나올 때.
  **1.0.0 전의 판으로 실어 둔 대상(싣기의 판 1)은 1.0.0 으로 올린 뒤 한 번 해야 한다.** 1.0.0 의 싣기의 판은 2 다 — 대상에 사이트 이름을 적는다.
- [사이트 이름을 바꿨을 때](#사이트-이름을-바꿀-때).

<!-- 시험: 돌리지 않음 -->
```powershell
Stop-ScheduledTask -TaskName minedocscan-serve
minedocscan info
minedocscan publish --rebuild
Start-ScheduledTask -TaskName minedocscan-serve
```

- 먼저 `info` 의 "사이트 이름 [site] name:" 줄에 이름이 있는지 본다. 없으면 `--rebuild` 도 "사이트 팩의 site.toml 에 [site] name 이 없습니다 …"로
  거절한다 (종료 코드 2). 이름을 적는 순서는 [3장](3-처음-설정.md#사이트-이름을-적는다).
- **맞는 대상인지 먼저 본다.** `--rebuild` 는 그 스키마에 이 프로그램이 만든 표가 있으면, 다른 사이트의 사본이어도 지우고 이 사이트로 바꿔 싣는다.
  `info` 의 "통합 DB:" 줄(서버/DB 스키마)을 확인한다.
- 그 스키마에 이름이 같은 표가 있는데 이 프로그램이 만든 것이 아니면 지우지 않는다 ("… 이 프로그램이 만든 표가 아니라 지우지 않았습니다 …").
  다른 스키마(`[publish] schema`)를 쓰거나 통합 DB 관리자가 그 표를 치운다.
- 2단계가 이 표에 뷰를 걸어 두었으면 "대상의 표에 다른 것(뷰 등)이 걸려 있어 지우지 않았습니다 — 그것을 먼저 치우십시오"로 멈춘다.
  뷰를 만든 쪽과 정해 뷰를 치우고, `--rebuild` 한 뒤 뷰를 다시 만든다.
- 다른 연결이 그 표를 쥐고 있으면 잠금을 기다리다 그만둔다 ("… 다시 실행하십시오"). 쥔 쪽이 끝난 뒤 다시 돌린다.
- 끝나면 "통합 DB … 에 실었습니다: 갈아 끼운 범위 — 문서 N, 날짜 N, 통째 N; 지운 범위 — …; 넣은 행 N" 이 나온다.

## 사이트 이름을 바꿀 때

`site.toml` 의 `[site] name` 은 엑셀 폴더와 통합 DB 가 "어느 현장의 사본인가"를 적는 이름이다
([3장](3-처음-설정.md#사이트-이름을-적는다)). 한 번 정하면 바꾸지 않는 것이 좋다. 꼭 바꿔야 하면 이 순서로 한다.

1. 작업을 멈춘다.
2. `minedocscan info` 를 돌린다. "평가셋의 분할 소금값([eval] split_salt)이 없어 사이트 이름 "…" 을 씁니다 — …" 줄이 나오면, 그 줄이 알려 준 값을
   **먼저** `site.toml` 의 `[eval] split_salt` 에 적는다. 그러지 않으면 평가셋의 test 날짜가 바뀐다.
3. `site.toml` 의 `[site] name` 을 바꾼다. `minedocscan info` 로 새 이름과, 소금값 줄이 없어졌는지 본다.
4. 엑셀 폴더의 기록 파일 `.minedocscan-export.json` 을 지운다. 엑셀 파일은 지우지 않는다 — 기록 파일이 없으면 전부 다시 쓴다.
5. `minedocscan export excel` 로 엑셀을 한 번에 다시 쓴다 (건너뛰면 serve 가 달마다 한 조각씩 다시 쓴다).
6. 통합 DB 에 싣는 현장이면 `minedocscan publish --rebuild`.
7. 작업을 켠다.

<!-- 시험: 돌리지 않음 -->
```powershell
Stop-ScheduledTask -TaskName minedocscan-serve
minedocscan info
notepad D:\minedocscan\site\site.toml
minedocscan info
Remove-Item D:\minedocscan\excel\.minedocscan-export.json
minedocscan export excel
minedocscan publish --rebuild
Start-ScheduledTask -TaskName minedocscan-serve
```

4를 빠뜨리면 홈의 엑셀이 "다른 사이트의 폴더 (쓰지도 지우지도 않음)", 6을 빠뜨리면 통합 DB 가 "싣지 못함 (다른 사이트의 대상, …)"이 된다.
둘 다 사본을 지키려고 멈춘 것이다 — 그때 위의 4·6 을 한다. 규칙은 [DATA.md](../DATA.md)의 "사본의 주인"에 있다.
