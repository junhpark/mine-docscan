# 6. 문제 해결

홈에 낯선 것이 보이거나 무엇이 되지 않을 때 이 장을 본다. 표는 **홈에 보이는 것 → 뜻 → 할 일** 순서다.

- 먼저 홈의 윗줄(작업·엑셀·통합 DB)과 "할 일"을 본다. 홈은 5초마다 새로 읽는다. 문서 화면은 저절로 새로 읽지 않는다 — F5.
- 홈이 열리지 않으면 [serve 가 켜지지 않을 때](#serve-가-켜지지-않을-때)로 간다.
- 명령은 새 PowerShell 창에서 친다. `run`·`watch`·`export excel`·`publish` 는 작업 스케줄러의 serve 를 멈추고 친다
  ([5장](5-관리.md#serve-를-멈추고-하는-명령)).
- 누구에게 물어볼 때 무엇을 보내는지는 [맨 끝](#물어볼-때)에 있다.

## 할 일

홈의 "할 일" 칸이다. 수가 0 이 아닌 칸을 본다. 날짜를 정할 문서·다시 스캔 의심 쪽·오류 난 쪽·실패한 문서·경로가 너무 긴 파일은
테두리가 갈색이 된다 — 먼저 볼 것들이다.

| 홈에 보이는 것 | 뜻 | 할 일 |
|---|---|---|
| 날짜를 정할 문서 N | 파일 이름으로 작업한 날을 알 수 없는 문서다 (스캐너가 붙인 이름 …). 날짜를 정할 때까지 처리하지 않고 기다린다 — 쪽도 값도 들어가지 않는다 | 홈의 "날짜를 정할 문서"에서 파일명을 누른다. 문서 화면에서 **종이에 적힌 날짜**를 읽어 "문서의 날짜"에 넣고 "날짜 저장" (`250326`·`25.03.26`·`0326` 도 된다). 쪽마다 날짜가 다르면 그 쪽의 "이 쪽은 다른 날짜". 받은 날보다 뒤이거나 31일 넘게 앞의 날짜는 한 번 되묻는다. [4장](4-날마다-쓰기.md#날짜를-정할-문서) |
| 다시 스캔 의심 쪽 N | 같은 날·같은 양식의 먼저 들어온 쪽과 손글씨 자리가 거의 같다. 같은 종이를 두 번 스캔했을 수 있다. 사람이 정할 때까지 적재하지 않는다 | 홈의 "다시 스캔 의심 쪽"에서 쪽을 누른다. 두 쪽을 견주고(그림을 누르면 크게) 셋 중 하나를 누른다: "같은 종이 — 이 쪽을 버린다", "같은 종이 — 먼저 쪽을 버리고 이 쪽을 쓴다", "다른 종이 — 둘 다 쓴다". [4장](4-날마다-쓰기.md#다시-스캔-의심-쪽) |
| 양식 없는 쪽 N | 템플릿 가운데 맞는 양식을 찾지 못한 쪽이다. 값을 읽지 않는다 | 아래 [양식 없는 쪽과 정합 실패 쪽](#양식-없는-쪽과-정합-실패-쪽) |
| 정합 실패 쪽 N | 양식은 알아봤지만 기준 이미지에 맞춰 펴지 못한 쪽이다 (많이 기울었다, 접혔다, 잘렸다, 다른 인쇄 판). 값을 읽지 않는다 | 아래 [양식 없는 쪽과 정합 실패 쪽](#양식-없는-쪽과-정합-실패-쪽) |
| 오류 난 쪽 N | 쪽을 처리하다 프로그램 오류가 났다. 그 쪽만 빠지고 같은 문서의 다른 쪽은 적재됐다 | `minedocscan pages --status error` 의 오류 열을 본다. serve 를 멈추고 `minedocscan run --skip-existing` 으로 다시 해 본다 (오류 난 쪽이 있는 문서는 다시 한다). 그래도 나면 그 오류 줄을 개발자에게 보낸다 |
| 실패한 문서 N | 파일을 열지 못했다. 쪽도 값도 없다 | 아래 [실패한 문서](#실패한-문서) |
| 다시 처리 대기 N | 날짜·버리기 같은 결정을 저장했거나 새로 받은 문서가 처리를 기다린다. 보통 몇 초 안에 줄어든다 | 줄지 않으면 윗줄의 "작업:"을 본다 ([아래](#윗줄--작업)). 보관 폴더가 네트워크 드라이브라 끊겼으면 처리하지 못하고 기다린다 (로그: "원본에 닿지 않은 문서 N건") — 연결하면 다음 바퀴에 처리한다 |
| 경로가 너무 길어 접수하지 않은 파일 N (접수 폴더에 그대로) | 보관할 경로(보관 폴더 + `intake\<해-달>\<받은 시각>-<문서 ID>\` + 파일 이름)가 259자를 넘는다. 윈도우가 그런 경로를 만들지 못해 접수하지 않았다. 파일은 접수 폴더에 그대로 있다 | 접수 폴더에서 그 파일의 이름을 줄인다. 이름에 작업한 날이 들어 있으면 그 부분은 남긴다 (날짜를 이름에서 읽는다). 다음 바퀴에 접수한다. 자주 생기면 관리자가 보관 폴더를 짧은 경로로 옮긴다 — 작업을 멈추고, 폴더를 통째로 옮기고, 설정의 `[paths] archive_root` 를 고치고, 작업을 켠다 |

### 양식 없는 쪽과 정합 실패 쪽

어느 쪽인지 먼저 찾는다. 출처 열이 `파일명#쪽 번호` 다. `--thumbs` 는 그 쪽들을 줄인 그림을 `<작업 폴더>\thumbs\<상태>\` 에 쓴다 (파일 이름에 문서 ID).

```powershell
minedocscan pages --status unknown_form --thumbs
minedocscan pages --status align_failed
```

그다음 홈의 "최근 문서"에서 그 파일명을 눌러 문서 화면에서 쪽을 본다.

| 쪽이 무엇인가 | 할 일 |
|---|---|
| 빈 뒷면, 표지, 양식이 아닌 서류 | 그 쪽의 "이 쪽 버리기" |
| 많이 기울었거나 접혔거나 잘린 스캔 | **그 종이만** 다시 스캔한다 (새 문서로 들어온다). 이 쪽은 "이 쪽 버리기" |
| 템플릿이 아직 없는 양식 | 관리자가 템플릿을 더한다 ([7장](7-새-양식-더하기.md)). 그다음 serve 를 멈추고 `minedocscan run --fresh` ([5장](5-관리.md#다시-처리)) |
| 같은 양식의 쪽이 어느 날부터 계속 정합에 실패한다 | 인쇄 판이 바뀌었을 수 있다. 관리자가 `minedocscan report --by-month` 로 달마다의 정합 실패를 보고 템플릿의 판을 더한다 ([SITE_PACK.md](../SITE_PACK.md)의 `valid_from`·"같은 날 섞여 쓰이는 판") |

빈 쪽(양면 스캔의 빈 뒷면)은 "할 일"에 세지 않는다. 문서 화면에 "빈 쪽"으로 나오고 적재하지 않는다. 할 일은 없다.
목록은 `minedocscan pages --status blank`.

### 실패한 문서

홈의 "최근 문서"에서 상태가 "실패"인 파일명을 누르면 문서 화면 위에 까닭이 한 줄 나온다. 목록은 이 명령으로 본다.

```powershell
minedocscan doc list --status failed
```

| 문서 화면의 글 | 뜻 | 할 일 |
|---|---|---|
| "DamagedPdfError: PDF 를 열 수 없습니다 (잘린 파일?): …. 원본을 다시 받으세요" | 파일이 잘렸거나 PDF 가 아니다. 전송이 끊긴 파일에서 생긴다 | 그 종이를 다시 스캔한다. 스캐너 PC 에 멀쩡한 원래 파일이 남아 있으면 그것을 접수 폴더에 다시 넣어도 된다. 새 파일은 새 문서로 들어온다. 실패한 문서는 "문서 버리기" — "실패한 문서" 수에서 빠진다 |
| "DamagedPdfError: PDF 의 끝 표시(%%EOF)가 없습니다 (잘린 파일?): …. 원본을 다시 받으세요 (스캐너가 만든 멀쩡한 파일이면 [pipeline] damaged_pdf = "warn")" | 파일 끝 1 KB 에 PDF 의 끝 표시가 없다. 보통은 덜 쓰이거나 잘린 파일이다 | 대개 위와 같다. 다만 이 스캐너가 만든 PDF 가 **늘** 이렇고 열어 보면 쪽이 다 있으면, 관리자가 설정 파일의 `[pipeline]` 에 `damaged_pdf = "warn"` 을 적는다. 그다음 serve 를 멈추고 `minedocscan run --skip-existing` (실패한 문서를 다시 한다) → 켠다. `warn` 이면 열리는 파일은 처리하고 경고를 남긴다 |
| 그 밖의 한 줄 (그림 파일이 깨졌다 …) | 파일을 읽지 못했다 | 그 종이를 다시 스캔하고 실패한 문서는 버린다. 같은 글이 되풀이되면 그 줄을 개발자에게 보낸다 |

- 끝까지 쓰이지 않는 PDF 는 접수가 120초(`[intake] give_up_seconds`) 기다린 뒤 등록한다. 그래서 잘린 파일은 2분쯤 뒤에 "실패"로 나온다.
- 버린 문서는 문서 화면의 "문서 되살리기"로 되돌린다.
- 버린 실패 문서는 관리자가 작업 DB 를 다시 만들어도(`run --fresh`) "버림"으로 남는다. 되살리면 다시 "실패"다 (열리지 않는 파일이므로).

## 윗줄 — 작업

| 홈에 보이는 것 | 뜻 | 할 일 |
|---|---|---|
| 작업: 쉬는 중 | 접수 폴더를 보며 기다린다 | 없다 |
| 작업: 처리 중 — 문서 … 3/14쪽 | 그 문서를 처리하고 있다 | 기다린다 |
| 작업: 엑셀 쓰는 중 — N초째 / 작업: 통합 DB 에 싣는 중 — N초째 | 바퀴 끝의 일이다. 그동안 접수·처리는 기다린다 | 보통 몇 초다. 통합 DB 가 1분 넘게 이어지면 대상 서버가 기다리게 하는 것이다 — 프로그램이 1분 반쯤 안에 스스로 그만두고 다음에 다시 한다. 아래 [통합 DB](#윗줄--통합-db) 표 |
| … · 지난 바퀴 오류 (영문 이름) | 한 바퀴가 통째로 실패했다. 접수 폴더나 보관 폴더에 닿지 않을 때가 많다. 다음 바퀴에 다시 한다 | 접수 폴더와 보관 폴더가 열리는지 본다 (네트워크 드라이브면 연결). 계속되면 로그와 그 이름을 관리자에게 |
| 작업: 꺼짐 (--no-watch — 처리는 watch 가 합니다) | 화면만 띄운 serve 다. 처리는 따로 띄운 `watch` 가 한다 | 작업 스케줄러의 serve 는 이렇지 않다. 손으로 띄웠으면 `--no-watch` 없이 띄운다 |

## 윗줄 — 엑셀

| 홈에 보이는 것 | 뜻 | 할 일 |
|---|---|---|
| 쓰지 못함 N개 (열려 있는 파일 — 잠시 뒤에 다시) | 엑셀이 그 파일을 열고 있어 바꾸지 못했다. 윈도우는 열린 파일을 바꿀 수 없다 | 그 파일을 엑셀에서 닫는다. 60초(`[export] retry_seconds`) 뒤의 바퀴에 다시 쓴다. 열어 둔 파일은 닫을 때까지 예전 내용이다. 늘 열어 두고 보려면 폴더의 파일 대신 홈 "최근 문서"의 "엑셀"·"월" 내려받기를 연다 — 그때 만든 사본이라 폴더의 파일을 잡지 않는다 |
| 폴더가 없습니다 | 엑셀 폴더(`[export] excel_dir`)가 없다. 네트워크 드라이브가 끊겼거나 폴더를 옮겼다. 프로그램은 엑셀 폴더를 만들지 않는다 | 드라이브를 연결하거나 폴더를 만든다. 다음 바퀴에 쓴다. 그동안에도 처리는 계속된다 |
| 다른 사이트의 폴더 (쓰지도 지우지도 않음) | 그 폴더의 기록 파일 `.minedocscan-export.json` 에 다른 사이트 이름이 적혀 있다. 남의 사본을 덮지 않으려고 멈췄다 | 설정의 엑셀 폴더가 맞는지 본다 (다른 현장의 폴더를 가리키고 있지 않은가). 이 현장의 사이트 이름을 일부러 바꿨으면 그 기록 파일을 지운다 — [5장](5-관리.md#사이트-이름을-바꿀-때) |
| 엑셀: 꺼짐 (…) | 자동 엑셀이 꺼져 있다 | 괄호 안이 까닭이다 — [3장의 표](3-처음-설정.md#홈-열기) |
| 처음 훑는 중 3/13 · 훑는 중 3/13 | 엑셀 폴더 전체를 달마다 한 조각씩 맞추는 중이다 | 기다린다 |

엑셀의 `?` 칸은 문제가 아니다 — [그 밖의 문제](#그-밖의-문제).

## 윗줄 — 통합 DB

통합 DB 에 싣지 못하면 윗줄에 "싣지 못함 (까닭, 밀린 범위 N)"이 붉게 나온다. **그동안에도 접수·처리·엑셀은 계속된다.** 싣지 못한 문서·날짜("밀린 범위")는
들고 있다가 60초(`[publish] retry_seconds`)마다 다시 해 본다. 서버가 돌아오면 저절로 따라온다.

까닭을 한 줄로 보려면 PowerShell 에서 `minedocscan publish --check` 를 친다 (serve 가 돌아도 된다 — 쓰지 않는다). 종료 코드 2 와 함께 까닭이 나온다.

| 괄호 안 | 뜻 | 할 일 |
|---|---|---|
| 대상의 잠금을 기다리다 그만둠 | 다른 연결이 실은 표를 쥐고 있다 (DB 도구에서 고치고 커밋하지 않았다, 표를 고치는 작업 …). 5초(`[publish] lock_timeout_s`) 기다리고 그만뒀다. 대상은 싣기 전 그대로다 | 통합 DB 관리자에게 알려 그 연결을 끝내게 한다. 풀리면 다음 시도에 따라온다. 실은 표에는 이 프로그램만 쓴다 |
| 대상의 시간 제한을 넘김 | 문장 하나가 60초(`[publish] statement_timeout_s`)를 넘었거나 관리자가 취소했다 | 저절로 다시 한다. 되풀이되면 서버가 느린 것이다 — 통합 DB 관리자에게 알린다. 서버가 원래 느리면 관리자가 `statement_timeout_s` 를 늘린다 |
| 닿지 못함 | 서버에 연결하지 못했다 — 서버가 꺼졌다, 망이 끊겼다, 주소·계정·비밀번호가 틀렸다 | 계속되면 `minedocscan publish --check` 의 줄을 본다. 사용자 환경 변수 `MINEDOCSCAN_PUBLISH_URL` 과 `pgpass.conf` 를 확인한다 ([2장](2-설치.md#통합-db-의-비밀번호)). 환경 변수를 고쳤으면 다시 로그온한다 |
| 싣는 가운데 연결이 끊김 | 싣다가 연결이 끊겼다 (서버가 꺼졌다, 망, 서버가 멈췄다). 커밋하지 못한 것은 서버가 되돌린다 — 대상은 싣기 전 그대로다 | 저절로 다시 한다. 되풀이되면 서버와 망을 통합 DB 관리자와 본다 |
| 다른 사이트의 대상 | 그 스키마에 다른 사이트 팩의 사본이 있다. 덮지 않으려고 싣지 않는다 | 주소(`MINEDOCSCAN_PUBLISH_URL`)와 `[publish] schema` 가 맞는지 본다. 이 현장의 사이트 이름을 일부러 바꿨으면 `publish --rebuild` ([5장](5-관리.md#사이트-이름을-바꿀-때)) |
| 이 프로그램이 만들지 않은 표 | 그 스키마에 이름이 같은 표가 있는데 이 프로그램이 만든 것이 아니다. 지우지도 쓰지도 않는다 | 다른 스키마를 쓰거나(`[publish] schema`), 통합 DB 관리자가 그 표를 치운다 |
| 판이 다름 — publish --rebuild | 대상이 다른 판의 프로그램으로 실렸다 (1.0.0 전의 판, 작업 DB 스키마가 바뀐 판) | serve 를 멈추고 `minedocscan publish --rebuild` 를 돌린 뒤 켠다 ([5장](5-관리.md#통합-db-관리)) |
| orphans | 작업 DB 에 어느 문서·날짜에도 들지 않는 행이 있어 싣지 않는다 | serve 를 멈추고 `minedocscan run --fresh` 를 돌린 뒤 켠다 |
| (붉은 글) 작업 DB 에 쪽이 없어 싣지 않음 (통합 DB 는 그대로) | 작업 DB 에 쪽이 하나도 없다 (새 PC, 작업 DB 를 지웠다, 되살리는 중). 그대로 실으면 대상이 비므로 싣지 않는다 | 작업 DB 를 되살린다 ([5장](5-관리.md#백업에서-되살리기)) — 쪽이 생기면 1분쯤 뒤에 저절로 싣는다. 정말 대상을 비우려면 `publish --rebuild` |
| 그 밖의 영문 이름 (보기: InsufficientPrivilege) | 대상 서버가 낸 오류의 종류다. InsufficientPrivilege 는 그 계정에 스키마의 권한이 없다는 뜻이다 | `minedocscan publish --check` 의 줄과 그 이름을 통합 DB 관리자에게 보낸다. 권한은 관리자가 준다 ([DATA.md](../DATA.md)의 "통합 DB") |
| (붉은 글) 실을 수 없는 값이 있어 건너뛴 범위 N | NUL 글자처럼 PostgreSQL 이 받지 않는 값이 든 문서·날짜다. 그 범위만 싣지 않았고, 대상에 있던 그 범위의 옛 행은 지웠다 | 다른 범위는 실렸다. 그 수를 개발자에게 알린다 |
| 통합 DB: 꺼짐 (…) | 싣기가 꺼져 있다 | 괄호 안이 까닭이다 — [3장의 표](3-처음-설정.md#홈-열기) |
| 실은 적 없음 · 처음 훑는 중 3/14 | serve 가 켜진 뒤 첫 전체 훑기다 — 달마다 한 조각씩 작업 DB 와 대상을 견주어 다른 것만 싣는다. 켤 때마다 이렇게 시작한다. 대상에 처음 싣는 것이면 다 돌 때까지 대상에는 앞의 달만 있다 | 기다린다. 처음 싣는 것을 한 번에 하려면 [5장](5-관리.md#통합-db-관리) |

## serve 가 켜지지 않을 때

홈(`http://127.0.0.1:8765/`)이 열리지 않으면 serve 가 돌지 않는 것이다. 작업 스케줄러는 창 없이 띄우므로 **까닭은 로그에 있다.**

1. 오늘 로그 `%LOCALAPPDATA%\minedocscan\logs\serve-YYYYMMDD.log` 를 메모장으로 열어 **맨 끝의 몇 줄**을 본다
   (까닭이 두 줄일 때가 있다 — 보기: "DB 오류: …" 다음 줄에 "`minedocscan run --fresh` 로 DB 를 다시 만드세요 …").
2. 아래 표대로 고친다.
3. 작업을 켠다: `Start-ScheduledTask -TaskName minedocscan-serve` (또는 다시 로그온).

<!-- 시험: 돌리지 않음 -->
```powershell
notepad "$env:LOCALAPPDATA\minedocscan\logs\serve-$(Get-Date -Format yyyyMMdd).log"
Get-ScheduledTask -TaskName minedocscan-serve          # State 가 Running 이면 돌고 있다
Get-ScheduledTaskInfo -TaskName minedocscan-serve      # 멈췄으면 LastRunTime 과 LastTaskResult (오류로 끝났으면 1)
Start-ScheduledTask -TaskName minedocscan-serve
```

| 로그의 끝에 보이는 것 | 뜻 | 할 일 |
|---|---|---|
| 포트 8765 를 열 수 없습니다 (…). 다른 프로그램이 쓰고 있으면 --port 로 바꾸세요 | 다른 프로그램이 8765 를 쓰고 있다. 창에서 띄운 `review serve`(또는 `serve --no-watch`)일 때가 많다 — 창에서 띄운 보통의 `serve` 면 아래 줄의 글이 먼저 나온다 | 그 창을 닫는다 (Ctrl+C). 어느 프로그램인지 모르면 PowerShell 에서 `Get-NetTCPConnection -LocalPort 8765` 의 `OwningProcess` 번호를 `Get-Process -Id <번호>` 로 본다. 그 프로그램을 끈 뒤 작업을 켠다. 바탕 화면의 바로 가기가 8765 를 열므로 작업의 포트는 바꾸지 않는다 |

## 자가 시험이 실패할 때

`minedocscan selftest` 는 검사마다 한 줄을 찍는다. 실패한 줄 끝에 까닭이 붙는다 ("실패 serve … — serve 가 포트를 알리기 전에 끝났다 …").
종료 코드는 통과 0, 실패 1, 받지 않는 `--publish-schema` 이름 2 다. 검사의 목록은 [3장](3-처음-설정.md#자가-시험)에 있다.

| 실패한 검사 | 흔한 까닭 | 할 일 |
|---|---|---|
| 까닭에 `DLL load failed` | 런타임 부품이 없다 | [설치할 때](#설치할-때)의 런타임 줄 |
| `synth` | 임시 폴더(`%TEMP%`)에 쓸 수 없다, 디스크가 찼다 | 디스크를 비우고 다시 돌린다. 보안 프로그램이 임시 폴더를 막는지 본다 |
| `intake`·`recognition`·`reprocess`·`excel`·`masked` | 이 PC 에서 프로그램이 기대와 다르게 돌았다 | `selftest.md` 를 개발자에게 보낸다 (경로·이름이 들어 있지 않다). `--keep` 으로 다시 돌리면 임시 폴더를 남긴다 |
| `serve` — "serve 가 포트를 알리기 전에 끝났다 (종료 코드 N): …" 또는 "serve 가 90초 안에 포트를 알리지 않았다" | 화면을 띄우지 못했다. 빈 포트를 쓰므로 8765 와는 상관없다 | 까닭의 마지막 부분을 본다. 보안 프로그램이 이 PC 안(127.0.0.1)의 서버를 막는지, PC 가 아주 느린지 본다 |
| `publish` — "--publish-schema 에는 환경변수 MINEDOCSCAN_PUBLISH_URL 이 있어야 한다" | 주소가 없다 | 사용자 환경 변수를 둔다 ([2장](2-설치.md#통합-db-의-비밀번호)) |
| `publish` — "그 스키마가 이미 있다 — …" | 지난 자가 시험이 남긴 스키마이거나 다른 것이다. 자가 시험이 만들지 않은 것은 건드리지 않는다 | 다른 이름(`minedocscan_selftest_…`)으로 다시 돌린다. 남은 스키마는 통합 DB 관리자가 지운다 |
| `publish` — "통합 DB: … (종류 …)" | 싣다가 실패했다 | 종류를 [윗줄 — 통합 DB](#윗줄--통합-db) 표에서 찾는다 (connect 는 "닿지 못함") |
| 건너뜀 — "앞의 검사(…)가 통과하지 않았다" | 앞의 검사가 실패해서 하지 않았다 | 앞의 실패부터 본다 |
| 건너뜀 `publish` — "요청하지 않았다" 또는 "… 권한(CREATE)이 없다 — 이 검사만 건너뛴다" | 실패가 아니다 | 없다 |

## 그 밖의 문제

**스캔했는데 홈의 "최근 문서"에 나오지 않는다.**

- `minedocscan info` 의 "접수 폴더:" 줄이 스캐너 프로그램의 저장 폴더인가. "없음"이면 접수하지 않는다.
- 스캐너가 아직 쓰는 중일 수 있다. 다 쓴 뒤 5초(`[intake] settle_seconds`)를 기다린다. PDF 는 끝 표시까지 있어야 다 쓴 것으로 본다.
  끝까지 쓰이지 않는 파일은 120초 뒤에 등록되어 "실패한 문서"가 된다.
- 보지 않는 파일이 있다: `_` 로 시작하는 폴더 안, `.`·`~` 로 시작하는 파일, PDF·그림(png, jpg, jpeg, tif, tiff, bmp)이 아닌 파일.
- 홈에 "경로가 너무 길어 접수하지 않은 파일"이 있는가 ([위](#할-일)).
- 윗줄의 "작업:"이 "쉬는 중"·"처리 중"인가. 홈이 열리지 않으면 [serve 가 켜지지 않을 때](#serve-가-켜지지-않을-때).

**접수 폴더에 `_already` 폴더가 생겼다.** 이미 받은 파일과 바이트까지 같은 파일이다. 같은 것이 보관 폴더에 있다. 할 일은 없다.

**접수 폴더에 `_failed` 폴더가 생겼다.** 120초가 지나도록 열 수조차 없었던 파일이다 (다른 프로그램이 잡고 있었다, 읽을 권한이 없다).
문서가 되지 않았고 보관 폴더에도 없다 (로그: "읽을 수 없는 파일(_failed) N"). 열리면 접수 폴더(맨 위)로 다시 옮긴다 — 다음 바퀴에 접수한다.
열리지 않으면 그 종이를 다시 스캔한다. 열리기는 하는데 깨진 파일은 여기 오지 않고 "실패한 문서"가 된다 ([위](#실패한-문서)).

**창에서 검수 화면을 띄우면 "포트 8765 를 열 수 없습니다".** 작업 스케줄러의 serve 가 8765 를 쓰고 있다. 따로 띄울 것 없이 serve 의
주소에 대기열 이름을 붙여 연다 (`http://127.0.0.1:8765/?name=haul-numbers` — [4장](4-날마다-쓰기.md#대기열-고르기)).
그래도 따로 띄워야 하면 다른 포트로 띄우고 브라우저에서 그 포트를 연다 (`http://127.0.0.1:8766/`).

<!-- 시험: 돌리지 않음 -->
```powershell
minedocscan review serve --queue haul-numbers --reviewer jp --port 8766
```

**명령이 "다른 파이프라인(run·watch·serve)이 이미 돌고 있습니다"로 끝난다.** serve 를 멈추고 친다 ([5장](5-관리.md#serve-를-멈추고-하는-명령)).

**`run --fresh` 가 "DB 를 지울 수 없습니다 — 다른 프로그램(serve, review serve)이 쓰고 있습니다"로 멈춘다.** 검수 화면 창과 serve 를 닫고 다시 친다.

**엑셀에 `?` 칸이 있다.** 아직 확정되지 않은 값이다 (검수 대기). `판독 불가` 는 사람이 읽을 수 없다고 한 칸이다.
엑셀에서 고치지 않는다 — 엑셀은 사본이라 고친 것이 프로그램으로 돌아오지 않고, 그날의 내용이 바뀌면 덮인다. 홈의 대기열에서 검수하면
다음 바퀴에 엑셀에 값이 나온다 ([4장의 "칸의 표시"](4-날마다-쓰기.md#칸의-표시)).

**교차검증이 맞지 않는다 (대기열 "mismatch").** 두 양식에 적힌 값이 다르다. 프로그램은 차이를 맞춰 넣지 않고 보여 준다.
대기열에서 두 칸의 그림을 보고 **각 칸에 적힌 대로** 넣는다. 종이끼리 정말 다르면 다른 채로 둔다 — 맞추는 것은 이 프로그램의 일이 아니다.

**날짜를 잘못 넣었다.** 문서 화면에서 맞는 날짜를 다시 넣는다 — 나중에 넣은 것이 이긴다. 쪽 하나만 다르면 그 쪽의 "이 쪽은 다른 날짜".

**잘못 버렸다.** 문서 화면의 "문서 되살리기", 쪽이면 그 쪽의 "되살리기". 명령으로는 `minedocscan doc restore <문서 ID 또는 쪽 ID> --reviewer jp`.
되살린 쪽이 다시 "다시 스캔 의심"으로 나오면 다시 고른다.

**쪽 하나가 잘못 버려졌는지 보고 싶다.** 문서 화면에서 버린 쪽은 흐리게 보인다. 목록은 `minedocscan pages --status discarded`.

## 물어볼 때

관리자나 개발자에게 물을 때 **보낼 것**:

- 화면의 글 그대로 (보기: "싣지 못함 (닿지 못함, 밀린 범위 3)", "정합 실패 쪽 2")
- 문서 ID·쪽 ID, 수
- 판: `minedocscan --version`
- 자가 시험의 `selftest.md`
- `minedocscan report` 의 결과
- 로그의 그 줄 (폴더 경로가 있으면 지운다)

```powershell
minedocscan --version
```

**보내지 않을 것**: 화면 갈무리, 엑셀 파일, 쪽 그림, 로그 파일 통째, `pages`·`doc list` 의 파일명 열, 통합 DB 의 주소·계정·비밀번호.
작업자 이름·서명·차량번호가 들어 있는 현장 데이터다.
