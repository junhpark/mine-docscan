## 1. 왜 하는가

숫자 인식기(0003)가 운반 횟수를 읽게 되었다. 그런데 일보 한 장이 행렬의 어느 자리인지는 아직 사람이 정한다:
차량번호와 작성자를 `labels/pages.json` 에 적거나 `page-fields` 대기열에서 입력해야 한다. 일보가 약 1,500쪽이다.
이것이 풀려야 교차검증과 배차 관측이 전 기간에서 사람 손 없이 돈다.

그리고 점검표의 ✓(이상 유/무) 판정에는 아직 정답이 없다. 675행 중 유 288 / 무 286 이라는 수치는 판정 결과이지 정확도가 아니다.

실제 일보를 보고 알게 된 것 (3일치 30쪽):

- **차량번호는 전부 네 자리 숫자**이고 11종이다. 인쇄된 "차량번호:" 뒤에 크게, 띄엄띄엄 쓴다. 여러 번호가 앞 두 자리가 같다.
- **작성자는 10명**이고 날마다 같은 사람이 자기 이름을 같은 글씨로 쓴다.
- 날짜 줄은 "20__년 __월 __일 __요일" 이 인쇄되어 있고 월·일·요일만 손으로 쓴다. 연도는 인쇄된 값이고 묵은 양식에서는 틀려 있다(위에 덧쓴다).
- 30쪽 중 8쪽은 행렬에 인쇄된 머리글(운전자·차량)과 실제가 달랐다 (이미 아는 것 — ADR 0004).

## 2. 끝났을 때 되는 일

```bash
minedocscan review serve --queue page-fields --reviewer jp          # 정답: 기계 값을 보지 않고 입력 (지금과 같다)
minedocscan review export-crops ~/meta --meta --split train         # 메타 필드의 크롭 + 정답 (검수·라벨·파일명 날짜)

minedocscan recognizer train --crops ~/meta --meta-key vehicle_no --name veh-v1 --cv 5     # 숫자: 읽고, 닫힌 목록에서 고른다
minedocscan recognizer train --crops ~/meta --meta-key operator   --name op-v1  --cv 5     # 이름: 닫힌 집합 분류
minedocscan recognizer eval  --crops ~/meta --model op-v1 --split val --errors

# 설정: [recognize.meta] vehicle_no = "veh-v1", operator = "op-v1"
minedocscan run DB_scans --fresh
minedocscan report                           # 일보 중 자리가 정해진 쪽: 사람 값 / 기계 값 / 못 정함. 기계 값과 사람 값이 다른 쪽
minedocscan eval --meta --split test         # 키마다 정확도, 자동 적재율, 자동 적재 오류율(구간), 목록에 없는 값
minedocscan pages --meta-mismatch            # 기계가 읽은 값이 사람·파일명의 값과 다른 쪽 (날짜 포함)

minedocscan review serve --queue checks --n 300 --reviewer jp       # ✓ 정답: 행마다 1(유) / 2(무) / Enter(표시 없음) / ?
minedocscan eval --checks                    # ✓ 판정의 정확도
```

## 3. 범위

**이번에 한다**
- 0003 에서 남은 손질 (단계 1)
- 쪽 메타의 출처를 DB 에 남기고, 메타 필드의 크롭과 정답을 내보낸다 (단계 2)
- 숫자로 된 메타 필드(차량번호, 날짜의 월·일)를 숫자 인식기로 읽고 닫힌 목록에서 고른다 (단계 3)
- 이름 필드(작성자)를 닫힌 집합 분류기로 읽는다 (단계 4)
- 읽은 값을 쪽 메타에 쓰고, 사람·파일명의 값과 대조하고, 평가한다 (단계 5)
- ✓ 판정의 정답을 만드는 대기열과 평가 (단계 6)

**이번에 하지 않는다**
- 날짜를 읽은 값으로 **정하는 것**. 날짜는 지금처럼 파일명 규칙과 라벨이 정하고, 읽은 월·일은 대조에만 쓴다 (4.3).
  읽은 날짜가 날짜의 출처가 되는 것은 폴더 감시(스캔 시각 ≠ 작업일)를 만들 때다 (ROADMAP M5)
- 요일, 연도 읽기. 행렬 양식의 작성자·가동시간·연료 칸
- 작성자와 차량의 짝을 이용한 판단(평소의 짝과 다르면 검수로 보내기 등). 실데이터의 수치를 본 뒤 정한다 (9절)
- 손글씨 텍스트(점검내역) 인식, 교정 백엔드
- 판정 규칙(정합·체크·잉크·덩어리)의 변경. ✓ 판정은 **재는 것**이지 고치는 것이 아니다. `null` 백엔드의 회귀 수치는 바뀌면 안 된다
- 외부 데이터·외부 API (ADR 0003)

## 4. 이미 정한 것

### 4.1 읽는 법은 둘이다: 숫자는 내용을 읽고, 이름은 고른다

- **숫자로 된 메타 필드**(차량번호, 월, 일): 0003 의 숫자 모델(CTC)로 읽는다. 다만 자유롭게 읽은 문자열을 쓰지 않고
  **닫힌 목록의 후보마다 그 문자열일 가능도를 계산해 가장 그럴듯한 후보를 고른다** (가능도 계산은 `recognize/digits/calib.py` 에 이미 있다).
  신뢰도 = 후보들 사이에서 정규화한 확률. 자유롭게 읽은 문자열이 목록에 없고 어느 후보보다도 뚜렷이 그럴듯하면 "목록에 없는 값"으로 답하고 검수로 보낸다 (새 차).
- **이름 필드**(작성자): 닫힌 집합 분류기. 종류 = 학습 때 본 값. 새 사람은 모른다 → 신뢰도가 낮게 나오고 검수로 간다.
- 차량번호를 분류기로 풀지 않는 이유: 한 차의 번호는 늘 같은 사람이 쓴다. 분류기는 숫자가 아니라 글씨체를 외우게 되고,
  그러면 운전자가 다른 차를 탄 날에 평소의 차로 읽는다 — 배차 관측이 잡으려는 바로 그 사건을 놓친다. 그래서 차량번호는 내용(숫자)을 읽는다.
  작성자는 반대로 글씨체가 곧 단서다.
- 사전 확인 (2026-10-04, 실제 일보 30쪽, 하루를 빼고 나머지 이틀로 학습 — **종류당 예 2개**. 표본이 작다, 참고만):
  - 작은 합성곱 분류기(합성곱 4층 + 전역 최대 풀링, 입력 40×128, 250 스텝, 약한 변형): 작성자 29/30, 차량번호 23/29.
    틀린 작성자 하나의 신뢰도는 0.52 (맞은 것의 중앙 0.87).
  - 기울기 히스토그램 + 가장 비슷한 예 찾기(학습 없음): 작성자 22/30, 차량번호 17/29 — 쓰지 않는다.
  - `cv2.HOGDescriptor` 는 OpenCV 5.0 에 없다. OpenCV 의 부가 기능에 기대지 않는다.
- 분류기도 0003 과 같은 길로 간다: 학습은 torch, 추론은 ONNX 를 `cv2.dnn` 으로, 합성곱·배치 정규화·ReLU·풀링·완전연결만.

### 4.2 닫힌 목록은 검수와 무관하게 정해진다

- 기계가 고를 후보 목록 = **모델이 학습 때 본 값 + 템플릿에 인쇄된 값**(행렬 머리글의 운전자·차량). 월은 1–12, 일은 1–31.
- 검수에 새로 나온 값은 다음 학습 때 목록에 들어간다. 검수를 저장하는 순간에 목록이 바뀌면 다른 쪽의 기계 값이 달라져
  "기계 값은 검수가 건드리지 않는다"(ADR 0008)와 불변식이 깨진다.
- 검수 화면의 후보 목록(`<datalist>`, 사람의 입력을 돕는 것)은 지금처럼 검수값을 포함해도 된다 — 그것은 기계 값이 아니다.

### 4.3 기계가 읽은 값은 메타의 맨 아래다. 위에 값이 있으면 대조만 한다

- 쪽 메타의 우선순위: **검수값 > 페이지 라벨 > 문서 라벨 > 파일명 규칙 > 기계가 읽은 값(자동 적재 기준을 넘은 것만).**
- 위에 값이 없으면 기계 값이 그 자리를 채운다 (차량번호·작성자). 기준을 못 넘었으면 지금처럼 비어 있고 `page-fields` 대기열에 나온다.
- 위에 값이 있으면 기계 값은 **대조에만** 쓴다. 다르면 다르다고 표시한다 — 고치지 않는다 (ADR 0006).
  라벨을 잘못 적었거나, 다른 날의 쪽이 섞였거나, 기계가 틀린 것이다. 어느 쪽인지는 사람이 본다.
- 날짜는 언제나 위(파일명·라벨)에 값이 있다. 그래서 월·일은 대조만 된다. 템플릿의 키 `date.month`, `date.day` 는 읽기 전용이고
  그 정답은 쪽의 날짜에서 나온다. `meta_key: date` 는 여전히 받지 않는다 (0002 의 4.1).

### 4.4 쪽 메타에도 출처를 남긴다

- 새 테이블 `doc_page_meta`: 쪽 × 키마다 한 행 — 최종 값, 출처(`review | label | filename | machine`),
  기계가 읽은 값·신뢰도·기계의 상태(`auto | pending | unlisted`), 대조(`match | mismatch | unread | none`), 그 필드의 `field_id`.
- 지금은 차량번호·작성자가 어디서 왔는지가 DB 에 없다 ("모든 값은 출처를 가진다" — 원칙 3).
- 기계 열은 검수가 건드리지 않는다. 불변식(저장 직후의 DB = 같은 검수 파일로 새로 돌린 DB)은 이 테이블에도 성립한다.
- `prod_haul` 의 차량·작성자, 자리(slot), `eq_assignment_obs` 는 이 테이블의 최종 값에서 만든다.

### 4.5 자동 적재 기준은 0003 의 규칙 그대로, 다만 정답이 적을 때는 날짜 묶음으로 돌려 가며 잰다

- 규칙(ADR 0012): 검증 칸에서 오류율이 목표 이하인 가장 낮은 임계값, 그 임계값에서 자동 적재된 검증 칸이 최소 수(기본 100) 미만이면 기준 없음,
  고른 기준 옆에는 윌슨 95 % 상한.
- 메타 필드는 쪽마다 하나라 정답이 적다 (20일치를 입력해도 약 200쪽). 검증으로 20 % 를 떼면 40쪽이고 기준이 나오지 않는다.
  그래서 `--cv K`: train 날짜를 K 묶음으로 나눠(날짜 단위, 소금값으로 고정) 묶음마다 "나머지로 학습 → 그 묶음을 읽기"를 하고,
  **그렇게 모은 읽기 전체**에서 온도와 기준을 정한다. 내보내는 모델은 train 날짜 전부로 학습한 것이다. 카드에 그렇게 적는다.
- `test` 는 여전히 학습·기준에 쓰지 않는다 (ADR 0009). `--cv` 가 없으면 0003 과 같은 방식(검증 날짜)이다.
- 메타 필드의 목표 오류율 기본값은 2 % 다 (9절). 틀린 메타는 틀린 자리로 이어지고, 그 쪽은 교차검증 불일치로 드러난다.

### 4.6 정답은 기계 값을 보지 않고 만든다. 자동 적재된 쪽도 표본으로 다시 본다

- `page-fields` 대기열은 지금처럼 기계 값을 보여 주지 않는다 (ADR 0008). 후보 목록의 순서도 기계의 답과 무관하다.
- 모델을 쓰기 시작하면 사람은 기계가 못 정한 쪽만 보게 된다. 그러면 자동 적재된 쪽의 오류를 잴 정답이 생기지 않는다.
  그래서 `--audit N`: 기계의 상태와 상관없이 날짜별로 고르게 뽑은 쪽 N 개를 (기계 값 없이) 보여 준다. 표본은 씨앗으로 고정된다.
- ✓ 정답(단계 6)도 같다: 기계의 판정을 보여 주지 않는다.

### 4.7 모델과 이름은 사이트 팩에만

- 모델은 `<site>/models/<이름>/` (ADR 0011). 분류기의 종류 목록(이름, 차량번호)은 그 폴더의 `classes.json` 에 둔다.
  **카드·로그·오류 메시지·PR 에는 이름과 차량번호를 적지 않는다** — 종류의 수와 종류별 개수의 분포(이름 없이)만.
- 시험과 문서에는 합성 값만 쓴다 (`ALPHA`, `V-101`, 합성 네 자리 번호).
- 저장소에 두는 시험용 모델은 합성 데이터로만 학습한 것, 1 MB 이하, 다시 만드는 명령과 함께 (`tests/fixtures/README.md`).

### 4.8 합성 데이터는 OpenCV 판과 무관해야 한다

- 0003 에서 배운 것: OpenCV 내장 글꼴은 4.x 와 5.0 에서 모양이 다르다. 그 글꼴로 만든 합성 셀로 학습한 시험용 모델은 다른 판에서 틀린다.
- 이번에 모델이 읽게 되는 합성 필드(차량번호, 작성자, 월·일)는 자체 획으로 그린다. 작성자는 "사람마다 다른 글씨"가 드러나야 한다
  (획의 기울기·굵기·크기·간격이 사람마다 다르게). CI 의 하한 판 작업(`lowest`)이 이 PR 의 시험도 돌린다.
- 기본 합성 데이터(지금의 테스트가 쓰는 것)는 바이트까지 그대로 둔다. 새 모양은 선택 기능으로 만든다 (0003 의 `low_cells` 처럼).

### 4.9 ✓ 검수는 새 판정 종류를 만들지 않는다

- 행의 답(유 / 무 / 표시 없음 / 모름)을 **두 체크 칸의 기존 판정**으로 적는다:
  유 = 유 칸 `value`·무 칸 `empty`, 무 = 그 반대, 표시 없음 = 둘 다 `empty`, 모름 = 둘 다 `illegible`.
- 그래서 검수 기록의 형식, `apply_verdict`, 핸들러의 `daily_values`·`on_review` 는 그대로 쓴다. 두 칸은 한 번의 저장으로 같이 적는다.

### 4.10 스키마 버전 5

- `doc_page_meta` (4.4). 마이그레이션은 만들지 않는다 (ADR 0005). `--fresh` 로 다시 만든다.

### 단계 2 — 쪽 메타의 출처, 메타 필드의 크롭과 정답

할 일
- `doc_page_meta` (4.4). 지금 `review/store.page_meta()` 가 계산하는 것을 이 테이블에 적고, 핸들러·교차검증은 여기서 읽는다.
  이 단계에서는 기계 값이 아직 없다 (열은 비어 있다).
- 템플릿: `fields[]` 의 `meta_key` 에 `date.month`, `date.day` 를 받는다 (읽기 전용, 4.3). `docs/SITE_PACK.md` 에 실제 템플릿에 넣을 조각을 예로.
- `review export-crops --meta [--meta-key K]`: `meta_key` 가 있는 필드의 크롭과 정답을 내보낸다.
  - 정답 = 그 쪽 메타의 **사람·파일명** 값(검수 > 라벨 > 파일명). 기계 값은 정답이 아니다. 줄마다 출처(`label_source`)를 적는다.
  - 값이 없는 쪽은 내보내지 않는다. `illegible` 로 검수된 필드는 `--include-illegible` 일 때만.
  - 분할(날짜), 규격(`spec`), 저장소 안 거절, 파일 이름 규칙은 0002·0003 과 같다. 폴더는 `OUT/<split>/meta/<키>/`.
- 메타 필드의 크롭 규격: 필드는 표의 칸이 아니라 여유의 "행 높이의 절반" 규칙이 맞지 않는다 (60 px 높이의 필드에 30 px). 고정 여유(기본 8 px)를 쓴다.
- 합성 데이터의 선택 기능 (4.8): 일보의 차량번호가 네 자리 숫자, 작성자는 사람마다 다른 획, 날짜 줄에 월·일 필드.
  배차가 바뀌는 날(같은 사람이 다른 차), 처음 보는 차, 다른 날의 쪽이 섞인 묶음을 만들 수 있게.

수용 기준 (합성 데이터)
- `doc_page_meta` 에서 만든 `prod_haul`·`xcheck_haul`·`eq_assignment_obs` 가 전과 같다 (기존 테스트 불변).
- 라벨을 비우고 같은 값을 검수로 넣으면 최종 값은 같고 출처만 `review` 로 바뀐다. 불변식이 이 테이블을 포함해 성립한다.
- `export-crops --meta` 의 줄 수 = PNG 수 = 사람·파일명 값이 있는 (쪽, 키) 수. `test` 와 `train` 이 섞이지 않는다.
- 같은 씨앗의 합성 필드가 OpenCV 5.0 과 하한 판에서 거의 같다 (0003 과 같은 기준).

### 단계 3 — 숫자로 된 메타 필드

할 일
- `recognizer train --meta-key K`: `export-crops --meta` 의 폴더에서 그 키의 줄만 읽어 숫자 모델을 학습한다.
  정답이 전부 숫자열이면 숫자 모델, 아니면 단계 4 의 분류기 — `--reader digits|choice` 로 바꿀 수 있다.
- 합성 셀: 필드의 크기와 규격으로, 자릿수는 정답에 나온 자릿수(차량번호 4, 월·일 1–2)로. 인쇄된 글자가 섞인 배경(예: "월", "일", 밑줄)도 넣는다.
- 닫힌 목록에서 고르기 (4.1): 후보 가능도, 정규화한 신뢰도, "목록에 없는 값". 후보 목록은 4.2 — 모델 폴더의 `classes.json` 과 템플릿.
- `--cv K` (4.5).
- 백엔드: 키마다 모델 하나. 설정 `[recognize.meta] <키> = "<모델 이름>"` (설정 파일 > `site.toml`).
  모델이 없는 키는 지금처럼 읽지 않는다. 카드에 키와 읽는 법을 적고, 다른 키에 꽂으면 시작할 때 오류.
- `recognizer eval` 이 메타 모델도 받는다 (크롭 단위, 0003 과 같은 출력 + 목록에 없는 값의 수).

수용 기준 (합성 데이터. 학습이 필요한 것은 `pytest -m train`)
- 합성 차량번호(네 자리, 앞 두 자리가 같은 번호들 포함)에서 닫힌 목록으로 고른 답의 정확도가 자유롭게 읽은 답보다 낮지 않고 0.97 이상.
- **글씨체가 아니라 숫자를 읽는다**: 학습에서는 번호마다 쓰는 사람이 정해져 있고, 시험에서는 사람과 번호의 짝을 바꾼 쪽만 모았을 때 정확도 0.95 이상.
- 목록에 없는 번호를 쓴 쪽은 "목록에 없는 값"으로 답하고 자동 적재되지 않는다 (0.9 이상에서).
- `--cv 5` 로 정한 기준·온도가 카드에 방식과 함께 적히고, 묶음의 날짜가 서로 겹치지 않으며 `test` 날짜가 들어가지 않는다.
- 기계의 후보 목록은 검수를 저장해도 바뀌지 않는다.

### 단계 4 — 이름 필드: 닫힌 집합 분류기

할 일
- `recognize/choice/` — 학습(torch)과 추론(torch 없음)을 파일로 나눈다. 입력·망은 4.1 의 사전 확인에서 시작하면 된다.
- 학습: 종류 = 학습 날짜에 예가 최소 수(기본 3) 이상인 값. 그보다 적은 값은 종류로 두지 않고 그 수를 알린다. 약한 변형, 좌우 뒤집기 없음.
- 답: 종류 하나 + 신뢰도(온도 보정) + 후보 상위 5. 기준은 4.5. 카드는 0003 의 항목 + 종류 수·종류별 개수 분포 (이름 없이, 4.7).
- `recognizer train --meta-key operator …`, `recognizer list`, `recognizer eval` 이 분류기도 다룬다. 틀린 칸 모아 보기는 저장소 밖에만.
- 시험용 모델 (4.7, 4.8).

수용 기준 (합성 데이터)
- 합성 작성자 6명, 종류당 예 5개로 학습한 분류기가 다른 날짜의 쪽에서 0.95 이상 (`train`).
- 학습에 없던 사람이 쓴 쪽은 기준을 넘지 못한다 (자동 적재 0, 또는 5 % 이하).
- torch 출력과 OpenCV 출력의 차이 1e-3 미만, 고른 종류가 전부 같다. 기본 `pytest`(torch 없음)에서 시험용 모델로 추론이 돈다 — 5.0 과 하한 판 모두.
- 카드·학습 로그·표준 출력에 종류의 값(이름)이 없다.

### 단계 5 — 파이프라인에 넣기: 채우기, 대조, 평가

할 일
- 메타 필드는 핸들러보다 먼저 읽는다 (쪽 메타가 핸들러가 행을 만들기 전에 정해져 있어야 한다).
  읽은 결과는 그 필드의 `doc_field` 행(기계 값: `value_raw`, `confidence`, `backend`, `status_raw`, `candidates`)과 `doc_page_meta` 에 같이 남는다.
- 채우기와 대조 (4.3). 기계의 상태: 기준을 넘으면 `auto`, 못 넘으면 `pending`, 목록에 없는 값이면 `unlisted`.
- 날짜: 읽은 월·일을 쪽의 날짜와 대조한다. 둘 다 기준을 넘었는데 다르면 `mismatch`.
- `report`: 키마다 출처별 쪽 수(사람 / 파일명 / 기계 / 없음), 대조 결과별 쪽 수. 일보 중 자리가 정해진 쪽의 수와 그 출처.
- `pages --meta-mismatch [--meta-key K]`: 대조가 `mismatch` 인 쪽 (출처, 날짜, 양식, 키). **값은 찍지 않는다** — 화면에서 본다.
- 대기열
  - `page-fields`: 최종 값이 없는 (쪽, 키)만 — 기계가 채운 쪽은 나오지 않는다. `--audit N` (4.6).
  - `meta-check`: 기계 값과 사람 값이 다른 쪽 (날짜 키는 제외 — 날짜는 검수로 받지 않는다). 여기서는 두 값을 보여 주고 맞는 값을 입력받는다.
- `eval --meta [--split …]`: 키마다 — 사람 값이 있는 쪽에서 기계 값의 정확도, 자동 적재율, 자동 적재 오류율(분자·분모·윌슨 구간), 목록에 없는 값의 수,
  **배차가 바뀐 쪽**(그 작성자의 가장 흔한 차가 아닌 차를 탄 쪽)만의 정확도. 그리고 기계 값만으로 정한 자리가 사람 값으로 정한 자리와 같은 쪽의 비율.
- `info`: 키마다 모델·읽는 법·기준(상한 포함).

수용 기준 (합성 데이터, 시험용 모델, **torch 없이**)
- 라벨을 비운 합성 묶음을 돌리면: 차량번호·작성자가 기계 값으로 채워지고, `xcheck_haul`·`eq_assignment_obs` 가 라벨이 있을 때와 같다
  (학습된 모델이므로 "전부 같다"가 아니라 문턱으로: 자리가 맞게 정해진 쪽 0.95 이상, 자동 적재된 메타 중 틀린 것 2 % 이하).
- 라벨이 있으면 최종 값은 라벨이고, 일부러 틀리게 적은 라벨은 `mismatch` 로 나온다. 최종 값은 바뀌지 않는다.
- 다른 날의 쪽을 섞은 묶음에서 그 쪽이 날짜 `mismatch` 로 나온다. `work_date` 는 바뀌지 않는다.
- 불변식: 메타 모델을 켠 DB 에 임의의 검수(메타 필드 포함)를 저장한 직후와, 같은 검수 파일로 새로 돌린 DB 가 같다. 기계 열은 검수 전후가 같다.
- 크롭 단위 평가의 답 = 파이프라인의 기계 값 (같은 쪽, 0003 과 같은 확인).
- 메타 모델이 없는 설정에서는 모든 결과가 전과 같다. `null` 의 회귀 수치가 그대로다.

### 단계 6 — ✓ 판정의 정답

할 일
- 대기열 `checks [--n 300] [--seed S]`: 점검표의 행(장비)을 날짜별로 고르게 뽑는다. 항목 = 행 하나. 유·무 두 칸이 같이 보이는 띠를 보여 준다.
  기계의 판정은 보여 주지 않는다. 판정 불가인 행, 점검을 하지 않은 날(`column_unused`)의 행도 모집단에 넣는다 — 표시가 없다는 것도 정답이다.
- 화면: `1` 유, `2` 무, 빈 채로 Enter = 표시 없음, `?` = 모름. 저장은 4.9. 다시 열면 전에 고른 답이 보인다.
- `eval --checks [--split …]`: 기계의 답(유 / 무 / 표시 없음 / 판정 불가) 대 정답의 표, 기계가 판정한 행 중 맞은 비율(구간),
  판정 불가의 비율, 판정 불가였던 행의 정답 분포. 날짜 단위로 `column_unused` 가 맞았는지.
- `review stats` 에 ✓ 검수 수.

수용 기준 (합성 데이터)
- 합성 점검표에서 전 행을 정답대로 검수하면 `eval --checks` 의 표가 손으로 센 것과 같다.
- 한 행의 저장이 두 칸의 검수 두 건으로 남고, `insp_daily` 가 바로 갱신되며, 불변식이 성립한다.
- 기계가 틀리게 판정한 행을 고쳐 검수하면 `insp_daily.abnormal` 은 검수값이고 필드의 기계 값(`has_value_raw`, `status_raw`)은 그대로다.
- `checks` 대기열에 기계의 판정이 응답 어디에도 없다.

여기까지 끝나면 PR 을 연다.

## 6. 시험

- 전부 합성 데이터. 실제 문서의 이미지·이름·차량번호를 테스트에 넣지 않는다.

- 0001 의 불변식 시험에 `doc_page_meta` 와 메타 모델을 더한다.
- 마지막에 깨끗한 환경에서 한 번: `pip install .`(torch 없음) → `pytest`, 그리고 합성 묶음으로 2절의 명령을 처음부터 끝까지.

- 판정 규칙의 임계값을 건드리지 않는다.

## 8. 사람이 할 일 (실데이터가 있는 컴퓨터에서)

PR 이 합쳐진 뒤, 순서대로.

1. `minedocscan run DB_scans --fresh` (스키마 5). `regress` — `null` 기준은 그대로여야 한다.
2. `review serve --queue page-fields` 로 **날짜순 20일치쯤**(약 200쪽)의 차량번호·작성자를 입력한다. 이것이 학습 데이터이자 정답이다.
   그중 `test` 날짜의 쪽은 평가에만 쓰인다 (`review stats` 로 분할별 쪽 수를 본다).
3. `review export-crops ~/meta --meta --split train` → `recognizer train --meta-key vehicle_no --name veh-v1 --cv 5`,
   `recognizer train --meta-key operator --name op-v1 --cv 5` → `recognizer eval … --errors` 로 틀린 것을 본다.
4. 설정에 `[recognize.meta]` 를 넣고 `run DB_scans --fresh` → `report` (자리가 정해진 쪽이 얼마나 늘었나) → `eval --meta --split test`.
5. `review serve --queue page-fields --audit 100` — 자동 적재된 쪽을 포함한 표본을 기계 값 없이 다시 본다. 그 뒤 `eval --meta`.
6. `review serve --queue meta-check` — 기계 값과 라벨·검수가 다른 쪽을 본다. 라벨이 틀렸으면 고친다.
7. (선택) 사이트 팩의 템플릿 세 종에 월·일 필드를 넣고(`docs/SITE_PACK.md` 의 조각) 월·일 모델을 학습한다 — 정답은 파일명 날짜라 입력할 것이 없다.
   `pages --meta-mismatch --meta-key date.day` 로 날짜가 다른 쪽을 본다.
8. `review serve --queue checks --n 300` → `eval --checks`.

**돌려줄 수치** (이름·차량번호 없이 수치만): 입력한 쪽 수와 날짜 수, 종류의 수(차량·작성자)와 종류당 예의 최소·중앙,
키마다 정확도·자동 적재율·자동 적재 오류율(분자·분모)·기준과 상한, 배차가 바뀐 쪽의 수와 그 정확도, 목록에 없는 값의 수,
일보 중 자리가 기계만으로 정해진 비율, 교차검증이 계산된 날짜 수의 변화, 대조가 어긋난 쪽의 수와 그 원인(라벨 오류 / 섞인 쪽 / 기계 오류),
✓ 판정의 표와 정확도, 한 시간에 입력한 쪽·행 수.

## 9. 열린 질문과 기본값

| 질문 | 기본값 |
|---|---|
| 메타 필드의 자동 적재 오류율 목표 | 2 %. 과제 책임자가 정한다 |
| 기준을 정하는 데 필요한 최소 검증 칸 | 100 (0003 과 같다). `--cv 5` 면 약 100–150쪽의 정답부터 기준이 나온다 |
| 분류기의 종류가 되려면 필요한 예의 수 | 3 |
| 메타 필드 크롭의 여유 | 8 px (고정) |
| 작성자와 차량의 짝을 판단에 쓸지 (평소와 다른 짝이면 검수로) | 쓰지 않는다. `eval --meta` 의 "배차가 바뀐 쪽" 수치를 본 뒤 정한다 |
| 차량번호 숫자 모델에 운반 횟수 칸의 실제 숫자를 같이 넣어 학습할지 | 넣지 않는다 (규격이 다르다). 성적이 모자라면 그때 비교한다 |
| ✓ 정답의 표본 수 | 300행. 판정 불가였던 행은 따로 전부 볼지 사람이 정한다 |
| 날짜(월·일) 대조를 기본으로 켤지 | 템플릿에 필드를 넣고 모델을 지정한 경우에만 |

## 11. 끝나고 보고할 것

- 단계별로 무엇을 만들었고 무엇을 만들지 않았는지. 수용 기준 중 충족하지 못한 것이 있으면 그것부터.
- 테스트 수와 시간(기본 / `train` / 하한 판). 기존 테스트와 `null` 백엔드의 리포트가 그대로인지.
- 두 모델의 구조와 크기, 합성 데이터에서의 학습 시간. (정확도는 "합성에서 문턱 통과"로만.)
- "글씨체가 아니라 숫자를 읽는다"는 수용 기준을 어떻게 시험했는지.
- 4절에서 벗어난 것이 있으면 무엇을 왜.
- 브라우저에서 직접 확인한 것(`checks` 의 키, `meta-check` 화면, `--audit`)과 확인하지 못한 것.
