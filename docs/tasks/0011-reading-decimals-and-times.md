## 1. 왜 하는가

**(가) 가동 일보의 값은 지금 전부 사람이 넣는다.** 형식이 있는 칸(`decimal`·`time`·`time_range`·`reading`)은 인식기에 보내지 않는다
(`handlers/base.readable`) — 잉크가 있으면 검수 대기, 없으면 빈 칸. 실제 가동 일보 40쪽(3일치)에서:

| | 계기 칸 (`reading`) | 근무 시각 칸 (`time_range`) |
|---|---|---|
| 템플릿의 칸 (네 양식) | 12 | 3 |
| 사람이 넣은 값 | 34 — 계기 값 28 (네 자리 10, 다섯 자리 18, 모두 소수 한 자리), 시각 6 | 9 (모두 `HH:MM~HH:MM`) |
| 사람이 넣은 빈 칸 | 44 (그중 잉크 판정이 있던 칸 3) | 9 (0) |
| 잉크 판정 | 값이 있던 34칸 모두 "있음" | 값이 있던 9칸 모두 "있음" |

하루 약 14칸, 40쪽 중 26쪽이 `readings` 대기열에 오른다. 0006 은 "하루 10칸 안팎이고 1분이 안 걸린다"며 미뤘다. 그래도 지금 하는 까닭:
- 가동 기록(`eq_usage_daily`)은 기계가 값을 하나도 정하지 못하는 유일한 업무 표다 — 가동 시간은 사람이 넣기 전까지 NULL (원칙 5).
- 자동 적재는 실데이터의 검증으로만 켜진다 (ADR 0012). 그 길(정답 → 학습 → 보정 → 감사)을 지금 만들어 두면 정답이 쌓이는 대로 명령 몇 개로
  켠다. 기준이 나오기 전에도 기계 값이 검수 화면에 미리 채워진다.
- 계기 표에는 쪽 안의 검산(총 = 종료 − 시작, 하루 24시간)과 날짜 사이의 검산(어제 종료 = 오늘 시작)이 있다 — 운반 숫자보다 자동 적재를 지키기 쉽다.

**이 단계로 현장의 자동 적재가 켜지지는 않는다.** 합성 데이터로 길·규칙·모델을 만들고, 기준은 실데이터의 정답으로만 정한다 (8절).

**(나) 실제 칸의 모양.** 값이 있던 칸의 정합 그림(200 dpi)에서 잰 것:

| | 계기 칸 (34) | 근무 시각 칸 (9) |
|---|---|---|
| 칸 크기 (템플릿 px) | 폭 112–297, 높이 45–62 — 값이 있던 칸은 모두 높이 51 | 308 × 62, 99, 100 |
| 글씨 높이 | 중앙 35 px (19–51) | 중앙 18 px (10–28) — "1" 을 사선 하나로 길게 쓴다 |
| 글씨 폭 / 칸 폭 | 중앙 0.93, 최대 1.01 | 중앙 0.94 |
| 위 / 아래 괘선을 넘은 칸 | 10 / 16 | 5 / 8 |
| 점(소수점·콜론)의 덩어리 | 4–7 px | 4–9 px |

- **키 큰 근무 시각 칸(99·100 px)은 글씨가 칸의 5분의 1 이고**, 숫자 모델의 크롭 규격(여유 = 행 높이의 절반)으로 뜨면 윗줄(오전 칸)의 글씨가
  같이 들어온다. 크롭 전체를 높이 48 로 줄이면 글씨가 계기 칸 17 px, 근무 시각 7 px, 키 큰 칸 4 px 이다. 칸 안에 무게 중심이 있는 잉크 덩어리를
  줄로 묶어 가장 잉크가 많은 줄로 자르면(4.3 의 글씨 띠) 같은 입력에서 계기 칸 21–36 px(중앙 31), 근무 시각 10–18 px(중앙 12)이고 윗줄의 글씨가
  빠진다. 덩어리를 줄로 묶지 않고 모두 합치면 키 큰 칸의 띠가 132 px 까지 커져 6 px 로 줄었다.
- 분의 "00" 을 흘려 쓴다(고리 둘). 근무 시각 칸에도 점으로 쓴 시각이 있다 (9칸 중 1칸). 계기 칸에 덧쓴 숫자, 아랫줄에서 넘어온 글씨가 있다.
- 숫자 모델의 입력(32 × 96)에 넣으면 근무 시각 11글자(`08:00~17:00`)가 96 px 폭에 들어가 점이 1–2 px 가 된다.

**(다) 사람이 넣은 값과 종이의 글자가 다르다.** 검수는 정규화한 값만 남긴다 (`review/store._save` 의 `normalized_value`): 점으로 쓴 시각은
콜론으로(사람이 시각이라고 정했으면), `8-17` 은 `08:00~17:00`. 이 값을 그대로 CTC 의 목표로 쓰면 종이에 없는 `:00` 을 읽으라는 것이 된다 → 4.4.

**(라) 점으로 쓴 시각(08.00)과 계기 값은 모양으로 갈리지 않는다** (ADR 0015). 기계도 가르지 않는다 — 사람이 정한다.

## 2. 끝났을 때 되는 일

```toml
[recognize.by_format]          # 형식마다 백엔드 — 적힌 형식만 읽는다
reading = "readings"
time_range = "readings"

[recognize.readings]
model = "readings-v1"          # <site>/models/readings-v1/
```

```bash
minedocscan review export-crops ~/crops --split train --include-illegible …   # 숫자 칸과 같은 폴더·같은 규격 (형식 칸은 종류를 묻지 않는다)
minedocscan recognizer train --readings --crops ~/crops --name readings-v1 --cv 5    # → <site>/models/readings-v1/
minedocscan recognizer eval  --crops ~/crops --model readings-v1 --split val --errors
minedocscan info                                                                     # 형식마다 백엔드·모델·기준
```

- 설정한 형식의 칸이 인식기로 간다. 기계는 **적힌 대로** 읽고(`1234.5`, `08.00`, `8-12`) 정규화한 값으로 적재한다.
- 자동 적재 = 칸의 기준(검증 날짜에서 고른 것) **그리고** 쪽 안의 검산. 점으로 쓴 시각은 늘 사람이 정한다.
- 검수 대기 칸에는 기계가 읽은 글자가 미리 채워진다 (`pending`). `readings` 대기열에는 기계가 사람에게 보낸 칸이 있는 쪽만 오른다.
- 학습은 사람이 넣은 정규화한 값으로 한다 — 종이에 쓸 수 있는 표기 모두를 정답으로 (4.4).
- 설정하지 않은 현장, 숫자 모델, 메타 모델은 그대로. 판 1.1.0.

## 3. 범위

하는 것
- 형식 칸을 인식기로 보내는 길(4.1), 칸의 규칙과 쪽 안 검산(4.2), 소수·시각 모델 `readings`(4.3), 쓸 수 있는 표기(4.4), 합성 칸(4.5),
  학습·평가 명령과 `inked`(4.6), 대기열·리포트(4.7). 판 1.1.0, `sig_probe` 의 작은 것(4.8).

하지 않는 것
- **계기의 연속성(어제 종료)을 읽기의 후보·제약으로 쓰는 것.** 쪽의 결과가 다른 쪽에 기대면 처리 순서에 따라 DB 가 달라진다 (불변식 — 0007).
  그리고 연속성의 어긋남은 보여 주는 것이다 (ADR 0006). 자동 적재된 값이 어긋나면 지금처럼 `xcheck_usage` → `usage-check`.
- 시작·종료·총의 후보를 같이 골라 검산을 맞추는 것 — 총은 거의 비어 있다. 검산은 자동 적재를 막기만 한다.
- 점으로 쓴 시각을 기계가 시각이나 계기 값으로 정하는 것.
- 형식이 없는 글자 칸의 인식, 교정, 운반·점검표 양식의 인쇄 층 (M3·M4·M1 의 다른 줄). 표 밖 필드(`fields`)의 형식 칸 (4.1).
- 합성 가동 일보(`synth --usage-logs`)의 모양을 바꾸는 것 — 학습용 합성 칸은 새 생성기로 (4.5).
- 자가 시험(`selftest`)의 검사 — 기본 설정이라 바뀌지 않는다.
- 합성 수치로 인식률을 말하는 것.

## 4. 설계

### 4.1 형식 칸을 인식기로 보내는 길

- 설정 `[recognize.by_format]`: 형식(`decimal`·`time`·`time_range`·`reading`) → 백엔드 이름. `integer` 는 받지 않는다 (정수 칸은 `by_kind`).
  우선순위: `by_format` > `by_kind` > `[recognize] backend`. `config.py` 는 `by_format` 을 `recognizer_options` 에서 뺀다 (`by_kind` 처럼).
- **형식 칸을 읽게 하는 것은 이 설정 하나다.** `build_recognizer` 는 `by_format` 이 비어 있지 않으면 늘 나눠 주는 인식기(`ByKindRecognizer` — 형식의
  표를 더 가진다)로 감싼다. 형식 칸이 인식기로 가는지는 함수 하나(`handlers/base.reads_format(recognizer, fmt)`)가 정한다: 그 인식기가 가진 형식의 표에
  `fmt` 가 있으면 참, 그 밖의 인식기(감싸지 않은 `null`·`oracle`·`digits`)는 늘 거짓. 적히지 않은 형식의 칸은 지금처럼 인식기에 가지 않고 잉크가 있으면
  검수 대기(`unread_row`) — 감싸지 않은 `oracle` 을 넘기는 `run --answers`(`cli.py` 의 `cmd_run`)와 자가 시험(`selftest.py` — 형식 칸은 "잉크 있음 +
  검수 대기"를 기대한다)이 그대로인 까닭이다.
- 백엔드는 읽는 형식을 선언한다 (`formats`). 선언하지 않은 형식에 꽂으면 인식기를 만들 때 멈춘다 ("digits 는 소수·시각을 읽지 않습니다"). `null` 은
  선언하지 않는다, `oracle` 은 넷 다. 선언은 검사에만 쓴다 — 읽게 하는 것은 위의 설정이다.
- `run --answers`: `[recognize.by_format]` 이 있으면 정답 oracle 을 그 형식들의 표로 감싼다 (`{형식: oracle}` — 적힌 백엔드 이름과 상관없이, 종류를 지금
  그렇게 하듯이). 없으면 지금과 같다. 그래서 oracle 로 형식 칸의 CER 0 을 확인할 수 있다 (`CLAUDE.md` 작업 규칙 3).
- `CellContext` 에 `fmt`(칸의 형식)와 `bbox`(템플릿 좌표) — 끝에, 기본값 `None`. 나눠 주는 인식기가 (형식, 종류)로 나누고, 크롭 규격도 그 칸을 읽을
  백엔드의 것이다 (`spec_for(recognizer, kind, fmt=None)` — 형식을 모르는 백엔드는 지금처럼 종류로). `backend_for(kind)` 의 한 인자 호출(`cli.py` 의 `info`)은
  그대로 돈다.
- 범위: **표의 칸**(region ≠ `fields`)만. generic·inspection(`FormHandler.load_handwritten` 을 물려받는다)과 usage(`UsageHandler.load`)가 `reads_format` 을
  같이 쓴다. 운반(`haul`)은 숫자 칸 밖의 손글씨를 인식기에 보내지 않는다 — 그대로. 표 밖 필드(`fields`)의 형식 칸은 지금처럼 읽지 않는다 (메타 필드의 길이
  따로 있고, 학습 데이터 `read_crops` 도 필드 줄을 뺀다). 칸 종류는 묻지 않는다 — 형식이 있는 `handwritten_text` 칸도 읽는다.
- `readable(cell)`(정수 경로 — 형식이 없거나 `integer`)은 그대로 두고 자가 시험도 그대로 쓴다.
- 값 유무 판정은 그대로 — usage 의 `presence`(덩어리 배정 또는 잉크 비율, 인쇄 층), generic 의 잉크 비율. 잉크가 없는 칸은 인식기에 가지 않는다.
- `info`: 형식마다 백엔드·모델·기준·상한 (지금의 종류마다 줄과 같은 꼴).

### 4.2 칸의 규칙과 쪽 안 검산

**칸** (`handlers/base.format_row` — `number_row` 와 같은 자리, generic·usage 가 같이 쓴다). 답의 종류를 말하는 백엔드(`readings`), 기준 t:

| 답 | 조건 | `has_value_raw` | 상태 | `value_final` |
|---|---|---|---|---|
| 빈 칸 | 신뢰도 ≥ t | 0 | auto | 그 핸들러가 지금 빈 칸에 쓰는 것 (generic `""`, usage NULL) |
| 빈 칸 | 그 밖 | 1 | pending | NULL |
| 거절 | | 1 | pending | NULL |
| 값 — `reading` 칸이고 점으로 쓴 시각(`formats.dotted_clock`) | | 1 | pending | NULL |
| 값 | 신뢰도 ≥ t | 1 | auto | `normalize(fmt, 적힌 글자)` |
| 값 | 그 밖 | 1 | pending | NULL |

- `value_raw` = 적힌 대로 읽은 글자(`08.00`, `8-12`), `candidates` = 상위 5개(적힌 글자), `confidence`, `backend` — 지금의 열 그대로.
- 점으로 쓴 시각의 줄은 `reading` 칸 모두에 (계기 표의 총 칸도 — 총은 거의 비어 있고, 두 자리 소수의 총은 드물다). `dotted_clock` 은 소수 두 자리만
  본다 — 한 자리로 잘못 읽은 시각(`8.0`)은 쪽 안 검산의 ⑤가 막는다.
- **검수 대기인 형식 칸의 `value_final` 은 NULL 이다.** 정수 칸(검수 대기여도 기계 값을 `value_final` 에 둔다)과 다르다: 가동 시간과 계기의 검산이
  기계의 추측으로 계산되지 않게 (ADR 0016 "추정하지 않는다"). 기계 값은 `value_raw`·후보와 검수 화면의 미리 채우기로만 쓰인다.
- **그리고 `handlers/usage._state` 는 검수 대기인 형식 칸을 값이 있어도 모르는 칸(UNKNOWN)으로 본다.** 지금은 "검수 대기 + 값 없음"만 UNKNOWN 이다
  (`_state`). 자동 적재한 칸에 사람이 `illegible` 을 넣으면 `apply_verdict` 는 값을 그대로 두고(`review/store.py`) `_save` 는 그 전에 `machine_final` 로
  기계 값을 되살리므로, 고치지 않으면 사람이 "읽을 수 없다"고 한 칸으로 가동 시간·연속성을 계산한다. 설정하지 않은 상태에서는 검수 대기인 형식 칸의
  `value_final` 이 늘 NULL 이라 결과가 같다.
- 답의 종류를 말하지 않는 백엔드(`oracle`): 글자가 형식에 맞고(`formats.is_valid`) 신뢰도 ≥ t 면 auto(정규화한 값), 아니면 pending(NULL).
- `machine_final` — load 가 만든 것과 같아야 한다 (`review/store._save` 가 검수를 다시 덮기 전에 쓴다). 형식 칸은 **형식을 먼저** 본다
  (`UsageHandler.machine_final` 은 지금 `fields` 칸이면 형식을 보기 전에 `value_raw` 를 돌려준다): `status_raw` pending → NULL, auto 이고 `has_value_raw` 1 →
  `normalize(fmt, value_raw)`, auto 이고 `has_value_raw` 0 → 그 핸들러의 빈 칸 (generic 은 지금처럼 `value_raw` 의 `""`, usage NULL). 설정하지 않은 상태의
  행(읽지 않은 칸 — `value_raw` NULL, 잉크 없는 칸)에서 지금과 같은 값이 나와야 한다 (시험 — generic 의 값 → `illegible` 검수 순서도).

**쪽 안 검산** (`UsageHandler.load`, 칸의 규칙 뒤·`apply_reviews` 앞 — **기계 값만으로**, 쪽 하나 안에서만). 통과하지 못하면 그 표의 auto 인
값 칸을 전부 pending 으로 내린다(`review_status`·`status_raw` 모두, `value_final` NULL). 빈 칸으로 자동 적재한 칸은 그대로.
- 계기 표(`role: meter`): ① 표의 형식 칸 중 하나라도 pending 이면 내린다 (읽지 않는 형식이라 pending 인 칸도). ② 값 칸이 없으면(모두 빈 칸) 그대로.
  ③ 시작·종료가 둘 다 값이고 같은 종류(계기 값끼리, 시각끼리 — `_meter_value`)여야 한다 (총만, 시작만, 섞임 → 내린다). ④ 계기 값: 0 ≤ 종료 − 시작 ≤ 24,
  총이 있으면 총 = 종료 − 시작 (쪽 안 검산 `validate/usage.page_checks` 와 **같은 함수**로 — 반올림 `round(·, 4)`, 허용 오차 `TOLERANCE` 0.05). 시각: 총이
  있으면 수이고 |총 − 길이(시간)| ≤ 0.05. ⑤ 계기 값인데 시작·종료가 둘 다 24 이하면 내린다 — 점으로 쓴 시각을 소수 한 자리로 읽었을 수 있다
  (`report.dotted_suspect` 와 같은 조건, 같은 상수에서).
- 근무 시각 표(`role: shifts` 의 `time_range` 칸 — `is_shift_cell`): 하나라도 pending 이면 내린다. 범위의 합이 24시간을 넘으면 내린다.
- 표마다 따로 한다 (계기 표가 내려가도 근무 시각 표는 auto 일 수 있다).
- 24시간은 하루의 상한이다 — 현장에 따라 다르지 않으므로 `site.toml` 이 아니라 상수, 근거를 주석에 (하루 두 장이면 장마다).
- 결과: 자동 적재된 쪽의 쪽 안 검산(`xcheck_usage` 의 `total`)은 mismatch 일 수 없다. 연속성은 다르다 — 잘못 쓴 시작을 바르게 읽으면 auto 이고
  연속성에서 overlap 으로 보인다 (ADR 0006).
- 내린 칸의 수를 이유별로 load 의 요약에 — 실행기가 더하는 정수 키 하나씩(`pipeline/runner.py` 는 int·float 만 더한다), 형식 칸을 읽었을 때만 (설정하지
  않은 `run --json` 은 그대로). DB 에는 남기지 않는다.

generic·inspection 핸들러의 형식 칸(V2 의 유류일지 같은)은 칸의 규칙만 — 쪽 안 검산은 가동 일보의 역할이 있는 표에서만.

### 4.3 소수·시각 모델 `readings`

- **숫자 모델과 따로 둔다** — 같은 망(합성곱·배치 정규화·ReLU·최대 풀링, CTC)과 같은 학습 코드, 다른 글자·입력·답. 숫자 모델의 코드는 지금 모듈
  상수에 묶여 있다 (`recognize/digits/model.py` 의 `CHARS`·`N_CLASSES`·`INPUT_W/H`·위치 격자 `_YS`·`_XS`, `beam_search`·`OnnxNet.logits`·`load_card`,
  `train.py` 의 `build_net`·`_targets`·`_greedy`·`fit`, `calib.py` 의 `encode`·`ctc_nll`). 같이 쓰려면 글자·입력을 담은 것 하나를 인자로 받게 고치고
  숫자 모델의 값을 기본값으로 둔다. **숫자 모델은 바이트까지 그대로다**: 카드의 키, 입력, `digits-fixture`·`meta-digits` 의 출력 (시험).
- 모델 폴더를 읽는 곳(`recognizer list`, `[recognize.digits]`·`[recognize.readings]`·`[recognize.meta]` 의 백엔드)은 카드의 `reader` 를 **먼저** 보고 갈래를
  고른다 — 지금은 소수·시각 카드를 숫자 모델로 읽어 "문자가 다릅니다 — 다시 학습하세요"(`load_card`)라는 엉뚱한 말로 멈춘다.
- 글자: blank + `0123456789.:~-?`. 답: 적힌 글자 · 빈 칸 `""` · 거절 `"?"` (ADR 0012 의 셋).
- **크롭 규격**은 숫자 모델의 기본과 같다 (원본, 1.5배, 여유 = 행 높이의 절반) — `review export-crops` 한 번으로 두 모델의 크롭이 나온다
  (`read_crops` 가 형식으로 가른다 — 지금도 숫자 모델은 형식 칸 줄을 뺀다).
- **글씨 띠** (입력을 만드는 함수 하나 — 학습·추론·평가·틀린 칸 모아 보기가 같이 쓴다):
  1. 크롭 안의 칸 자리를 규격으로 계산한다 (`CellContext.bbox` + 카드의 규격, 내보낸 줄은 `bbox`·`pad`·`out_scale`, 합성 칸은 생성기가 안다).
  2. 이진화(`grid.binarize`)·괘선 지우기(`cells.remove_rules`) — 숫자 칸과 같은 구현.
  3. 무게 중심이 칸 안(가로·세로)에 있는 잉크 덩어리(면적 4 px 이상, 템플릿 px — 배율로 환산)를 고른다 — 괘선을 넘은 글씨는 들어오고, 윗줄·아랫줄과
     옆 칸(같은 줄의 시작·종료·총)에서 넘어온 글씨는 빠진다.
  4. 덩어리를 줄로 묶는다 (세로 구간이 짧은 쪽 높이의 30 % 넘게 겹치면 한 줄, 면적이 큰 것부터) → 잉크가 가장 많은 줄의 세로 범위 ± 그 높이의
     15 %(최소 3 px). 덩어리가 없으면 칸의 세로 범위.
  5. 가로는 칸 ± 칸 높이의 1/4(최소 4 px, 템플릿 px) — 크롭의 옆 여유(행 높이의 절반)에는 옆 칸의 값이 들어온다. 값의 폭은 칸 폭의 0.93–1.01 이다 (1절 나).
  6. 높이를 48 로 비율을 지켜 줄이고 왼쪽에 붙여 폭 320 까지 종이색(그 그림의 중앙값)으로 채운다 — 넓으면 폭을 320 으로 줄인다.
  7. 잉크·세로 위치·가로 위치 채널 (숫자 모델의 `normalize` 의 잉크). 위치 채널은 칸에 맞춘다 — 세로는 띠의 위·아래가 −1·+1, **가로는 칸의 왼쪽·오른쪽이
     −1·+1**(그 밖은 그대로 이어서, 채운 곳도). 칸 크기마다 가로 배율이 달라도 "칸 안의 어디"가 같은 값이다. 가로 80칸의 CTC — 근무 시각 11글자에 넉넉하다.
  띠는 자리만 정한다 — 모델이 보는 것은 회색 그림 그대로다 (괘선 지우기는 세로획 하나의 "1" 을 지운다 — `CLAUDE.md`). 위 수(면적, 30 %, 15 %, 1/4,
  48 × 320)는 기본값이고 근거(1절 나)를 주석에. 카드에 `input`(폭·높이·띠의 기본값)을 적고, 카드와 코드가 다르면 읽지 않는다.
- **해독 — 고르기만 한다** (원칙 4): CTC 빔(숫자 모델의 `beam_search`, 글자만 다르다)의 후보 중 그 칸의 형식에 맞는 글자(`formats.is_valid`)와 빈 칸·거절만
  남긴다. 같은 값으로 정규화되는 글자(`08:00`·`8:00`)의 확률은 더한다 (숫자 모델의 `07`·`7` 처럼). 답 = 확률이 가장 큰 값, `value_raw` = 그 값의
  가장 큰 글자, 신뢰도 = 그 값의 확률 — 형식에 맞지 않는 글자의 몫은 다시 나누지 않는다 (신뢰도를 깎는다). 형식에 맞는 답이 빔에 없으면 거절
  (신뢰도 0). 빔은 숫자 모델(12)보다 넓게 — 형식으로 거르고도 후보가 남게 (폭은 보고).
- **온도·기준**은 숫자 모델의 규칙 그대로 (ADR 0012): 검증 날짜(소금값 + `":val"`) 또는 `--cv K`(메타 모델과 같은 방식 — 날짜 묶음마다 나머지로 학습해
  그 묶음을 읽는다, `cv-reads.jsonl`, ADR 0014). 자동 적재된 검증 칸이 100 미만이면 기준 없음(자동 적재 없음), 고른 기준에는 윌슨 95 % 상한.
  자동 적재 대상 = 값(점으로 쓴 시각이 아닌 것)과 빈 칸. 기준은 하나 — 형식마다 두지 않는다(칸이 적다). 카드에 형식마다 성적.
  현장 셀로 학습했는데 검증할 현장 셀이 없으면 기준을 정하지 않는다 (숫자 모델과 같다). 합성만으로 학습하면 합성 검증 칸으로 정한다 (시험용 모델).
- **카드**: 숫자 모델의 키 + `reader: "readings"`, `formats`(넷), `input`. 값의 분포 대신 **모양의 분포**(숫자를 `d` 로 — `dddd.d: 18`) — 카드에 값을
  적지 않는다. `[recognize.digits]` 에 이 모델을, `[recognize.readings]` 에 숫자·메타 모델을 꽂으면 멈춘다 (지금 메타 모델을 그렇게 거절하듯이).
- **백엔드 `readings`** (`recognize/readings/`): `[recognize.readings] model`(설정 > `site.toml`), `auto_accept_conf`(설정 > 카드 >
  `[pipeline] auto_accept_conf` — 0003 과 같다). 선언하는 형식 = 카드의 `formats`. 형식이 없거나 선언하지 않은 형식의 칸이 오면 읽지 않고 신뢰도 0 의
  빈 답 (숫자 모델이 모르는 종류에 하는 것처럼).

### 4.4 정답: 쓸 수 있는 표기

- `formats.spellings(fmt, value) -> list[str]`: 그 정규화한 값이 될 수 있는, 사람이 종이에 쓰는 글자들. 첫째가 정규형, 순서는 정해져 있다.
  - `decimal`, `reading` 의 계기 값: 그 값 하나.
  - `time`: 시 `08`·`8` × (`:mm`, `.mm`, `mm` — `0800`·`800`), 분이 `00` 이면 시만(`8`·`08`)도.
  - `reading` 의 시각: `08:00`·`8:00`·`08.00`·`8.00` — 점은 사람이 시각으로 정한 것이다 (1절 라).
  - `time_range`: 양쪽의 `time` 표기 × `~`·`-` (많아야 128).
- `formats.same_value(fmt, written, value)`: `normalize(fmt, written) == value`, 또는 `reading` 이고 `dotted_clock(written) == value`.
  `spellings` 의 모든 글자에서 참이다 (시험).
- **학습**: 실제 셀의 정답은 정규형이므로 목표가 여럿이다 — 손실 = −log Σ P(표기) (표기마다 CTC 를 계산해 log-sum-exp). 빈 칸 `[""]`,
  `illegible` → `["?"]`. 합성 셀은 적힌 글자 하나.
- 표기는 같은 글자를 한 번만, 정규형부터, 많아야 128. 학습은 (칸, 표기) 쌍을 펼쳐 CTC 를 `reduction='none'` 으로 한 번에 계산하고 칸마다 log-sum-exp —
  지금의 `fit` 은 칸마다 목표 하나다.
- 보정(온도)의 음의 로그우도도 같은 식이다. 지금의 `calib.ctc_nll` 은 파이썬 반복이라 표기 128개 × 온도 격자 약 24개면 검증 칸 몇백 개에도 오래 걸린다 —
  표기를 한 번에(벡터로) 계산한다. 검증 칸 1,000개의 보정 시간을 보고한다.
- 평가는 `same_value` 로 견준다: 크롭 단위(`recognizer eval`·카드의 성적), 그리고 `evaluate/fields.py` 의 **기계 값**(`--target raw`) 비교. 점으로 쓴 시각을
  봐주는 것은 기계가 읽은 글자에만이다 — 사람이 넣은 최종 값(`--target final`)의 계기 값 `8.00` 을 시각 정답 `08:00` 과 같다고 하지 않는다.
  `null`·`oracle` 의 기계 값에는 차이가 없다.

### 4.5 합성 칸 (`tools/synth_readings.py`)

- 학습 명령이 쓰는 생성기 — `tools/synth_cells.py` 와 같은 자리, 같은 획(`tools/handfont.py`)과 같은 스캔 효과. 같은 씨앗이면 화소까지 같고,
  난수는 따로 쓴다. **기존 합성(`synth` 의 모든 선택, `synth_cells`)의 바이트는 그대로** — `handfont` 에 꼴을 더하면 새 생성기만 쓴다.
- 칸 크기는 실제 크롭에서 형식마다 (숫자 모델의 `_geometry_of` 처럼), 실제 크롭이 없으면 `--synthetic-geometry`(`형식=WxH`, 형식 없이 쓰면 모든 형식).
- 넣는 것 (1절 나에서 본 것):
  - 값: 계기 값(세–다섯 자리 + 소수 한 자리, 가끔 소수 없이), 시각(콜론, 점, 붙여 쓴 `0800` — 붙여 쓴 것은 `time`·`time_range` 칸에서만: `reading` 칸의
    `0800` 은 계기 값 800 이다), 시각 범위(정규형, `8-12`, 인쇄된 `~` 양옆에 쓴 `8`·`12`, 섞인 것). 기본 비율: `reading` 0.5 (계기 값 0.75, 콜론 시각 0.15, 점 시각 0.10), `time_range` 0.3, `decimal` 0.1, `time` 0.1.
  - 꼴: 흘려 쓴 `00`, 사선 하나의 `1`, 칸보다 큰 글씨(괘선 사이 높이의 0.6–1.2), 칸 폭을 거의 다 쓰는 값, 덧쓴 숫자, 윗줄·아랫줄과 옆 칸(같은 줄의 다른 값)에서
    넘어온 글씨, 키 큰 칸(근무 시각 99 px 같은)의 작은 글씨(칸 높이의 0.2–0.3).
  - 인쇄: 계기 칸 왼쪽의 인쇄된 이름표(합성 글자 몇 개와 `:`), 근무 시각 칸 가운데의 인쇄된 `~` (`synth_usage._tilde` 와 같은 선). 인쇄만 있는 칸의
    정답은 빈 칸이다.
  - 빈 칸의 갈래: X 표, 덧칠, 칸 위에 걸친 메모, 이웃 글씨만, 아무것도 없음 (`synth_cells.KINDS` 와 같은 뜻).
- 한글 인쇄 글자(실제 계기 칸의 "시작:" 같은)는 그리지 않는다 (글꼴이 없다) — 실제 크롭으로 학습할 때 들어온다.

### 4.6 학습·평가 명령

- `recognizer train --readings [--crops DIR] --name N [--cv K] [--synthetic N] [--synthetic-geometry …] [--target-auto-error] [--min-val-auto]`:
  크롭 폴더에서 형식이 넷 중 하나인 **표의 칸** 줄만 (칸 종류는 묻지 않는다 — 4.1 의 범위와 같게). test 줄 거절, 규격 하나, 저장소 안 거절
  (`--allow-in-repo` 는 합성 시험용 모델만) — 숫자 모델과 같다. 기본값도 숫자 모델과 같다 (`--target-auto-error` 0.01 …). `--cv` 는 지금 `--meta-key`
  없이는 거절된다 — `--readings` 에도 연다. `--synthetic-geometry` 의 항목은 `WxH`(모든 형식) 또는 `형식=WxH` — 지금의 꼴 그대로 읽힌다.
  학습 중의 출력·카드·오류 글에 값을 찍지 않는다 — 수와 모양만.
- `recognizer eval --crops … --model <readings 모델> --split val [--errors]`: 형식마다 값 정확도(`same_value`)·빈 칸·거절, 자동 적재율과 오류(분자·분모·
  윌슨 구간), 점으로 쓴 시각으로 읽은 칸의 수. `--errors` 의 그림에 모델이 본 띠를 같이 (저장소 밖 — 지금과 같다). `--cv` 모델은 `cv-reads.jsonl` 로.
- `recognizer list`: 모델의 종류(숫자·메타·소수·시각)와 형식.
- `review export-crops` 의 `inked`: 형식 칸은 "인식기에 갔다(`backend` ≠ `ink`) **또는** 잉크 판정이 있다". 지금은 `has_value_raw` 만 보아, 기계가 빈
  칸으로 자동 적재한 칸(인식기에 갔다 — `has_value_raw` 0)이 검증에서 빠진다.

### 4.7 대기열·리포트

- `readings`(`--audit` 없이): 쪽의 칸 중 **기계가 사람에게 보낸 칸**(`status_raw` pending)이 있는 쪽. 지금은 잉크 판정이 있는 칸(`has_value_raw`)이 있는
  쪽이다 — 형식 칸을 읽지 않는 동안 둘은 같다 (잉크가 있으면 늘 pending). 항목의 칸, 끝난 쪽의 규칙, 기계 값을 숨기는 것은 그대로.
  (`review/queue._FIELD_SQL` 은 지금 `status_raw` 를 고르지 않는다 — 더한다.)
  `--audit N` 그대로 (기계 값 없이, 기계의 상태와 상관없이 날짜별로 고르게 — 자동 적재된 쪽의 감사가 된다).
- `pending`: 그대로 — 기계 값이 미리 채워지고, 계기 시작·종료 칸에 점으로 쓴 시각이면 지금의 물음(`ask_dotted`).
- `usage-check`: 그대로 — 칸에 지금의 최종 값을 싣는다. 자동 적재된 칸이면 기계가 읽은 값이다 (지금의 설명 "계기 칸은 기계가 읽지 않는다"를 고친다).
  연속성이 어긋난 자동 적재 칸은 여기서 사람이 본다.
- `report`: 형식 칸을 읽은 백엔드가 있을 때만(`backend` ≠ `ink` 인 형식 칸이 있을 때) `format_cells` — 형식마다 읽은 칸, 자동 적재(값·빈 칸), 검수 대기,
  점으로 쓴 시각으로 읽은 칸. 그런 칸이 없으면 키가 없다 (`null` 리포트 그대로).

### 단계 1 — 형식 칸의 길과 규칙 (oracle 로)

할 일

수용 기준
- **설정하지 않으면 그대로**: 합성 묶음(기본, `--usage-logs`, `--v2-forms`, `--low-cells`)을 `null` 로, `run --answers`(`by_format` 없이)로,
  `digits-fixture` 로 돌린 작업 DB 의 모든 표의 행과 리포트, `run --json` 의 요약이 main 과 같다 — 같은 환경에서 main 과 이 브랜치로 만든 덤프를 견준다
  (저장소에 지문을 두지 않는다 — 윈도우의 OpenCV 는 다르다). 자가 시험 그대로.
- **oracle 로 형식 칸**: 합성 가동 일보(`--usage-logs --print-layers`, 6일 — 인쇄된 `~` 만 있는 칸이 인식기에 가지 않게. oracle 은 그 칸에 빈 답을
  주고, 답의 종류를 말하지 않는 빈 답은 검수 대기다)를 `run --answers` + `[recognize.by_format]` 넷 → 형식 칸의 기계 값 CER 0 (`same_value`).
  `TRUCK_total_mismatch` 쪽의 계기 칸은 전부 pending(`value_final` NULL), 그 밖의 쪽은 auto 이고 `eq_usage_daily` 의 가동 시간·근거·`reading_kind` 가
  정답(`truth.json`)과 같다. `TRUCK_wrong_start` 는 auto 이고 `xcheck_usage` 의 연속성이 overlap, `usage-check` 에 나온다.
  `decimal`·`time` 칸은 합성 가동 일보에 없다 — `--v2-forms` 의 유류일지·환경일지(generic)를 같은 설정으로: 형식 칸 CER 0, 칸의 규칙만 (쪽 안 검산 없음).
- **칸의 표**(4.2)를 가짜 백엔드(답의 종류·글자·신뢰도를 정해 주는)로 한 줄씩 — generic 과 usage 둘 다. 점으로 쓴 시각 — 가짜 백엔드가 합성 계획의
  종이 글자(`PagePlan.meter` — 같은 씨앗으로 `plan_days` 를 다시 돌려 얻는다, 난수 `[seed, 5005]`. `truth.json` 에 더하면 합성의 바이트가 바뀐다)를
  돌려주면 `PUMP` 쪽의 점 칸은 pending, 그 쪽의 계기 표는 내려간다.
- **`_state`·`machine_final`**: 자동 적재한 계기 칸에 `illegible` 을 넣으면 그 쪽의 가동 시간은 NULL, `reading_kind` 는 pending (4.2). 설정하지 않은 상태의
  generic·usage 형식 칸에서 `machine_final` 이 지금과 같은 값을 낸다 — 값 → `illegible` → 값 순서의 검수를 지금의 코드와 이 브랜치에서 견준다.
- **쪽 안 검산**을 함수 하나로 시험한다 (표): 시작 > 종료, 26시간, 총 어긋남(반올림 경계 — `page_checks` 와 같은 답), 섞임, 시작만, 총만, pending 하나,
  시작·종료가 둘 다 24 이하인 계기 값, 시각 쪽의 총, 근무 시각 합 25시간, 표마다 따로.
- `spellings`·`same_value`: 모든 표기에서 `same_value` 참, 첫째가 정규형, 128개 이하, 합성 가동 일보의 종이 글자가 모두 그 정답의 `spellings` 안에.
- **불변식**: 형식 칸을 읽는 상태에서 계기·근무 시각 칸의 검수(값·빈 칸·`illegible`)와 다시 처리의 순서를 흔들어도 처음부터 만든 DB 와 같다
  (지금의 흔들기 시험에 그 선택을 더한다 — `slow`).
- `readings` 대기열: 형식 칸을 읽지 않을 때 지금과 같은 쪽·같은 수, 읽을 때 자동 적재된 쪽은 오르지 않는다. `--audit` 은 그대로.
- 엑셀: 자동 적재된 계기 값이 가동 기록 시트에 확정 값으로, 검수 대기는 `?` 로 (지금의 규칙 — 내보내기의 코드는 바꾸지 않는다).

할 일

수용 기준 (torch 없이)
- **숫자 모델 그대로**: `digits-fixture`·`meta-digits` 로 합성 셀 수백 개를 읽은 출력(점수의 바이트, 답)이 main 과 같다. 숫자 모델의 카드가 그대로 읽힌다.
- **글씨 띠**: 합성 값 칸의 99 % 이상에서 띠가 그 칸 글씨의 잉크를 95 % 이상 담고, 띠의 높이가 그 글씨의 세로 범위의 1.5배 이하다. 키 큰 칸에서 윗줄
  글씨의 잉크가 띠에 5 % 미만. 입력에서의 글씨 높이를 칸 크기마다 보고한다 (1절 나의 실제 칸 크기로 만든 합성 칸 포함).
- **해독**: 형식에 맞지 않는 글자는 답이 되지 않는다, 같은 값의 글자는 합친다, 형식에 맞는 답이 없으면 거절 — 정해 준 점수로.
- **생성기**: 같은 씨앗이면 바이트까지 같다, 정답(적힌 글자)이 그 칸의 형식에 맞고 정규화한 값의 `spellings` 안에 있다, 비율이 정확하다.
- **시험용 모델**: 따로 뽑은 합성 칸 2,000 에서 형식마다 값 정확도 0.95 이상, 빈 칸(인쇄만 있는 칸 포함) 0.95 이상 — OpenCV 로 읽어서 (`slow` — 빔이
  넓고 가로 80칸이라 오래 걸린다. 기본 시험은 그중 300 으로 0.93 이상). 카드에 값이 없다 (시험: 합성 값 몇 개가 카드의 글에 없다).
- 잘못 꽂은 모델(숫자 ↔ 소수·시각 ↔ 메타)은 멈춘다.

수용 기준 (`pytest -m train`)
- 합성만으로 CPU 에서 학습 — 시간을 보고한다 (4코어에서 15분 안). 위의 시험용 모델의 문턱을 넘는다. torch 와 OpenCV 의 답이 같다.
- 실제를 흉내 낸 크롭 폴더(합성 칸을 `export-crops` 의 꼴로 — 정답은 정규형, `illegible` 포함)로 학습하면 여러 표기의 손실로 돈다. test 줄은 거절,

## 7. 지켜야 할 것

- **기계는 고르고 만들지 않는다** (원칙 4) — 형식에 맞는 후보 중에서만. 종이에 없는 글자를 적재하는 것은 정규화(`formats.normalize`) 한 곳이다.
- **점으로 쓴 시각은 사람이 정한다** (ADR 0015).
- **쪽 하나 안에서만** — 칸의 상태가 다른 쪽(앞날)에 기대지 않는다. 순서에 기대지 않는다.
- 불일치를 맞춰 넣지 않는다 (ADR 0006) — 검산은 자동 적재를 막기만 한다.
- 모델·크롭·카드·틀린 칸 모아 보기는 저장소 밖 — 예외는 합성만으로 만든 시험용 모델(`readings-fixture`).
- 로그·카드·오류 글·보고에 값·이름을 찍지 않는다 — 수와 모양(`dddd.d`)만.
- 추론은 OpenCV(`cv2.dnn`)만, torch 는 학습에서만 import.
- 합성 수치로 인식률을 말하지 않는다.
- `CLAUDE.md` 의 작업 규칙을 따른다.

## 8. 사람이 할 일

PR 이 합쳐진 뒤, 실데이터가 있는 컴퓨터에서. 0006·0005 8절(가동 일보 템플릿·인쇄 층·판 B·대응표)이 먼저다.

1. **정답**: `review serve --queue readings` 로 가동 일보의 날짜를 넓힌다. 기준이 나오려면 자동 적재된 검증 칸이 100 이상이어야 한다 (ADR 0012) — `--cv 5`
   로 하루 약 14칸이면 15–20일치가 어림이다 (자동 적재의 몫에 따라).
2. **학습**: `review export-crops ~/crops --split train --include-illegible` (숫자 칸과 같은 폴더 — `--kind` 없이: 형식이 있는 글자 칸도) →
   `recognizer train --readings --crops ~/crops --name readings-v1 --cv 5` → `recognizer eval … --errors` 로 틀린 칸과 띠를 본다 (저장소 밖).
   근무 시각의 키 큰 칸에서 글씨가 모자라 보이면 입력 높이를 다음 지시서에서 (9절).
3. **켜기**: `[recognize.by_format]`·`[recognize.readings]` → `info`. 기준이 없어도(자동 적재 없음) 켜면 검수 화면에 기계 값이 미리 채워진다.
4. **다시 처리와 회귀**: `run --fresh`(또는 다시 처리) → `regress` → 달라진 수치를 보고 `--update`, 무엇이 왜 바뀌었는지 커밋 메시지에 (윈도우의 현장 PC 에서 —
   회귀 기준은 비교할 OS 에서).
5. **감사와 test**: `review serve --queue readings --audit 50` → `review export-answers answers.json --split test` →
   `eval --answers answers.json --target raw --only-listed --split test` (test 는 한 번). 형식마다 정확도·자동 적재 오류율과 상한을 ROADMAP 의 실데이터 표에.
