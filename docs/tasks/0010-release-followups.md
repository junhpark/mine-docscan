## 1. 왜 하는가

PR #18 의 검증(실제 운반 3일치 83쪽 + 점검표 27쪽, 합성 묶음, 실제 3일치를 252일로 복제한 DB)에서 남은 것이다.

**(가) 빈 작업 DB 로 실으면 통합 DB 가 비워진다.** 합성: 새로 만든(쪽 0) 작업 DB 로 같은 사이트 이름·같은 스키마에 `publish` → "지운 범위 — 문서 3,
날짜 3", 대상의 `doc_field` 2,221 → 0, 종료 코드 0. 엑셀은 같은 경우 "작업 DB 에 쪽이 없어 지우지 않은 파일 4" 로 지키는데 (0009 4.1 다) 싣기는
지키지 않는다. 새 PC 로 옮기며 설정(통합 DB 의 주소)을 먼저 옮기면 `serve` 의 첫 바퀴가 대상을 비운다 — 지금은 설명서 5장이 "되살린 뒤에 주소를
넣으라"고 안내할 뿐이다 (0009 12절).

**(나) 버린 실패 문서가 `run --fresh` 뒤에 다시 failed 다.** 끝이 잘린 PDF 가 failed → "문서 버리기" → discarded. `run --fresh` 로 처음부터 만들면 다시
failed. main(0008)에서도 같다 — 등록(`pipeline/runner.register`)이 파일을 열지 못하면 `_fail_document` 로 끝나 결정을 보지 않고, 처리
(`process_document`)는 결정을 먼저 본다 (열기 전에 discarded). "지금의 DB = 같은 파일·검수·결정으로 처음부터 만든 DB" (0007) 를 어긴다.

**(다) 다시 스캔 서명이 작은 정합 오차에 약하다.** 실제 81쪽의 정합 그림을 옮기거나 돌려 원래 그림과 서명(`imaging/signature.py`, `BLOCK` 16)을 견줬다:

| 같은 그림을 | 유사도 중앙 | 5 % | 최소 |
|---|---|---|---|
| 1 px 옮김 | 0.995 | 0.989 | 0.970 |
| 2 px 옮김 (x 2, y 1) | 0.971 | 0.871 | **0.608** |
| 3 px 옮김 (x 3, y 2) | 0.907 | 0.627 | **0.316** |
| 0.2° 돌림 | 0.976 | 0.866 | 0.810 |

같은 날 다른 종이는 최대 0.601 (245쌍), 다른 날은 최대 0.852. 붙잡는 기준 `dup_min_sim` 은 0.80 이다. 정합의 괘선 오차는 대개 1 px 안이지만 양식에
따라 4 px 까지 나온다. 윈도우의 OpenCV 는 같은 그림을 조금 다르게 정합해 합성 다시 스캔 한 쪽의 유사도가 0.9987 → 0.8626 이었다 (0009 12절 단계 4).
실제 다시 스캔의 2–3 % 가 0.80 아래였던 것(ADR 0020)도 같은 까닭일 수 있다. 인쇄(괘선·글자)가 인쇄 마스크 밖으로 밀려 나온 것이 서명을 흔드는
것으로 보인다 — 손글씨는 1–2 px 옮겨도 같은 칸에 남는다. 같은 81쪽으로 후보 둘을 재 보았다 (참고 — 고르는 것은 단계 2):

| 서명 | 2 px 5 % / 최소 | 3 px 5 % / 최소 | 0.2° 5 % / 최소 | 같은 날 다른 종이 최대 |
|---|---|---|---|---|
| 지금 | 0.871 / 0.608 | 0.627 / 0.316 | 0.866 / 0.810 | 0.601 |
| 인쇄 마스크를 더 넓힘 (7 × 7 팽창) | 0.949 / 0.839 | 0.880 / 0.699 | 0.936 / 0.738 | 0.610 |
| 긴 가로·세로 선(41 px)을 지움 | 0.939 / 0.758 | 0.743 / 0.334 | 0.950 / 0.930 | 0.589 |

**(라) 설치 묶음을 다시 만들 수 없다.** 묶음의 바퀴는 만들 때마다 PyPI 의 그때 최신 판이다 (`scripts/bundle.py` 의 `pip download` 에 판이 없다 —
검증한 날 다시 받으니 numpy 2.5.3). zip 에는 파일의 수정 시각이 들어간다. 등록한 판의 묶음을 같은 커밋에서 다시 만들어 같은 것임을 보일 수 없고,
CI 산출물은 14일 뒤 지워진다.

**(마) 묶음 안의 LGPL 구성요소.** PDF 를 pypdfium2 로 읽게 되어(ADR 0023) 묶음에 AGPL 은 없다. 남은 소스 조건은 LGPL 둘이다.
- `psycopg`·`psycopg-binary` (LGPL-3.0-only) — 바이너리(`psycopg_binary` 의 C 확장)를 나눠 주면 그 대응 소스를 같이 주거나 받을 길을 알려야 한다.
- OpenCV 바퀴 안의 FFmpeg (`cv2/opencv_videoio_ffmpeg500_64.dll`, 30.9 MB, LGPL-2.1). 이 프로그램은 동영상을 읽지 않는다 (`cv2.VideoCapture` 를
  쓰지 않는다).
윈도우의 numpy 바퀴에는 libquadmath 가 없다 (OpenBLAS·LAPACK — BSD, GCC 런타임 — 예외가 있다). 법률 판단은 사람의 일이다 (8절).

**(바) CI 를 밖에서 볼 수 없다.** 검증 환경의 GitHub 연결은 산출물과 기록(다른 호스트에 있다)을 받지 못한다. 윈도우의 수치(시험 수, 설치 시간,
묶음의 크기·해시, 자가 시험 시간)를 0009 의 보고 밖에서는 확인할 길이 없었다.

**(사) 작은 것.** `publish` 의 판이 다를 때 "대상의 싣기의 판 이(가) 이 프로그램과 다릅니다" (`이(가)`, `을(를)` 이 글 세 곳에),
`template preview` 의 범례가 양식의 제목과 겹친다 (설명서의 V2 유류일지 그림).

## 2. 끝났을 때 되는 일

- 빈 작업 DB(쪽 0)로는 대상에서 아무것도 지우지 않는다 — 명령은 종료 코드 2 와 이유, 자동 싣기는 그 바퀴의 실패 `empty_work_db` 와 홈의 한 줄.
  `--rebuild` 는 사람이 고른 것이라 그대로 (경고 한 줄).
- 버린 문서는 열리지 않아도 버린 문서다 — 지금의 DB = 처음부터 만든 DB.
- 다시 스캔 서명이 ±2 px·0.2° 의 정합 오차에도 같은 종이를 0.93 넘게 본다 (합성, 리눅스·윈도우). 서명에 판이 있다.
- 잠금(`scripts/bundle.lock` — 바퀴)과 `scripts/bundle.toml`(sdist·빌드 도구)이 묶음에 드는 것의 판과 해시를 고정하고, 같은 커밋 + 같은 잠금이면
  zip 의 바이트가 같다.
- 묶음에 FFmpeg 가 없고 `sources/` 에 psycopg 의 소스가 있다. 라이선스 검사가 "소스를 같이 줘야 하는 것"을 확인한다.
- CI 의 주요 수치가 알림으로 남는다.
- 판 1.0.1.

## 4. 설계

### 4.1 빈 작업 DB 로 싣지 않는다

- **빈 작업 DB** = `doc_page` 에 행이 없다 — 엑셀과 같은 정의 (`export/writer.py` 의 `empty_db`). 문서만 등록된 상태(received·needs_date)도 빈 것이다.
- `publish/core.publish`: 빈 작업 DB 이고 대상의 상태 표에 문서·날짜 범위가 하나라도 있으면 **아무것도 하지 않고** `PublishError` 종류
  `empty_work_db`, 종료 코드 2: "작업 DB 에 쪽이 없습니다 — 통합 DB(문서 N·날짜 M)를 지우지 않았습니다. 되살리는 중이면 처리가 끝난 뒤에 다시,
  정말 비우려면 minedocscan publish --rebuild". `--check` 도 2 (같은 글). 대상이 비었으면(처음 싣기) 지금처럼 표를 만들고 통째(장비)를 싣는다.
  자리는 `publish()` 안, 판·사이트 검사 뒤이고 조각(`slices()`) 앞이다. 대상의 범위 수를 세는 메서드를 `Target` 에 더한다 (시험의 가짜 대상도).
- 자동 싣기(`publish/auto.py`): 그 바퀴의 실패 `empty_work_db` — 다른 실패처럼 `retry_seconds` 를 지키고(바퀴마다 연결하지 않게), 홈의 통합 DB 줄에
  "작업 DB 에 쪽이 없어 싣지 않음". `doc_page` 에 행이 생기면 `retry_seconds` 뒤의 첫 바퀴부터 지금처럼 싣는다.
- 요약 줄(`watch`·`serve` 의 로그)은 이 실패의 수·종류가 바뀔 때만 — 지금 `cli.py` 의 `_worth_showing` 은 싣기의 오류를 바퀴마다 찍는다. 엑셀의
  `failed_changed` 와 같은 장치를 싣기에도.
- `--rebuild` 는 빈 작업 DB 여도 한다 (사람이 고른 것) — 지운 범위의 수와 "작업 DB 에 쪽이 없다" 경고 한 줄. 지금은 표를 먼저 버리므로
  (`_drop_and_create`) `Result.removed` 가 늘 0 이다 — 버리기 전에 대상의 범위를 종류마다 세어 `Result` 에 싣는다.
- 작업 DB 를 처음부터 다시 만드는 동안(쪽이 몇 개 있다)은 막지 않는다 — 설명서 5장의 순서(되살리는 동안은 `serve` 를 끄거나 `[publish]` 를 비운다)에
  이 규칙 한 줄을 더한다. `publish --check` 의 도움말(`cli.py`)과 `명령.md` 에 빈 작업 DB 의 경우.

### 4.2 버린 문서는 열리지 않아도 버린 문서다

- 등록(`register`)이 파일을 열지 못하면 지금은 `_fail_document` 로 failed 다. 그 전에 그 문서의 결정(`decs.effective`)을 보고 **버린 문서면 처리가 버린
  문서에 하는 것과 같은 행**을 남긴다 — 열 수 없어도 discarded. `process_file` 이 파일을 읽지도 못한 길(`OSError`)도 같은 규칙.
- 어느 열(쪽 수, `error`, `warning`, `work_done` …)이 어떤 값이어야 하는지는 불변식이 정한다: 라이브 길(실패 → 버리기 → 처리)과 처음부터 길
  (`run --fresh`)이 같은 행을 남긴다. 결정은 `Pipeline.__init__` 에서 등록보다 먼저 읽힌다.
- **되살리기(`restore`)** 하면 두 길 모두 다시 failed 다. 그런데 지금 두 길의 날짜 열이 다르다 — 라이브 길은 처리(`process_document`)의 실패 갈래가
  `_finish_document` 를 날짜 없이 불러 `work_date`·`date_source` 가 NULL, 처음부터 길은 등록의 `_fail_document` 가 파일명의 날짜를 적는다 (검토에서
  재현). **처리의 실패 갈래도 `(doc_date, date_source)` 를 적는다.** 합성 접수 묶음의 잘린 PDF 는 등록에서 실패하므로 그 묶음의 행은 그대로다.
- 접수의 `_failed`, 손상 방침(`damaged_pdf`)은 그대로.

### 4.3 다시 스캔 서명을 작은 정합 오차에 강하게

**가. 먼저 잰다.** `scripts/sig_probe.py`:
- `--synthetic`: 합성 다시 스캔 묶음(`synth --rescans` — `tests/test_rescans.py` 와 같은 x/y 쌍. `--intake` 와는 같이 쓰지 못한다)을 만들어 처리하고,
  그 정합 그림에서 ① 같은 그림을 옮기고 돌린 것과의 유사도 ② 합성 다시 스캔(같은 종이)의 유사도 ③ 같은 날·같은 계열의 다른 종이의 유사도 —
  분포(중앙·5 %·최소·최대).
- **옮기는 법** (①): 정합한 회색 그림에 `cv2.warpAffine` (`INTER_LINEAR`, `borderValue=255`) — 옮김 (dx, dy) = (1, 0)·(2, 1)·(3, 2) px, 그림의 가운데를
  축으로 0.2° 돌림, (2, 1) px + 0.2° 를 같이. 서명은 같은 템플릿의 마스크로. 4.3 나의 기준은 (2, 1) px·0.2°·둘을 같이, 이 셋에 걸린다.
- 지금의 서명과 **후보 전부를 한 번에** 재고 (그래서 단계 2 의 한 CI 실행으로 전과 후가 나온다), 요약을 스스로 `::notice` 로 찍는다 (4.6 의 꼴).
  리눅스(slow 작업)와 윈도우(windows 작업)에서 단계 2 부터 돈다.
- `--site … --work-root …`: 있는 작업 DB 의 정합 그림으로 ①과 ③ (실데이터 — 사람이 돌린다, 8절). 값·그림·이름 없이 수만 찍는다.

**나. 고친다** — 서명(`imaging/signature.py`)만. 판정 규칙(같은 날·계열의 앞 순서 적재된 쪽, `dup_min_sim`)은 그대로.
- 후보는 1절 다의 둘(인쇄 마스크를 서명에서만 더 넓힌다, 긴 선을 지운다)과 둘을 같이, 그 밖에 이유가 있는 것. **수치로 고른다** (합성, 리눅스와 윈도우
  둘 다): 가의 세 경우마다 5 % ≥ 0.93·최소 ≥ 0.85. 합성 다시 스캔(같은 종이) 전부 ≥ 0.95. 같은 날 다른 종이의 최대가 지금보다 0.02 넘게 오르지
  않는다. 쪽 하나의 서명 시간과 글자열 길이가 지금의 2배를 넘지 않는다. 고른 것과 버린 것의 수치를 ADR 0020 에.
  (검토에서 합성 하루치 6쪽으로 잰 것: 7 × 7 로 넓힌 마스크에서 (2, 1) px + 0.2° 가 0.598 → 0.950, 0.2° 가 0.889 → 0.982, 같은 날 다른 종이 최대 0.594 그대로.)
- 넓힌 마스크는 템플릿마다 한 번 만들어 두어도 된다 (`Template.signature_mask` 옆의 캐시).
- **서명의 판**: `encode` 가 앞에 판을 적는다 (`2|<높이>x<너비>:…` — 판이 없는 지금 것은 판 1). 판이 다른 두 서명은 비교하지 않는다 (`similarity` →
  None — 다시 스캔으로 보지 않는다). 스키마는 그대로 (글자열). `report` 는 옛 판 서명의 쪽이 **있을 때만** 그 수의 키를 낸다 (`variants` 처럼 —
  `null` 리포트가 그대로이게). `info` 는 작업 DB 를 읽기 전용으로 열어 같은 수를 알리고(없으면 아무 말도 하지 않는다) `run --fresh` 를 안내한다.
- `dup_min_sim` 0.80 그대로 — 기준은 실제 다시 스캔을 본 뒤에 사람이 정한다 (0008 1절 라, 8절).

### 4.4 묶음을 다시 만들 수 있게

- **잠금** `scripts/bundle.lock` — pip 의 requirements 꼴로, 묶음에 드는 **바퀴**마다 `이름==판 --hash=sha256:…` (cp312-win_amd64). `minedocscan`
  자신은 커밋에서 만든다 (잠금 밖). 앱 전용 파이썬과 pip 은 지금처럼 `scripts/bundle.toml`. 4.5 의 소스(sdist)는 잠금에 넣지 않는다 — 같은 이름의
  바퀴와 sdist 를 한 requirements 로 받을 수 없다 (검토에서 재현: pip 이 바퀴를 골라 sdist 의 해시가 어긋난다. `--no-binary` 로 받으면 해시 없는 빌드
  의존성을 깔고 sdist 의 빌드를 돌린다). sdist 는 `bundle.toml` 의 `[sources]`(URL + sha256)로 `fetch()` 가 받는다 (`[pip]` 처럼).
- `python scripts/bundle.py lock` — 지금처럼 풀어서(`pip download`) 잠금과 `[sources]` 의 판·해시를 새로 쓴다 (사람이 판을 올릴 때, 인터넷이 되는 곳에서).
  묶음 만들기는 `pip download --no-deps --require-hashes --only-binary=:all: --platform win_amd64 --python-version 3.12 --implementation cp -r scripts/bundle.lock`
  — 잠금에 없는 것은 받지 않는다 (이 명령이 바퀴만으로 되는 것은 검토에서 확인했다).
- 잠금이 맞는지: **`bundle.py` 가 받은 뒤에** 잠금의 바퀴들의 `Requires-Dist` 를 (win32·cp312 의 표식으로) 따라가 런타임 의존성의 닫힘
  (`minedocscan[postgres]` 와 `windows_only`)을 다 담는지, 판이 `pyproject.toml` 의 범위 안인지 본다 — 모자라면 멈춘다. 시험은 가짜 바퀴로 (기본 시험에서는
  리눅스에 깔린 최신 판의 메타데이터가 잠금이 아니다). 윈도우 작업의 설치가 `--no-index` 로 되는 것이 마지막 확인.
- **같은 바이트**: 같은 커밋 + 같은 잠금이면 zip 의 바이트가 같다. 그러려면
  - `minedocscan` 의 바퀴: `SOURCE_DATE_EPOCH` = 커밋 시각 (hatchling 이 따른다 — 검토에서 확인). 빌드 백엔드(hatchling)와 설명서를 만드는 `markdown` 의 판을
    `bundle.toml` 에 고정하고 (`[build]` — 판 + 해시), 그 판을 깔아 `pip wheel --no-build-isolation` 으로 만든다 (지금은 둘 다 고정되지 않았다).
  - 윈도우에서 받은 저장소의 글 파일이 CRLF 로 바퀴에 들어가지 않게 `.gitattributes` (바퀴·설명서에 드는 글은 LF. `.ps1` 은 `bundle.py` 가 BOM·CRLF 로
    바꾼다 — 지금처럼).
  - zip: `ZipFile.writestr(ZipInfo)` 로 — 이름 순서, `date_time` 고정(커밋 시각, UTC, 1980 이후), `external_attr`·`create_system`·압축 수준 고정.
    지금의 `z.write()` 는 파일의 수정 시각과 권한을 옮긴다. 4.5 에서 다시 묶는 OpenCV 바퀴도 같은 방법으로.
  windows-install 작업이 묶음을 **두 번** 만들어(다른 폴더) 해시가 같은지 본다. 같은 커밋을 리눅스(우분투 작업)에서 만든 해시도 보고만 (같으면 좋다).
  해시는 알림으로.
- 테스트 작업(우분투·윈도우의 pytest)은 지금처럼 최신 판으로 돈다 — 위쪽의 깨짐을 먼저 본다. 잠금은 묶음에만 쓴다.
- 판을 올리는 순서(`bundle.py lock` → CI → 자가 시험)를 `scripts/README.md` 와 설명서 2장에.

### 4.5 LGPL 구성요소

- **FFmpeg 를 뺀다.** `bundle.py` 가 OpenCV 바퀴(잠금의 해시로 확인한 원래 바퀴)에서 `cv2/opencv_videoio_ffmpeg*.dll` 을 빼고 `RECORD` 의 그 줄을
  지워 다시 묶는다 (이름·판 그대로. `SHA256SUMS.txt` 는 바꾼 바퀴의 것). `THIRD_PARTY_NOTICES.txt` 의 OpenCV 항목에 "FFmpeg 플러그인을 뺐다 —
  이 프로그램은 동영상을 읽지 않는다". 그 DLL 이름이 바퀴에 없으면(OpenCV 의 판이 바뀌었다) 멈추고 알린다. pip 은 설치할 때 `RECORD` 의 해시를
  확인하지 않으므로(`pip check` 도) 맞는지는 시험이 본다: 다시 묶은 바퀴의 모든 항목에 해시·크기가 맞는 `RECORD` 줄이 있고, 모든 줄에 항목이 있다.
  `cv2.pyd` 는 동영상 플러그인을 쓸 때만 이름으로 찾아 읽는다 (검토에서 바이너리의 가져오기 표로 확인 — 윈도우의 자가 시험이 마지막 확인).
- **psycopg 의 소스.** 묶음에 `sources/` — 묶음의 `psycopg`·`psycopg-binary` 와 같은 판의 sdist (`psycopg-<판>.tar.gz`, `psycopg_c-<판>.tar.gz` —
  `psycopg-binary` 는 `psycopg_c` 로 만든다: 그 바퀴에는 생성된 C 와 libpq·libssl·libcrypto 가 든다). 판·해시는 `bundle.toml` 의 `[sources]` (4.4).
  `sources/README.txt`: 어느 바퀴의 소스인가, 바이너리를 만드는 방법이 있는 곳(psycopg 저장소의 그 판 태그). `NOTICE` 와 `INSTALL.txt` 에 한 줄.
- **검사.** `scripts/licenses.py` 가 항목마다 "소스를 같이 줘야 하는가"(LGPL·GPL·AGPL·MPL 이면 예, GCC 런타임 예외는 아니오)를 적는다. 바퀴 안에 같이 든
  바이너리의 라이선스는 대응표로 (지금은 `psycopg-binary` 의 `EXTRA_TEXTS` 만 있다 — `opencv_videoio_ffmpeg*` → LGPL-2.1 같은 표를 더한다), 배포판과
  sdist 의 대응도 (`psycopg-binary` → `psycopg_c`).
  **소스 검사는 `--wheels` 일 때만** 새 선택 `--sources DIR` 로: 그런 배포판의 sdist 가 없거나 바퀴 안의 그런 구성요소가 빠지지 않았으면 종료 코드 1.
  `--installed`(우분투의 test 작업 — 리눅스 바퀴에는 numpy 의 libquadmath, OpenCV 의 libav* 가 들고 `sources/` 가 없다)는 세기만 한다.

### 4.6 CI 의 알림과 작은 것들

- **알림**: 작업마다 `::notice title=…::…` 한두 줄 — 수만 (경로·이름 없이). 실패한 작업에서도 남게 (`if: always()`).
  - windows: 시험 통과·건너뜀·실패, 시간. (`sig_probe --synthetic` 의 요약은 단계 2 부터 스스로 찍는다.)
  - windows-install: 묶음의 바이트·sha256, 두 번 만든 해시가 같은지, 설치·올리기·자가 시험의 초, `serve` 가 작업 스케줄러로 떴는지, 라이선스 검사의 수.
  - 우분투 test: 자가 시험의 초, 라이선스 검사의 수. slow: V2 지표 한 줄 (그리고 `sig_probe`).
  알림 글은 한 곳(`scripts/` 의 작은 함수)에서 만든다: **ASCII 로만** (윈도우 러너의 표준 출력은 cp1252, run 블록도 ASCII — 0009), `key=value` 꼴,
  `%`·줄바꿈 등은 GitHub 의 규칙대로 이스케이프, 작업마다 두 줄 안 (한 단계에 같은 종류 10개, 한 작업에 50개가 상한). 시험이 경로·사용자 이름이 들어가지
  않는 것을 본다.
- **글**: `NeedRebuild` 의 "대상의 {what} 이(가) …" → 조사를 붙이지 않는 꼴로 ("대상의 싣기의 판: 이 프로그램과 다릅니다 — …"). 같은 꼴의 `이(가)`·
  `을(를)` (`recognize/digits/model.py`, `review/export.py`)도. 옛 글을 옮겨 적은 설명서 5장도 고친다.
- **범례**: `template preview` 의 범례를 그림의 **오른쪽이나 아래에 덧붙인 띠**에 — 양식의 어떤 부분도 가리지 않고, 미리보기의 화소 좌표가 그대로
  템플릿 좌표이게 (위나 왼쪽에 붙이면 좌표가 밀린다). `tests/test_template_tools.py` 의 크기 단언을 고친다.

## 6. 시험

- 전부 합성 데이터. 시험에서 잠들지 않는다 (시계 주입). PostgreSQL 시험은 0008·0009 와 같다.

  옮긴 그림 몇 장으로 (기본 시험의 시간 안에서).

## 7. 지켜야 할 것

- **원본을 지우지 않는다.** 버린 실패 문서도 보관 폴더의 파일은 그대로다.
- 작업 DB 가 진실이다 (ADR 0021) — 빈 작업 DB 하나만 막는다. 대상에 다른 것이 쓰게 하지 않는다.
- 다시 스캔 의심을 기계가 스스로 버리거나 합치지 않는다 (ADR 0020) — 서명만 고친다.
- 설치는 망에 닿지 않는다. 묶음은 잠금 밖의 것을 받지 않는다.
- 로그·알림·보고에 경로·이름·차량번호를 찍지 않는다 — 수만. `sig_probe` 도.
- `CLAUDE.md` 의 작업 규칙을 따른다.

## 8. 사람이 할 일

PR 이 합쳐진 뒤. 0009 8절의 일(현장 PC 설치, 사이트 표식, 통합 DB 의 `--rebuild`, 가린 그림, 성적서의 실데이터 칸, 설명서 읽기)은 그대로이고, 아래가 더해진다.

1. **회귀 기준**: PDF 를 PDFium 으로 읽게 된 것(0009)과 서명(이 지시서)을 한 번에 — **윈도우의 현장 PC 에서** (`CLAUDE.md` — 기준은 비교할 OS 에서).
   달라진 수치를 커밋 메시지에 (PR #18 의 검증에서 리눅스 기준 값 유무 28/14,729 칸이 바뀌었다).
2. **실제 다시 스캔**: 하루치를 두 번 스캔해 접수 → 붙잡힌 쪽의 수, `sig_probe --site … --work-root …` 의 분포 → `dup_min_sim` 을 정한다 (0008 1절 라).
3. **엑셀 조각의 시간**: 현장 PC 에서 한 해치(또는 `scripts/bigdb.py` 의 복제)로 바뀐 것 없는 조각 하나의 시간. 5초를 넘으면 다음 지시서에서 조각을 줄인다
   (검증한 2코어 기계에서 실제 밀도로 최대 6.0초).
4. **라이선스**: 이 프로그램의 라이선스 문구 — 저장소는 공개인데 `pyproject.toml` 은 `Proprietary`, `NOTICE` 의 첫 줄은 비어 있다. FFmpeg 를 뺀 것과
   psycopg 의 소스를 넣은 것으로 충분한지 (기관).
5. **새 PC 로 옮기기**: 설명서 5장의 순서를 한 번 해 본다 — 빈 작업 DB 의 싣기가 막히는지.
6. **등록**: `v1.0.1` 태그와 GitHub Release 에 설치 묶음·잠금·성적서 (CI 산출물은 14일 뒤 지워진다).
