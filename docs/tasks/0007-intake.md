## 1. 왜 하는가

지금까지는 정리된 묶음 폴더에 `minedocscan run` 을 치는 것으로 검증했다: 파일명에 날짜가 있고, 쪽이 바로 서 있고, 종이마다 한 번씩만 스캔된 묶음이다.
현장에서는 스캐너의 저장 폴더에 파일이 떨어진다. 그 사이에서 깨지는 것을 실제 3일치(83쪽)와 스캐너 사양으로 미리 재 보았다.

**(가) 날짜를 모르는 파일이 조용히 적재된다.** 날짜는 파일명 규칙(`[ingest] date_from_filename`)과 라벨에서만 온다.
스캐너가 붙이는 이름은 그 규칙에 맞지 않는다.
- 하루치(28쪽)를 규칙에 맞지 않는 이름으로 넣어 보았다: 28쪽 전부 `loaded`, 업무 행이 `work_date` NULL 로 들어갔다
  (`prod_haul` 1,700행, `prod_tally` 60행, `eq_usage_daily` 13행). 교차검증은 0행(날짜가 없어 건너뛴다), 경고는 없다.
- 날짜는 분류보다 먼저 필요하다 — 그날 유효한 판만 후보가 된다 (ADR 0010). 날짜를 모르면 개정판을 가릴 수 없다.
- 스캔한 날은 작업한 날이 아니다 (다음 날 아침에, 또는 며칠 치를 모아서 스캔한다). 파일의 시각으로 날짜를 정할 수 없다.

**(나) 쪽이 돌아서 들어온다.** 양식은 B5 가로(257 × 182 mm)다. 보유한 스캐너(Canon imageFORMULA R10)는 급지 폭이 216 mm 까지라
짧은 변부터 넣어야 하고, 그러면 지금의 기준 이미지에서 90° 돈 그림이 된다. 뒤집어 넣으면 270°·180° 다. (지금 가진 스캔은 복합기로 만든 것이라 전부 바로 서 있다.)
- 실제 83쪽을 90°·180°·270° 돌려 지금 코드에 그대로 넣었다. 양식은 83/83 같게 분류되고 83/83 `loaded` 다 — ORB 와 호모그래피가 회전을 흡수한다.
- **그러나 결과가 조용히 달라진다**:

  | | 괘선 오차 (바로 선 쪽과의 차이, 최대) | 값 유무가 달라진 칸 (10,274칸 중) | 교차검증 일치 (바로 선 묶음 564) |
  |---|---|---|---|
  | 90° | +2.0 px (최대 4.0) | 16 | 565 |
  | 180° | +4.0 px (최대 6.0 — 통과 한계) | 32 | 568 |
  | 270° | +1.5 px (최대 3.0) | 20 | 565 |

- 첫 정합의 호모그래피에서 방향(90° 단위)을 읽으면 83쪽 × 네 방향 전부 맞았다 (90° 단위에서 벗어난 각은 최대 2.05°, 중앙 0.15°).
  그 방향만큼 정확히 되돌려 세운 뒤 다시 정합하면 **정합 그림이 바로 선 쪽과 바이트까지 같았다** (249/249). 드는 시간은 돌아간 쪽마다 0.3초.

**(다) 같은 종이를 다시 스캔하면 두 번 들어간다.** 문서 ID 는 파일의 해시라 같은 파일만 막는다. 급지식 스캐너는 걸리면 묶음을 다시 넣는다.
- 하루치 30쪽을 다시 스캔한 것처럼(다시 렌더링해 조금 기울이고 밀고 흐리게) 한 파일 더 넣었다: 60쪽 전부 `loaded`,
  `prod_haul` 1,700 → 3,400행, `prod_tally` 60 → 120행, `eq_usage_daily` 15 → 30행.
  그날의 교차검증은 200행(일치 192·불일치 8)에 `missing_matrix` 200행이 더 붙었다 — 다시 스캔한 일보가 없는 차량처럼 보인다.
- **같은 날·같은 양식 안에서는 손글씨의 자리로 갈린다.** 정합 그림에서 인쇄를 지운 손글씨를 16 px 칸으로 센 벡터의 코사인:

  | 쌍 (실제 3일치) | 수 | 유사도 |
  |---|---|---|
  | 같은 날, 같은 양식의 서로 다른 종이 | 258 | 최대 0.66 (인쇄를 기준 이미지로 지우면 0.60) |
  | 다른 날, 같은 양식의 서로 다른 종이 | 586 | 최대 0.84 — 같은 사람이 같은 차로 같은 칸에 쓴다 |
  | 같은 종이를 흔들어(±2.5°, ±25 px, 배율 ±3 %, 흐림, 밝기, JPEG 45–80) 다시 정합 | 83 | 최소 0.91, 중앙 0.99 |

  다른 날까지 비교하면 겹친다. 다시 스캔한 종이는 날짜가 같으므로 같은 날 안에서만 비교하면 된다.
  아래 줄은 흔들어 만든 것이다 — 진짜 다시 스캔은 8절에서 해 본다.

**(라) 빈 쪽.** 양면으로 스캔하면 뒷면이 들어온다. 합성 빈 쪽 60장(흰 종이, 티, 가장자리 그림자, 앞면이 비친 뒷면)은 전부 `unknown_form` 이 되고
그 문서는 `needs_review` 가 된다. 어두운 화소의 비율(`grid.binarize` 뒤 2 × 2 열기)로는 갈린다: 실제 83쪽은 최소 0.046,
흰 종이·티 ≤ 0.0003, 가장자리 그림자 ≤ 0.011, 옅게 비친 뒷면(15 %) ≤ 0.001. 진하게 비친 뒷면은 겹친다 (30 % ≤ 0.028, 45 % ≤ 0.053).

**(마) 묶음이 나뉘는 것은 이미 된다.** 급지대가 20매라 하루치(25–30쪽)는 두 파일이 된다. 30쪽을 20 + 10 으로 나눠 넣으면
쪽 상태·업무 행 수·교차검증·값 유무(3,713칸)가 한 파일일 때와 같았다. 고칠 것이 없다 — 시험으로만 남긴다.

**(바) 화면이 대기열마다 따로다.** `review serve --queue X` 는 대기열 하나를 띄운다. 무엇이 들어왔고 무엇이 남았는지 보는 곳,
문서 하나를 통째로 보는 곳이 없다 (ROADMAP "검수 화면: 문서 단위 화면 — 없음").

그래서 이번에 하는 것은 **접수**다: 스캐너 폴더에 떨어진 파일이 날짜를 얻고(가), 바로 서고(나), 한 번만 들어가고(다·라),
사람은 날짜를 모를 때와 의심스러울 때만 한 화면에서 본다(바). ROADMAP M5 의 "폴더 감시"와 "문서 단위 화면"이다.
엑셀 내보내기·가려서 내보내기·PostgreSQL 은 다음 지시서로 넘긴다 — 접수가 먼저 서야 내보낼 것이 믿을 만하다.

## 2. 끝났을 때 되는 일

```bash
# minedocscan.toml:  [paths] inbox = "…/스캐너 저장 폴더"   (또는 MINEDOCSCAN_INBOX)
minedocscan serve --reviewer jp          # 접수 폴더 감시 + 운영 화면 (127.0.0.1:8765). 스캔 버튼을 누르면 화면에 문서가 뜬다
minedocscan watch                        # 화면 없이 감시만.  --once 면 한 바퀴(접수 + 대기 중인 문서 처리) 돌고 끝낸다

minedocscan doc list [--status needs_date]                          # 문서 목록: 받은 시각, 쪽 수, 날짜, 상태, 다시 처리 대기
minedocscan doc date    <문서 ID | 쪽 ID> 2025-03-26 --reviewer jp   # 날짜를 정한다 (결정을 남긴다 — 처리는 watch·serve 가 한다)
minedocscan doc discard <문서 ID | 쪽 ID> --reviewer jp              # 버린다 (걸린 스캔, 다시 스캔한 쪽).  restore 로 되살린다
minedocscan doc keep    <쪽 ID> --reviewer jp                        # "다시 스캔한 것이 아니다" — 다른 종이다

minedocscan run DB_scans --skip-existing              # 묶음 폴더는 지금처럼. 날짜를 못 얻은 문서는 적재하지 않고 기다린다
minedocscan report                                    # 날짜를 정할 문서, 돌아간 쪽, 빈 쪽, 다시 스캔 의심 쪽, 버린 것
minedocscan template init <이미지> --name <이름> --rotate 90        # 돌아간 스캔으로 템플릿을 만들 때 기준 이미지를 세운다
minedocscan synth out/intake --intake                 # 합성 접수 폴더: 돌아간 쪽, 날짜 없는 이름, 빈 뒷면, 다시 스캔, 잘린 PDF …
```

## 3. 범위

**이번에 한다**
- 쪽의 방향을 세운다, 빈 쪽을 가린다 (단계 1)
- 날짜 없는 문서는 기다린다, 문서·쪽의 결정 기록(날짜·버리기·되살리기·다른 종이), 문서를 지우고 다시 처리하기 (단계 2)
- 다시 스캔한 쪽을 붙잡아 둔다 (단계 3)
- 접수 폴더 감시: 다 쓰인 파일만, 보관 폴더로 옮기고, 죽었다 켜도 이어서 (단계 4)
- 운영 화면: 홈, 문서 화면, 결정 입력, 대기열로 가는 길 (단계 5)
- 합성 접수 시나리오, 문서 (단계 6)

**이번에 하지 않는다**
- 엑셀 내보내기, 가려서 내보내기, PostgreSQL 어댑터 (다음 지시서)
- 손으로 쓴 월·일로 날짜를 정하는 것. 메타 모델의 실데이터 수치가 나온 뒤에 다시 정한다 — 지금처럼 대조에만 쓴다 (4.2)
- 한 문서에 섞인 다른 날짜의 쪽을 기계가 가르는 것. 쪽의 날짜는 사람이 정할 수 있게만 한다 (4.2)
- 설치 파일(exe), 윈도우 서비스·시작 프로그램 등록 (M6). 문서에 띄우는 법만 적는다
- 스캐너를 직접 다루는 것(TWAIN·드라이버). 스캐너의 프로그램이 폴더에 저장한 파일만 본다
- 다른 컴퓨터에서 화면에 접속하는 것, 로그인, 두 사람이 동시에 입력하는 것. 화면은 지금처럼 127.0.0.1 하나다
- 사이트 팩(템플릿·모델·대응표)을 고친 것을 돌고 있는 `serve` 가 알아채는 것. 고친 뒤에는 다시 띄운다
- 관리 계열 양식, 여백 행 규칙, 소수·시각 읽기, 정답 대기열(`--n`·`--audit`)의 변경
- 정합·✓·잉크·덩어리의 임계값 변경. **날짜가 있고 바로 선 묶음의 결과는 그대로여야 한다** — `null` 회귀 수치, 기본 합성 묶음의 바이트,
  리포트의 지금 있는 항목 (새 항목은 더해진다)

## 4. 이미 정한 것

### 4.1 문서는 등록되고, 날짜가 있어야 처리된다

`doc_document.status` 가 문서의 자리다.

| 상태 | 뜻 | 쪽·필드·업무 행 |
|---|---|---|
| `received` | 등록했고 처리가 아직 끝나지 않았다 (새 문서, 또는 처리하다 끊긴 문서) | 없거나 만들다 만 것 |
| `needs_date` | 날짜를 얻지 못했다 (4.2). 사람이 정할 때까지 기다린다 | 없음 |
| `processed` · `needs_review` | 지금과 같다 | 있음 |
| `failed` | 지금과 같다 (읽지 못한 문서) | 없음 |
| `discarded` | 사람이 버렸다 (4.3) | 없음 |

- **등록** = 파일을 한 번 열어 해시와 쪽 수를 적는 것. 열리지 않는 파일(쓰레기 바이트, 쪽이 없는 PDF, 손상 방침에 걸린 PDF)은 날짜와 상관없이
  지금처럼 `failed` 다 — 날짜를 보는 것은 그 뒤다. **처리** = 그 문서의 쪽을 분류·정합·적재하는 것. 지금은 `process_file` 하나가 둘 다 한다 — 나눈다:
  `Pipeline.process_document(document_id)` 가 처리이고, `process_file(path)` 는 "등록하고 바로 처리"로 남는다 (서명과 돌려주는 값은 그대로).
- **다시 처리 대기는 상태가 아니라 요청 번호로 적는다**: `doc_document.work_requested`(다시 처리해 달라는 요청이 올 때마다 +1)와
  `work_done`(처리를 시작할 때 읽은 요청 번호를 끝날 때 적는다). 대기 중 = `status = 'received'` 이거나 `work_requested > work_done`.
  처리하는 도중에 온 요청은 남아서 다음 바퀴에 다시 처리된다. 다시 처리를 기다리는 문서는 옛 상태와 옛 행을 그대로 가지고 있고, 목록과 화면은
  "다시 처리 대기"를 따로 보여 준다. 세 가지를 지킨다: ① `work_requested`·`work_done`·`received_at` 은 문서 행의 `upsert` 로 쓰지 않는다
  (지금의 `upsert` 는 키가 아닌 열을 전부 덮어쓴다) — 전용 UPDATE 로만. ② 처리는 요청 번호를 **결정을 읽기 전에** 읽는다 (4.8 의 2번 트랜잭션 안에서).
  ③ 처리하다 `failed` 가 된 문서도 `work_done` 을 적는다 — 아니면 바퀴마다 다시 처리된다.
- `update_document_status` 는 `processed` 와 `needs_review` 사이에서만 바꾼다. 지금은 검수를 저장할 때마다 무조건 다시 적어서
  (`review/store.save`) `received`·`needs_date`·`discarded`·`failed` 를 덮어쓴다.
- **날짜가 없는 쪽은 핸들러에 넘기지 않는다.** 업무 테이블(`prod_*`, `eq_*`, `insp_*`)에 `work_date` 가 NULL 인 행이 생기지 않는다.
- `needs_date` 는 `run` 에도 같다. 요약에 "날짜를 정할 문서 N건"이 한 줄 나오고 종료 코드는 0 이다 (실패가 아니다).
  `run --skip-existing` 은 `processed`·`needs_review`(쪽 오류 없음, 대기 중 아님)와 `discarded` 를 건너뛰고, `needs_date` 는 날짜만 다시 본다.
- **파이프라인을 도는 것은 한 번에 하나다** (`run`, `watch`, `serve` 의 작업 스레드). 둘째는 시작하지 않고 한 줄로 알린다. 잠금은 죽은 프로세스의 것이
  남지 않는 방법으로 (예: `WORK_ROOT` 의 작은 SQLite 파일에 배타 트랜잭션을 잡고 있기 — 표준 라이브러리만으로 윈도우에서도 된다).
  잠금은 명령이 잡는다 (`Pipeline` 객체가 아니다 — 시험이 한 프로세스에서 `Pipeline` 을 여럿 만드는 것은 그대로 된다).
  `doc …` 명령과 화면은 결정을 남기기만 하므로 잠금과 상관없다.

### 4.2 날짜의 출처와 순서

쪽의 날짜는 앞의 것이 이긴다:

1. 쪽의 결정 (4.3) 2. 문서의 결정 3. 라벨 (쪽 라벨이 문서 라벨을 이긴다 — 지금 그대로) 4. 파일명 규칙

- **쪽의 날짜가 정해지는 곳은 지금 두 군데다**: `SitePack.page_meta`(분류 후보와 `doc_page.work_date`)와 `pagemeta.human_values`
  (→ `doc_page_meta` 의 `date` 행 → 핸들러의 `ctx.work_date`). 둘이 위의 순서 하나를 쓰게 한 곳으로 모은다.
  `pagemeta.refresh_page`(메타 필드를 검수한 직후에 최종 값을 다시 계산한다)가 결정을 잊으면 안 된다.
- 출처에 `decision` 을 더한다. 사람의 출처 목록이 네 군데에 따로 적혀 있다 — `pagemeta.HUMAN_SOURCES`, `review/queue.py`, `review/export.py`,
  `evaluate/meta.py`. 한 곳에서 가져다 쓰게 고친다 (결정으로 날짜를 얻은 쪽이 `export-crops --meta`·`eval --meta`·표본 감사에서 빠지지 않게).
- 문서의 날짜(`doc_document.work_date`)는 문서의 결정 > 문서 라벨 > 파일명 규칙. 없으면 `needs_date` 다 — 쪽의 날짜만 있는 문서도 기다린다.
  ISO 날짜(`YYYY-MM-DD`)가 아닌 라벨 값은 문서의 날짜로 치지 않는다 — 그런 라벨뿐인 문서는 `needs_date` 다 (지금은 그대로 적재한다).
  `human_values` 가 그런 값에서 월·일을 대조하지 않는 것은 그대로다.
- 파일명 규칙은 **원래 파일명**에 건다 (접수 폴더에서 보관 폴더로 옮겨도 `source_name` 은 원래 이름).
- 사람이 넣는 날짜는 한 곳에서 읽는다 (`intake/dates.py`): `2025-03-26`, `25.03.26`, `250326`, `0326`(해는 받은 날을 넘지 않는 가장 가까운 해).
  달력에 없는 날짜만 거절한다. 받은 날보다 뒤이거나 31일 넘게 앞이면 화면이 한 번 되묻고(확인하면 저장), 명령은 경고 한 줄을 내고 저장한다
  — 지난 묶음을 넣는 일은 있고, 합성 묶음의 날짜는 2030년이다. "받은 날"은 인자로 받는다 (시험에서 시계에 기대지 않게).
- 손으로 쓴 월·일(`date.month`·`date.day`)은 지금처럼 대조만 한다 (`pages --meta-mismatch --meta-key date.day`). 날짜를 정하지 않는다.
- 화면은 날짜를 미리 채우지 않는다. 첫 쪽의 그림을 보여 주고 사람이 종이의 날짜를 읽어 넣는다 (4.9).
- `run` 에 날짜를 주는 선택(`--date`)은 만들지 않는다. 날짜 없는 쪽 하나를 돌려 보려면 파일명에 날짜를 넣거나 `doc date` 로 정한다
  — 날짜가 한 번의 실행에만 있으면 그 뒤의 검수·다시 처리에서 사라진다.

### 4.3 결정 기록 — 추가 전용 파일이 원본이고, 결정은 "다시 처리"로 적용한다

문서와 쪽에 대해 사람이 정한 것은 검수 기록(ADR 0008)과 같은 방식으로 남긴다.

- 파일: 검수 파일과 같은 폴더의 `decisions.jsonl` (기본 `<site>/reviews/decisions.jsonl`, `MINEDOCSCAN_REVIEWS` 를 주면 그 옆).
  한 줄 = 결정 하나, 추가 전용. 지우거나 덮어쓰지 않는다. 시각은 검수 기록과 같은 표기(UTC).

  ```json
  {"decision_id": "…", "target": "<document_id 또는 page_id>", "kind": "date", "value": "2025-03-26",
   "decided_by": "jp", "decided_at": "2026-10-08T00:12:44Z", "note": ""}
  ```

- 종류: `date`(문서·쪽, value 는 ISO 날짜) · `discard`·`restore`(문서·쪽 — 버린다·되살린다) · `keep`(쪽 — 다시 스캔한 것이 아니다, 4.6).
- 유효한 결정은 대상마다, 묶음(`date` / `discard`·`restore` / `keep`)마다 파일에서 가장 뒤의 것 하나. 버린 쪽에 `keep` 이 있어도 버린 것이다.
- 대상은 DB 에 있는 문서, 또는 그 문서의 1–`n_pages` 쪽이어야 한다 (쪽 ID 는 `document_id-pN` 이라 다시 처리해도 같다). 아니면 거절하고 파일에 남기지 않는다.
  여러 결정을 한 번에 저장할 때는 전부 검사한 뒤에야 쓴다 (검수의 `/api/reviews` 와 같다).
- 파이프라인이 시작할 때 검수 파일과 같이 `doc_decision` 으로 읽어 들인다 (그때는 대상이 DB 에 없어도 된다 — 문서가 등록되면 붙는다).
  문서 ID 는 파일의 해시이므로 DB 를 지우고 다시 만들어도 같은 파일이면 결정이 그대로 붙는다.
  **회귀 검사(`regress`)도 결정은 읽는다** — 날짜와 버리기는 무엇을 적재하는가의 일부다. 검수는 지금처럼 읽지 않는다.
  그래서 기준에 든 문서에 결정을 내리면 회귀 수치가 움직인다 (DATA.md 에 적는다).
- **결정은 업무 테이블을 직접 고치지 않는다.** 저장 = 파일에 한 줄 붙이기 → `doc_decision` → 그 문서의 `work_requested` 를 올린다 (4.1). 그 뒤 처리(4.8)가
  그 문서의 행을 지우고 결정을 적용해 다시 만든다. 화면도 명령도 `--fresh` 도 같은 길을 지난다 — 적용하는 곳이 하나다.
- 검수(칸의 값)는 그대로 `reviews.jsonl` 이다. 다시 처리하면 지금처럼 `apply_reviews` 가 다시 붙인다.
- 결정 기록에는 값·이름이 없다. 그래도 현장의 운영 기록이므로 사이트 팩과 같이 저장소 밖에 두고 같이 백업한다. `note` 는 로그에 찍지 않는다.

### 4.4 쪽의 방향은 정합에서 읽고, 바로 세워 다시 정합한다

- 첫 정합의 인라이어가 `MIN_INLIERS` 이상이면 호모그래피의 회전각(`atan2(H[1,0], H[0,0])`)을 90° 단위로 반올림한다.
  0 이 아니면 쪽을 그만큼 **정확히**(`np.rot90`) 되돌려 세우고 다시 정합한다. 쓰는 것은 세운 쪽의 결과다 (통과 여부도 그 결과로).
  동시 판의 묶음(ADR 0018)도 같다: 고른 판의 호모그래피에서 방향을 읽고, 세운 쪽으로 판을 다시 고른다.
- 바로 선 쪽은 정합을 지금과 같은 횟수만 한다 (판이 하나면 한 번). 정합 호출 수를 세는 시험(`tests/test_variants.py`)과 `runner.align_to_template` 을
  바꿔 끼우는 픽스처(`tests/conftest.py`)가 있다 — 함수를 옮기면 같이 고친다.
- 1절 (나): 그대로 두면 값 유무가 16–32칸 달라지고, 세우면 바로 선 쪽과 같다. 그래서 수용 기준은 "정확히 돌린 쪽의 결과 = 바로 선 쪽의 결과"다.
- `doc_page.rotation` 에 0·90·180·270 (시계 방향으로 그만큼 돌리면 바로 선다). 정합하지 않은 쪽(양식 없음·분류 전용)은 NULL.
- **`doc_page.homography` 는 지금처럼 "렌더링한 원래 쪽 → 템플릿"이다** (세우는 회전을 합성해 적는다). 원본 해상도 크롭(`imaging/hires.py`,
  `cropspec`)과 인쇄 층의 다시 펴기(`tools/printlayer.py`)는 방향을 몰라도 그대로 돈다. 다만 돌아간 쪽을 그 호모그래피로 다시 편 그림은
  정합 그림과 화소가 조금 다를 수 있다(보간 자리의 반올림) — 바이트까지 같다는 보장은 바로 선 쪽에만 남는다.
- 세워서 정합하는 일은 한 함수에 둔다. 파이프라인, `template print-layer` 의 직접 정합, `template preview --scan` 이 그것을 쓴다.
  `template variant` 는 자기 호모그래피(표 밖의 특징점으로 구한 것)를 쓰므로 거기서 같은 식으로 방향을 읽어 세운 뒤 다시 한다.
- `template init --rotate 90|180|270`: 돌아간 스캔으로 새 템플릿을 만들 때 기준 이미지를 세워서 적는다. 주지 않으면 지금처럼 들어온 방향 그대로다
  — "바로 선 것"은 기준 이미지의 방향이다.
- 분류는 지금 그대로 한다 (돌아간 쪽 249장이 전부 같은 양식으로 분류되었고 여유는 최소 1.9 였다).
- 쪽 미리보기(`pages --thumbs`)와 화면의 쪽 그림은 방향을 알면 세워서 보여 준다.

### 4.5 빈 쪽은 양식을 못 찾은 쪽 중에서만 가린다

- 분류가 양식을 찾지 못한 쪽에서만 본다: 어두운 화소의 비율(`grid.binarize` → 2 × 2 열기 → 0 이 아닌 화소의 비율)이
  `blank_max_ink`(기본 0.02) 미만이면 `doc_page.status = 'blank'`. 양식을 찾은 쪽은 아무리 옅어도 빈 쪽이 아니다.
- 0.02 의 근거 (1절 라): 실제 쪽의 최소가 0.046, 흰 종이·티·가장자리 그림자가 0.011 이하. 진하게 비친 뒷면(0.028–0.053)은 `unknown_form` 으로
  남는다 — 사람이 본다. 실제 빈 쪽의 표본은 아직 없다 (8절).
- `blank` 는 문서를 `needs_review` 로 만들지 않는다. `report` 에 수가 나온다.
- 끼워 넣은 흰 쪽이 `unknown_form` 이기를 기대하는 시험(`tests/test_archive.py`)은 `blank` 로 고친다.

### 4.6 다시 스캔한 쪽은 붙잡아 두고 사람이 정한다

- **서명**: 정합을 통과한 쪽의 정합 그림 → `grid.binarize` → 인쇄 자리를 0 으로(템플릿에 인쇄 층이 있으면 `Template.print_mask`, 없으면
  `printlayer.mask(기준 이미지)`) → 2 × 2 열기 → 16 × 16 px 칸마다 잉크 화소의 수. **유사도**는 두 서명의 코사인. 서명이 전부 0 이면 비교하지 않는다.
- **순서**: 문서의 순서는 (`intake/` 아래의 문서가 뒤, 보관 경로 — `source_rel`, 없으면 `source_path` — 를 `/` 로 나눈 성분들의 코드포인트 순서,
  `document_id`). 쪽의 순서는 (문서의 순서, 쪽 번호). 파이썬에서 한 함수로 정한다 — SQL 의 `ORDER BY` 에 맡기지 않는다 (DB 마다 글자 순서가 다르다).
  접수한 문서의 보관 폴더 이름은 받은 시각으로 시작하므로(4.7) 받은 순서와 같고, DB 를 지우고 다시 만들어도 같다. 묶음 폴더는 지금 `run` 이 한 폴더를
  도는 순서와 같다 (`Pipeline.expand` 의 경로 정렬 — 글자열 정렬과는 다르다: 성분별로 견준다). 먼저 있던 묶음이 새로 접수한 스캔보다 늘 앞이다.
- **규칙**: 쪽은 같은 날짜, 같은 계열(`family` 가 있으면 그것, 없으면 템플릿 이름)의 **자기보다 앞 순서인 적재된 쪽** 중 가장 비슷한 것과의 유사도가
  `dup_min_sim`(기본 0.80) 이상이면 적재하지 않고 붙잡힌다: `status = 'duplicate'`, `duplicate_of`(그 앞쪽), `duplicate_sim`. 필드도 업무 행도 만들지 않는다.
  문서는 `needs_review` 가 된다. 다른 날의 쪽과는 비교하지 않는다 (1절 다: 다른 날의 다른 종이가 0.84 까지 올라간다).
  0.80 의 근거: 같은 날의 다른 종이 최대 0.66(258쌍), 흔들어 다시 정합한 같은 종이 최소 0.91(83쪽) — 그 사이.
- **처리한 순서와 상관없어야 한다.** 규칙이 "앞 순서의 적재된 쪽"이므로, 문서 X 를 처리한 뒤(버리기·날짜 바꾸기 포함) X 때문에 판정이 달라질 수 있는
  **뒤 순서의** 문서에 다시 처리를 요청한다(4.1 의 요청 번호): ① X 의 쪽(지우기 전의 것 포함)과 같은 날짜·계열에 `duplicate` 인 쪽이 있는 문서
  (붙잡힌 쪽은 서명이 없어 무엇과 가장 비슷한지 다시 재야 안다), ② X 의 적재된 쪽과 같은 날짜·계열이고 유사도가 기준 이상인 적재된 쪽(`keep` 이 없는 것)이
  있는 문서. 요청은 뒤로만 가므로 끝난다. 대기 중인 문서는 문서의 순서대로 처리한다. `run` 도 준 경로를 다 돈 뒤 대기 중인 문서를 마저 처리한다.
- 붙잡는 쪽으로 틀리는 것이 두 번 들어가는 것보다 낫다: 붙잡힌 쪽은 화면에 뜨고 사람이 한 번 누르면 풀린다. 두 번 들어간 값은 아무도 모른다.
- 사람이 정하는 것은 셋이고 전부 4.3 의 결정이다 (앞쪽 = 먼저 들어온 쪽, 뒤쪽 = 붙잡힌 쪽):

  | 화면의 선택 | 결정 |
  |---|---|
  | 같은 종이다 — 뒤쪽을 버린다 | 뒤쪽에 `discard` |
  | 같은 종이다 — 앞쪽을 버리고 뒤쪽을 쓴다 (앞쪽이 걸린 스캔일 때) | 앞쪽에 `discard` |
  | 다른 종이다 — 둘 다 쓴다 | 두 쪽 모두에 `keep` |

- `keep` 이 있는 쪽은 비교 없이 적재한다. 그 쪽의 서명은 남아 뒤에 오는 쪽의 비교 대상이 된다. 앞쪽을 버리면 뒤쪽은 더 걸릴 것이 없어 적재된다 (①).
  규칙만 보면 뒤쪽의 `keep` 하나로 충분하다 (`doc keep <붙잡힌 쪽>`). 화면은 두 쪽 모두에 적는다 — 보관 폴더를 정리해 순서가 바뀌어도 풀린 채로 남게.
- 서명은 `doc_page_sig` 에 적재된 쪽만 남긴다 (쪽마다 2만 자 안팎의 글자열 — `doc_page` 에 넣지 않는다).
- 기준 이미지로 쓴 그 종이 자신은 서명이 0 에 가깝다(자기 손글씨가 인쇄 자리로 지워진다) — 그 한 장은 다시 스캔해도 잡지 못한다. 그대로 둔다.

### 4.7 접수 폴더: 다 쓰인 파일만 가져오고, 지우지 않는다

- 설정 `[paths] inbox` (또는 `MINEDOCSCAN_INBOX`). 스캐너 프로그램의 저장 폴더를 그대로 가리킨다. `archive_root` 가 없으면 감시를 시작하지 않는다.
  접수 폴더가 `archive_root`·`work_root`·사이트 팩의 안이거나 그것들을 품으면 거절한다.
- 보는 것: 접수 폴더와 그 하위 폴더의 `SUPPORTED_EXT` 파일. `_` 로 시작하는 폴더, `.`·`~` 로 시작하는 파일은 보지 않는다.
- **다 쓰인 파일만** — 기억 없이 파일만 보고 정한다 (`--once` 를 여러 번 돌려도 같게): 수정 시각이 지금보다 `settle_seconds`(기본 5) 이상 앞이고, 열린다
  (PDF 는 복구 없이, 이미지는 디코딩). 열리지 않으면 다음 바퀴에 다시 보고, 수정 시각이 `give_up_seconds`(기본 120) 이상 앞인데도 그러면
  지금의 손상 방침(`damaged_pdf`)대로 등록한다 (`fail` 이면 그 문서는 `failed`). 두 값은 `watch` 의 선택으로도 준다 (`--settle-seconds 0` — 시험과 합성 시나리오용).
  계속 도는 `watch`·`serve` 는 하나를 더 본다: 지난 바퀴에 잰 크기와 같아야 한다 (수정 시각을 옛것 그대로 두고 복사하는 프로그램이 있다).
- **접수**: 해시 → 이미 있는 문서(같은 바이트)면 `<inbox>/_already/` 로 옮기고 DB 는 건드리지 않는다. 새 문서면 보관 폴더로 복사하고 해시를 다시 확인한 뒤
  접수 폴더의 것을 치운다: `archive_root/intake/<받은 해-달>/<받은 시각>-<document_id>/<원래 파일명>`.
  받은 시각은 UTC, 폭이 고정된 `YYYYMMDDThhmmssfffZ` (해-달 폴더도 UTC). 한 바퀴 안에서는 (수정 시각, 이름) 순서로 접수하고, 받은 시각이 지금까지 접수한
  것 중 가장 늦은 것(DB 에서 읽는다)보다 늦지 않으면 그것의 1 ms 뒤로 민다 — 같은 바퀴에 들어온 파일의 순서도, 시계가 뒤로 간 뒤의 순서도 폴더 이름에 남는다
  (4.6 의 문서의 순서).
  복사는 `SUPPORTED_EXT` 가 아닌 임시 이름으로 쓰고 이름을 바꾼다. 그 뒤 문서를 등록한다(4.1): `source_name` = 원래 파일명에서 확장자를 뺀 것,
  `source_rel`, `received_at`. 커밋.
- `archive_root` 는 지금까지 읽기만 하는 곳이었다. 이제 그 아래 `intake/` 에만 쓴다 — 그 밖은 여전히 읽기만 한다 (`config.py` 와 문서의 설명을 고친다).
- 읽을 수조차 없는 파일(잠겨 있다)은 그대로 두고 다시 본다. `give_up_seconds` 뒤에도 그러면 `<inbox>/_failed/` 로 옮기고 요약에 알린다.
  `_already`·`_failed` 안에서 이름이 겹치면 문서 ID 나 번호를 붙인다 — 덮어쓰지 않는다.
- **지우지 않는다.** 접수 폴더에서 사라진 파일은 보관 폴더, `_already`, `_failed` 중 한 곳에 바이트 그대로 있다.
- 감시는 폴링이다 (`poll_seconds` 기본 3). 한 바퀴 = 접수 폴더를 훑어 접수 → 대기 중인 문서(4.1)를 문서의 순서대로 처리(4.8).
  접수 폴더가 설정되어 있지 않으면 `watch --once` 는 대기 중인 문서만 처리한다.
- **`source_name` 은 더 이상 문서마다 하나가 아니다** — 스캐너는 같은 이름을 다시 쓴다. 문서를 가리키는 것은 `document_id` 다.
  라벨(`labels/pages.json`)과 정답 파일은 파일명으로 찾으므로 이름이 겹치면 두 문서에 같이 붙는다 — 날짜 있는 묶음 폴더를 위한 것이니 접수한 문서에는
  쓰지 말라고 DATA.md 에 적는다 (사람에게 하는 안내다. 코드는 접수한 문서를 따로 가리지 않는다 — 라벨이 있으면 지금처럼 붙는다).
  미리보기 파일 이름(`tools/thumbs.py`)에는 문서 ID 를 넣어 겹치지 않게 한다.
- 잘린 파일이 `failed` 문서로 남은 뒤 온전한 파일이 오면 그것은 새 문서다 (해시가 다르다). 실패한 문서는 목록에 남고, 화면에서 버린다.
- 이미지 파일도 받지만 파일 하나가 문서 하나다 — 쪽마다 파일이 나오는 설정이면 날짜를 파일마다 정해야 한다. 스캐너는 PDF 로 저장하게 한다 (8절).

### 4.8 처리: 지우고 다시 만든다, 쪽마다 커밋한다

- `process_document(document_id)`:
  1. 원본을 찾는다 (`resolve_source`). 닿지 않으면(네트워크 드라이브가 끊겼다) 그 문서를 건드리지 않고 다음 바퀴에 다시 본다 — 요약에 알린다.
  2. 그 문서가 만든 것을 지운다 (자식부터): 쪽을 가리키는 업무 행(`prod_haul`, `prod_tally`, `eq_usage_daily`, `xcheck_usage`, `insp_daily`),
     `doc_page_sig`, `doc_page_meta`, `doc_field`, `doc_page`. `doc_review` 와 `doc_decision` 은 지우지 않는다.
     쪽을 가리키는 테이블의 목록은 `store/db.py` 에 `PRIMARY_KEYS` 옆에 둔다 — 새 업무 테이블을 더할 때 같이 고친다.
     문서의 상태는 이때 `received` 가 된다 (끊기면 다시 처리된다).
  3. 버린 문서면 `discarded`, 날짜가 없으면 `needs_date` — 4번을 건너뛰고 5번으로 간다 (지운 것만큼 다시 계산하고 뒤 문서에 요청한다).
  4. 쪽마다: 결정(쪽의 날짜·버리기·`keep`) → 분류 → 정합(4.4) → 빈 쪽(4.5) → 다시 스캔(4.6) → 핸들러. 버린 쪽은 `status = 'discarded'` 로만 남는다.
  5. 그 문서의 쪽이 있던 날짜(지우기 전과 뒤)와 장비에 대해 교차검증·배차 관측·검산을 다시 계산한다. 쪽이 하나도 남지 않은 날짜의 `xcheck_haul`·
     `eq_assignment_obs` 는 지워져야 한다 (지금의 `crosscheck_haul` 은 행이 남은 날짜만 돈다). 그 문서의 상태를 정하고 `work_done` 을 적는다.
- 5번을 위해 핸들러의 마무리(`FormHandler.finalize`)가 날짜(와 장비)를 받게 넓힌다. 등록된 핸들러 전부에 대해 부른다 — 지금의 `Pipeline.finalize` 는
  이번 프로세스에서 쪽을 적재한 핸들러만 돈다 (버리기만 한 처리에서는 아무것도 다시 계산되지 않는다).
  지금의 서명으로 부르는 곳(시험 포함: `finalize(con, site, settings)`, `process_page`, `_document_row`)이 그대로 돌게 새 인자는 기본값을 둔다.
- **순서를 고정한다.** 같은 내용의 DB 가 같은 결과를 내려면 행이 들어간 순서에 기대면 안 된다:
  - `validate/crosscheck._crosscheck_date` 는 `prod_haul` 을 순서 없이 읽고, 자리 배정(`assign_slots`)은 먼저 나온 쪽에 자리를 준다 →
    쪽의 순서(4.6)로, 한 쪽 안에서는 필드의 자리(`doc_field.row_no`, `x0`) 순서로 읽는다 (`prod_haul` 에는 `page_id` 와 `source_field_id` 뿐이라
    `doc_page`·`doc_document`·`doc_field` 를 이어서 읽고 파이썬에서 정렬한다 — 행렬 쪽 안의 행 순서가 자리 사전의 순서가 된다).
    지금의 `run` 이 그 순서로 넣으므로 결과는 그대로여야 한다 (합성과 실데이터 회귀로 확인).
  - `validate/usage._order` 의 끝에 쪽 ID 를 더한다 (`source_name` 이 겹칠 수 있다).
  - `insp_daily` 는 날짜:장비가 키라 같은 날의 두 쪽이 같은 장비를 적으면 나중에 넣은 쪽이 이긴다. 규칙을 "쪽의 순서가 뒤인 쪽이 이긴다"로 고정하고
    (적재는 지금의 `run` 과 같다), 쪽을 지우거나 더한 뒤에는 그 날짜의 점검 행을 남은 쪽들의 최종 필드 행에서 다시 만든다. `insp_daily` 에 `page_id` 를 더한다
    (`source_field_id` 는 비고 열이 없는 템플릿에서 NULL 이다). 검수도 같은 규칙을 따른다: 지금의 `InspectionHandler.on_review` 는 검수한 칸이 어느 쪽의 것이든
    그 날짜:장비의 행을 그 쪽의 값으로 다시 쓴다 — 이기는 쪽(행의 `page_id`)의 칸을 검수했을 때만 고친다.
- **불변식**: 문서를 몇 번을 어떤 순서로 다시 처리하든, 지금의 DB = 같은 파일·같은 검수·같은 결정으로 처음부터 만든 DB.
  비교에서 빼는 것: 시각(`created_at`, `received_at`, `reviewed_at` …), 요청 번호, 경로(`source_path`), 그리고 `eq_equipment`
  (장비 마스터는 템플릿에서 오는 것이라 쪽을 지워도 남는다).
- **쪽마다 커밋한다.** 지금은 문서 하나가 한 트랜잭션이라(30쪽에 30–70초) 그동안 화면의 저장이 기다린다. 쪽 하나가 한 트랜잭션이 되면
  기다림은 1–2초다. 문서를 읽다 실패하면 롤백 대신 그 문서의 행을 지우고 `failed` 로 남긴다 — 끝난 모습은 지금과 같다 (그 문서의 쪽·필드·업무 행 0).
- SQLite 파일은 WAL 로 열고 `busy_timeout` 을 준다 (30초). **쓰는 트랜잭션은 `BEGIN IMMEDIATE` 로 시작한다** (`store/db.py` 에 도우미 하나) —
  읽고 나서 쓰기로 올라가는 트랜잭션은 다른 연결이 그 사이에 커밋하면 기다리지 않고 바로 실패한다. `review/store.save` 와 결정의 저장은 읽는 것부터
  그 안에서 한다 (지금 `save` 는 필드 행을 트랜잭션 밖에서 읽는다). `crosscheck_haul` 안의 커밋처럼 가운데에서 끊는 커밋이 쪽 단위를 깨지 않게 한다.
  `--fresh` 는 `-wal`·`-shm` 도 같이 지운다. `WORK_ROOT` 는 지금처럼 로컬 디스크.
- 다시 처리하는 동안 그 문서의 칸은 잠깐 없는 필드다. 그때 그 칸의 검수를 저장하면 "없는 필드"로 거절된다 — 화면은 잠시 뒤에 다시 하라고 알린다.

### 4.9 운영 화면: 한 프로세스, 스레드 둘, 127.0.0.1

- `minedocscan serve --reviewer ID [--port 8765] [--no-watch]`. 작업 스레드가 4.7 의 바퀴를 돌고, 화면 스레드는 지금의 단일 스레드 서버다.
  **연결은 스레드마다 하나**, 파이프라인은 작업 스레드만 돈다. 화면 스레드의 쓰기는 검수 저장과 결정 저장뿐이다.
- **PyMuPDF 는 여러 스레드에서 같이 쓰면 안 된다.** 작업 스레드는 쪽을 렌더링하고(`imaging/io.load_pages`) 화면 스레드도 크롭과 쪽 그림을 렌더링한다
  (`hires.render_source`). `imaging/io.py` 의 잠금 하나로 PyMuPDF 를 부르는 곳을 전부 감싼다 (열기·쪽 꺼내기·렌더링·닫기). `load_pages` 는 쪽을 내주는
  동안(`yield`)에는 잠금을 놓는다 — 문서 하나를 다 읽을 때까지 잡고 있지 않는다.
- 주소:
  - `/` (질의 없음) → 홈. `/?name=<대기열>` → 지금의 검수 화면 그대로. `/doc?id=<document_id>` → 문서 화면.
    (`review serve --queue X` 에서는 지금처럼 `/` 가 그 대기열이다.)
  - `GET /api/home`, `GET /api/doc?id=`, `POST /api/decision {items: [{target, kind, value, note}]}` (전부 검사한 뒤에 쓴다)
  - `GET /page.png?page_id=…` 또는 `?doc=…&page=N` (`w` 로 폭). 원본에서 그때그때 렌더링한다 (몇 장만 캐시, 디스크에 쓰지 않는다).
- **홈**: 할 일(날짜를 정할 문서, 다시 스캔 의심 쪽, 양식 없는 쪽·정합 실패 쪽, 운영 대기열마다 남은 수 — 누르면 그 대기열로), 최근 문서 50건
  (받은 시각, 파일명, 쪽 수, 날짜, 상태, 다시 처리 대기), 작업 상태(쉬는 중 / 어느 문서의 몇 쪽째). 5초마다 다시 읽는다.
  - 운영 대기열은 `pending`(양식별)·`mismatch`·`readings`·`usage-check`·`meta-check`·`page-fields`. 표본 대기열(`haul-numbers`·`checks`)은 홈에 두지 않는다.
  - 홈을 읽을 때마다 대기열을 통째로 만들지 않는다 (`queue_progress` 는 대기열 전부를 만든다 — 5초마다 부르면 저장이 막힌다).
    남은 수의 뜻은 대기열이 정한다: `build_queue(이름)` 의 `total − done` (`pending` 은 `total`). 한 번 세어 두고 DB 가 바뀔 때(쪽 처리·검수 저장·결정 저장)만 다시 센다.
- **문서 화면**: 쪽 목록(세운 미리보기, 양식, 상태, 날짜). 문서의 날짜 입력(키보드: 숫자 넣고 Enter), 문서 버리기·되살리기, 쪽 버리기·되살리기,
  "이 쪽은 다른 날짜", 다시 스캔 의심 쪽은 두 쪽을 나란히 놓고 4.6 의 세 선택. `needs_date` 문서는 쪽 행이 없으므로 원본의 쪽을 그대로 보여 주고
  화면에서 돌려 볼 수 있게 한다 (방향을 아직 모른다).
- 결정을 저장하면 화면은 "다시 처리 대기"를 보여 주고, 작업 스레드가 다음 바퀴에 처리한다. `--no-watch` 이면 결정은 남고 처리는 `watch` 가 한다
  — 화면이 그렇게 알린다.
- 지금의 규칙 그대로: 127.0.0.1 에만, Host·Origin·Content-Type 검사, `Cache-Control: no-store`, 서버 로그에는 경로와 상태 코드만.
- `review serve --queue X` 는 그대로 남는다 (정답을 만드는 표본 대기열: `--n`, `--seed`, `--audit`). 검수 화면에 "홈으로"만 더한다.
- 화면은 한 장짜리 HTML 을 하나 더 두는 정도로 (`review/static/`). 프레임워크·빌드 없이.

### 4.10 스키마 버전 8

스키마 8 의 전부를 단계 1 에서 넣는다 (뒤 단계가 쓸 열과 테이블까지 — 버전은 한 번만 오른다).

- `doc_document`: 상태에 `needs_date`·`discarded`, `received_at`(등록한 시각 — 다시 처리해도 바뀌지 않게 `upsert` 가 덮어쓰지 않는다. 접수한 문서는
  보관 폴더 이름의 시각에서 다시 읽을 수 있다), `date_source`(`decision`·`label`·`filename`), `work_requested`, `work_done`.
- `doc_page`: 상태에 `blank`·`duplicate`·`discarded`, `rotation`, `duplicate_of`(외래 키를 걸지 않는다 — 가리키는 쪽이 먼저 지워질 수 있다), `duplicate_sim`.
- `insp_daily`: `page_id`.
- 새 테이블 `doc_decision`(결정 기록의 사본), `doc_page_sig`(`page_id`, 계열, 날짜, 서명).
- `update_document_status`: `duplicate` 인 쪽이 있으면 `needs_review`. `blank`·`discarded` 는 아니다 (4.1 — `processed`·`needs_review` 사이에서만).
- SQLite 와 PostgreSQL 에서 같이 도는 문법만 (서명은 글자열로). 마이그레이션은 없다 (ADR 0005). 예전 DB 는 `--fresh`.

## 5. 단계

### 단계 1 — 스키마 8, 쪽의 방향과 빈 쪽

할 일
- 스키마 8 (4.10).
- 세워서 정합하는 함수 (4.4). `pipeline/runner.py` 가 쓰고, `doc_page.rotation` 과 합성한 호모그래피를 적는다.
  `template print-layer` 의 직접 정합, `template preview --scan`, `template variant`, `template init --rotate`.
- 빈 쪽 (4.5): `[pipeline] blank_max_ink`. 근거를 주석으로.
- `tools/thumbs.py`: 방향을 아는 쪽은 세워서, 파일 이름에 문서 ID.
- `report`: 방향별 쪽 수(0 이 아닌 것), 빈 쪽 수. `pages --status blank`, `pages --rotated`.
- 합성: 쪽을 90° 단위로 돌려 넣는 선택과 빈 뒷면(흰 종이·티·가장자리 그림자)을 끼우는 선택. 난수는 따로 써서 기본 합성 묶음의 바이트가 바뀌지 않게.

수용 기준
- **무손실 그림으로**: 합성 쪽(운반·점검표·가동 일보·동시 판에서 한두 쪽씩)을 PNG 문서로 넣은 것과, 그 그림을 `np.rot90` 으로 1·2·3번 돌린 PNG 문서로 넣은 것의
  `doc_field` 기계 값 열(`ink`, `has_value_raw`, `value_raw`, `status_raw`, 좌표)과 업무 테이블이 같다 (문서 ID 가 다르므로 쪽 번호와 필드 이름으로 맞춰 비교).
  `rotation` 이 맞게 적힌다. (합성 PDF 는 쪽을 JPEG 로 담아서 돌린 뒤에 담으면 화소가 달라진다 — 정확히 같다는 비교는 PNG 로만 한다.)
- 돌린 쪽을 담은 합성 PDF, 그리고 돌린 뒤에 흔들기(`scan_effect`)를 건 쪽 — 정확한 90° 가 아닌 것 — 도 전부 `loaded` 이고 방향이 맞게 읽힌다.
  값 유무가 바로 선 것과 달라진 칸의 수를 보고한다.
- 돌아간 쪽의 원본 해상도 크롭이 바로 선 쪽의 크롭과 같은 칸을 보여 준다 (같은 크기, 화소 차이의 평균 2 이하 — 바이트는 요구하지 않는다).
- 빈 뒷면은 `blank` 이고 그 문서는 그것 때문에 `needs_review` 가 되지 않는다. 손글씨가 없는 빈 양식은 `blank` 가 아니다 (분류가 먼저다).
- 바로 선 쪽의 정합 횟수가 그대로다. 기본 합성 묶음의 파일 바이트, 인쇄 층이 없는 템플릿의 결과, `null` 리포트의 지금 있는 항목이 그대로다.

### 단계 2 — 날짜 없는 문서, 결정 기록, 다시 처리

할 일
- `intake/decisions.py`: 결정 하나(`Decision`), 파일에 붙이기, 읽기, `doc_decision` 으로 읽어 들이기, 유효한 결정 고르기, 저장(4.3).
  `review/store.py` 와 같은 모양으로. `intake/dates.py`: 날짜 읽기 (4.2).
- 날짜의 순서를 한 곳으로 (4.2): `SitePack.page_meta`, `pagemeta.human_values`·`refresh_page`, 출처 `decision`.
- `pipeline/runner.py`: 등록과 처리를 나눈다 (4.1), `needs_date`, 요청 번호, 지우고 다시 만들기와 쪽마다 커밋 (4.8), 날짜·장비를 받는 마무리,
  한 번에 하나만 도는 잠금. `store/db.py`: 쪽을 가리키는 테이블의 목록, WAL, `BEGIN IMMEDIATE` 도우미.
- 순서 고정 (4.8): 교차검증, 계기의 연속성, 점검표.
- 명령: `doc list|date|discard|restore|keep`. `--reviewer` 가 없으면 결정을 저장하지 않는다 (검수와 같다). `watch --once` 의 처리 부분(대기 중인 문서) —
  접수 폴더는 단계 4.
- `report`: 날짜를 정할 문서 수, 다시 처리 대기 문서 수, 버린 문서·쪽 수, 날짜의 출처별 문서 수. `minedocscan info`: 결정 파일의 경로와 줄 수.
- 날짜 없는 이름으로 도는 기존 시험은 날짜 있는 이름·라벨·결정으로 고친다. 열리지 않는 파일의 시험(`tests/test_archive.py` 의 쓰레기·빈 PDF)은 그대로
  통과해야 한다 — 등록이 먼저 실패한다 (4.1). 무엇을 왜 고쳤는지 보고한다.

수용 기준
- 날짜 규칙에 맞지 않는 이름의 합성 묶음: `needs_date`, 쪽·필드·업무 행 0, 종료 코드 0, 요약에 한 줄, `doc list` 에 쪽 수가 나온다.
  `doc date` → `watch --once` 뒤의 DB 가 같은 파일을 날짜 있는 이름으로 처음부터 돌린 것과 같다 — 두 쪽 다 라벨이 없는 사이트 팩으로 비교한다
  (라벨은 파일명으로 찾으므로 이름이 다르면 붙지 않는다). `source_name`·`source_path`·`source_rel`·`date_source`·시각은 뺀다.
- 어느 실행 뒤에도 업무 테이블에 `work_date` 가 NULL 인 행이 없다.
- 날짜를 다른 날로 바꾸면 옛 날짜의 교차검증·배차 관측·계기의 연속성이 그 문서 없이 계산한 것과 같고(쪽이 하나도 안 남은 날짜의 행은 사라진다),
  새 날짜에는 그 문서가 들어 있다.
- `discard` 한 문서의 행이 0 이고 나머지는 그 문서 없이 돌린 것과 같다. `restore` 하면 원래와 같다. 쪽에 건 `discard`·`date` 도 같다.
- 메타 필드(차량번호)를 검수한 뒤에도 결정으로 정한 날짜가 그 쪽의 `doc_page_meta` 와 업무 행에 남아 있다.
- **4.8 의 불변식**: 2–3쪽짜리 합성 묶음 몇 개에서 결정과 검수를 섞어 수십 번 넣고(날짜 바꾸기 — 다른 문서가 있는 날짜로도, 버리기, 되살리기, 칸 검수)
  그때마다 처리한 DB 가 처음부터 만든 DB 와 같다. 같은 날짜에 일보 두 문서·점검표 두 쪽이 있는 경우를 넣는다. 0001 의 불변식 시험에 더한다.
- 처리하는 도중에 온 결정이 사라지지 않는다 (요청 번호). 검수를 저장해도 `needs_date`·`discarded`·`received` 가 바뀌지 않는다.
- `--fresh` 뒤에 결정이 그대로 붙는다. 결정 파일의 앞줄이 바뀌거나 사라지지 않는다 (추가 전용). 달력에 없는 날짜·모르는 대상·없는 쪽 번호는 거절되고
  파일에 남지 않는다. 받은 날보다 뒤의 날짜는 경고와 함께 저장된다.
- 쪽마다 커밋: 문서를 처리하는 도중에 다른 연결에서 앞쪽의 행이 보인다 (쪽이 끝날 때 부르는 훅으로 시험 — 시간을 재지 않는다).
- 문서를 읽다 실패하면 그 문서의 행이 0 이고 `failed` 다. 처리 도중 끊고(`received` 인 채로) 다시 처리하면 한 번에 돌린 것과 같다.
- 파이프라인을 도는 둘째 프로세스는 시작하지 않고 한 줄로 알린다. 첫째가 죽은 뒤에는 시작한다.
- 교차검증의 순서를 고정한 뒤 합성 묶음의 교차검증 수가 그대로다.

### 단계 3 — 다시 스캔한 쪽

할 일
- 서명과 유사도 (4.6): `imaging/` 에 순수 함수로 (DB 를 모른다). `doc_page_sig`. `[pipeline] dup_min_sim`. 근거를 주석으로.
- `pipeline/runner.py`: 앞 순서의 쪽과 비교, 붙잡기, `keep`, 뒤 문서에 다시 처리 요청 (①②). `report`: 붙잡힌 쪽의 수와 유사도의 분포(최소·중앙·최대).
  `pages --status duplicate`.
- 합성: 같은 쪽을 다른 흔들기로 두 번 찍는 선택.

수용 기준
- 같은 합성 쪽을 다른 씨앗의 `scan_effect` 로 찍어 다른 파일로 넣으면 뒤 순서의 것이 `duplicate` 이고 `duplicate_of` 가 앞의 것이다. 업무 행은 한 번만 있다.
  JPEG 로 다시 압축한 것, 90° 돌려 넣은 것도 잡힌다.
- 같은 날의 다른 종이(다른 차량의 일보, 같은 장비의 둘째 장, 동시 판의 다른 판)는 붙잡히지 않는다. 다른 날의 쪽과는 비교하지 않는다
  (같은 값·같은 필체로 만든 다른 날의 쪽이 붙잡히지 않는다).
- **처리 순서와 무관하다**: 두 문서를 어느 쪽부터 처리하든, 앞 문서를 뒤늦게 다시 처리하든(날짜 바꾸기·되살리기), DB 가 문서의 순서대로 처음부터 만든 것과 같다.
  앞 문서를 버리거나 다른 날짜로 옮기면 붙잡혀 있던 뒤쪽이 풀려 적재된다.
- 4.6 의 세 선택이 각각 맞게 적재된다: 뒤쪽을 버리면 앞쪽만, 앞쪽을 버리면 뒤쪽만, 다른 종이면 둘 다. 그 뒤 `--fresh` 로 다시 만들어도 같다.
- 단계 2 의 불변식 시험에 다시 스캔한 쪽이 있는 묶음을 더한다.
- 지금의 합성 묶음 전부(기본, `--low-cells`, `--meta-fields`, `--usage-logs`, 동시 판)에서 붙잡힌 쪽이 0 이고 리포트의 지금 있는 수가 그대로다.
- 합성에서 잰 두 분포를 보고한다 (같은 날 다른 종이의 최대, 다시 찍은 쪽의 최소). 그 사이가 0.80 을 품지 못하면 멈추고 묻는다.

### 단계 4 — 접수 폴더

할 일
- `intake/inbox.py`: 훑기, "다 쓰였는가", 접수(복사·확인·치우기), `_already`·`_failed` (4.7). 시계는 주입한다 — 시험에서 잠들지 않는다.
- `minedocscan watch [--once] [--settle-seconds N] [--give-up-seconds N]`. 설정 `[paths] inbox`, `[intake] settle_seconds`·`poll_seconds`·`give_up_seconds`,
  `MINEDOCSCAN_INBOX`. `info` 에 접수 폴더.
- `watch`·`serve` 의 요약과 로그에는 수와 문서 ID 만 낸다. 파일명은 `doc list` 와 화면에서 본다 (`run`·`report` 가 지금 내는 것은 그대로 둔다).

수용 기준
- 수정 시각이 `settle_seconds` 안인 파일은 건드리지 않는다. 지나면 접수한다. `--once` 를 두 번 돌려도 한 번 돌린 것과 같다.
- 잘린 PDF 는 `give_up_seconds` 뒤에 `failed` 문서가 되고(`damaged_pdf = "fail"`), 접수 폴더에 남지 않는다. 뒤에 온전한 파일이 오면 새 문서로 접수된다.
- 같은 바이트의 파일은 `_already` 로 가고 DB 가 변하지 않는다. 이름이 겹쳐도 덮어쓰지 않는다.
- 한 바퀴 뒤 접수 폴더(`_` 폴더 밖)가 비어 있고, 넣은 파일 전부가 보관 폴더·`_already`·`_failed` 중 한 곳에 바이트 그대로 있다.
- 원래 파일명이 `source_name` 에 남고 파일명 규칙이 그것에 걸린다. 접수 폴더의 하위 폴더에 든 파일, 한글 이름의 파일도 접수된다.
  같은 이름의 다른 파일 둘이 두 문서가 된다.
- 접수만 하고 끊은 뒤(`received`) 다시 `watch --once` 하면 결과가 한 번에 돌린 것과 같다. 보관 폴더로 복사하다 끊긴 임시 파일은 문서가 되지 않는다.
- DB 를 지우고 보관 폴더를 `run` 으로 다시 돌린 DB 가 접수로 만든 DB 와 같다 (문서의 순서가 같다 — 4.6).
- 하루치를 두 파일로 나눠 넣은 결과가 한 파일일 때와 같다 (1절 마 — 쪽 번호가 달라지므로 내용으로 비교한다).
- 접수 폴더가 `archive_root` 안이면 시작하지 않고 한 줄로 알린다.

### 단계 5 — 운영 화면

할 일
- `minedocscan serve` (4.9). 화면의 처리부는 지금의 `ReviewApp` 처럼 HTTP 없이 부를 수 있게 둔다.
- 홈, 문서 화면, `POST /api/decision`, `/page.png`. 검수 화면에 "홈으로". PyMuPDF 잠금.
- 작업 스레드의 상태(쉬는 중·처리 중인 문서와 쪽)를 화면이 읽는다. 작업 스레드의 예외는 그 문서를 `failed` 로 남기고 다음 바퀴를 돈다 — 스레드가 죽지 않는다.

수용 기준
- 홈의 수가 DB 와 같다 (날짜를 정할 문서, 의심 쪽, 운영 대기열마다 남은 수). 홈을 읽는 것이 표본 대기열을 만들지 않는다.
- 날짜 결정을 보내면 결정 파일에 한 줄이 붙고 문서가 다시 처리 대기가 되며, 작업 한 바퀴 뒤 쪽이 적재되어 있다. 달력에 없는 날짜는 400 이고 파일에 남지 않는다.
  여러 결정을 보냈는데 하나가 틀리면 아무것도 남지 않는다.
- 의심 쪽의 세 선택이 단계 3 과 같은 결과를 낸다. 문서·쪽 버리기와 되살리기도.
- `/page.png` 가 세운 그림을 준다 (돌아간 합성 쪽에서 바로 선 쪽과 같은 방향).
- 다른 출처의 POST 는 403, JSON 이 아닌 본문은 415 (지금의 검사 그대로). 서버 로그에 파일명·날짜·메모가 없다.
- 작업 스레드가 문서를 처리하는 중에 화면 스레드의 검수 저장과 크롭 요청이 성공한다 (두 연결, WAL, PyMuPDF 잠금).
- 브라우저에서 직접: 합성 접수 폴더에 파일을 넣고 홈에 뜨는 것, 날짜 입력, 의심 쪽 풀기, 대기열로 갔다가 홈으로 오는 것. 한 것과 못 한 것을 보고한다.

### 단계 6 — 합성 접수 시나리오, 문서

할 일
- `minedocscan synth OUT --intake`: `OUT/inbox/` 에 다음을 만든다 (같은 seed 면 바이트까지 같다). 무엇이 어떻게 되어야 하는지(접수 순서, 문서·쪽의 상태,
  넣을 결정)는 `truth.json` 에. 사이트 팩의 라벨은 이 파일들의 이름으로 만든다. 접수 순서가 정해지게 파일의 수정 시각을 아래 번호 순서로 적는다 (`os.utime`).
  이 묶음의 PDF 는 쪽을 무손실로 담는다 — 돌린 쪽이 바로 선 쪽을 정확히 돌린 것이어야 아래의 비교가 선다 (단계 1). 견줄 묶음(네 날의 하루치를 바로 선 것·
  날짜 있는 이름·빈 쪽 없이)도 같은 화소로 `OUT/baseline/` 에 같이 만든다. `truth.json` 의 결정은 날짜와 버리기뿐이다 (5번의 쪽은 버린다).
  1. 첫날: 날짜 있는 이름의 하루치, 바로 선 것
  2. 둘째 날: 하루치를 두 파일로 — 둘째 파일은 90° 돌려서
  3. 셋째 날: 날짜 규칙에 맞지 않는 이름의 하루치 (`scan0003.pdf`)
  4. 넷째 날: 양면으로 찍은 하루치 (쪽마다 빈 뒷면)
  5. 첫날의 몇 쪽을 다시 스캔한 파일 (다른 흔들기, 첫날의 날짜가 든 이름)
  6. 1번과 바이트가 같은 파일 (다른 이름)
  7. 가운데에서 잘린 PDF
- 10절의 문서. 깨끗한 환경에서 `pip install .` → `pytest`, 그리고 합성 접수 폴더로 2절의 명령을 처음부터 끝까지
  (`watch --once --settle-seconds 0 --give-up-seconds 0` → `doc list` → `doc date` → `watch --once` → `doc discard` → `watch --once` → `report`).

수용 기준
- `--intake` 묶음을 `watch --once` 와 `truth.json` 의 결정으로 끝까지 처리하면 문서와 쪽의 상태가 `truth.json` 과 같고, 업무 테이블이
  `OUT/baseline/` 을 `run` 한 것과 내용으로 같다 (문서 ID·쪽 번호·경로가 다르므로 날짜·양식·필드 이름으로 맞춰 비교한다).
- 지금의 `synth` 선택들(없음, `--low-cells`, `--meta-fields`, `--mix-pages`, `--usage-logs`, `--print-layers`, `--usage-variants`)의 출력 바이트가 그대로다.

## 6. 시험

- 전부 합성 데이터. 실제 문서의 이미지·이름·장비 번호·파일명을 테스트에 넣지 않는다.
- 기본 `pytest`(torch 없음)는 OpenCV 5.0 과 하한 판에서 통과하고, 시간은 지금의 1.25배를 넘지 않는다. 새 파이프라인 실행은 세션 픽스처로 같이 쓴다.
  돌린 쪽의 비교는 양식마다 한두 쪽으로, 불변식 흔들기는 2–3쪽짜리 묶음으로. 그래도 넘으면 무거운 흔들기를 표시(`-m`)로 떼어 CI 의 작업 하나로 돌리고 보고한다.
- 시험에서 잠들지 않는다 (시계를 주입한다). 스레드를 쓰는 시험은 단계 5 의 하나뿐이고, 시간을 재지 않고 순서로 확인한다.
- 접수 폴더·보관 폴더·결정 파일·검수 파일은 전부 `tmp_path` 로.
- 고쳐야 하는 기존 시험이 있다 (4.2 의 ISO 가 아닌 라벨 날짜, 4.4 의 정합 호출 수와 바꿔 끼우는 픽스처, 4.5 의 흰 쪽, 날짜 없는 이름으로 도는 시험,
  DB 를 통째로 비교하면서 `created_at` 만 빼는 시험). 기대를 바꾼 시험은 목록으로 보고한다 — 통과시키려고 뜻을 바꾸지 않는다.
- 윈도우에서 다른 것: 열려 있는 파일은 옮길 수 없다, 경로에 한글이 있다. 파일을 옮기는 코드는 실패를 "다음 바퀴에 다시"로 받고, 한글 이름의 합성 파일을 시험에 넣는다.
- 마지막에 깨끗한 환경에서 한 번 (단계 6).

## 7. 지켜야 할 것

- **원본을 지우지 않는다.** 접수 폴더에서 치우는 것은 보관 폴더의 사본을 해시로 확인한 뒤에만. `archive_root` 에는 `intake/` 아래에만 쓴다.
- 결정 파일과 검수 파일은 추가 전용이다. 시험이 진짜 사이트 팩의 파일에 쓰지 않게 경로를 `tmp_path` 로 돌린다.
- 기계 값(`value_raw`, `has_value_raw`, `confidence`, `backend`)은 결정도 검수도 건드리지 않는다 (ADR 0008).
- 다시 스캔 의심은 사람이 풀기 전까지 적재하지 않는다. 의심을 기계가 스스로 버리거나 합치지 않는다.
- 화면은 127.0.0.1 에만. `watch`·`serve` 의 로그와 요약, 새 오류 메시지에 파일명·이름·차량번호·메모를 찍지 않는다 — 수와 문서 ID 만.
  화면의 갈무리를 PR 에 붙이지 않는다.
- 날짜가 있고 바로 선 묶음의 결과는 그대로다 (3절). 달라진 수치가 있으면 무엇이 왜 달라졌는지 보고한다.
- `CLAUDE.md` 의 작업 규칙을 따른다.

## 8. 사람이 할 일 (스캐너와 실데이터가 있는 컴퓨터에서)

PR 이 합쳐진 뒤, 순서대로.

1. 스캐너 프로그램의 저장 설정: PDF, 300 dpi, 회색조, 단면, 화질 보정(문자 강조·배경 제거·가장자리 강조·드롭아웃)은 끔, 기울기 보정은 켬.
   자동 회전은 꺼 둔다 (켜져 있어도 되지만 손글씨 양식에서는 믿을 수 없다 — 방향은 파이프라인이 세운다). 빈 쪽 건너뛰기는 끈다.
2. `minedocscan.toml` 의 `[paths] inbox` 를 그 저장 폴더로, `minedocscan serve --reviewer <이름>`.
3. 종이가 있는 하루치를 스캔한다 (없으면 가진 스캔 몇 쪽을 인쇄해서 — 그 경우 방향과 정합만 본다). 홈에 뜨면 날짜를 넣는다.
   한 번은 뒤집어서, 한 번은 양면으로도 넣어 본다.
4. 같은 묶음을 한 번 더 스캔한다 (다시 스캔 실험). 붙잡힌 쪽과 못 잡은 쪽을 센다.
5. 가진 전체 묶음(보관 폴더)을 `run --fresh` 로 다시 돌린다 (스키마 8). `report` 에서 `duplicate`·`blank`·돌아간 쪽의 수를 본다 —
   지난 스캔에 실제로 두 번 찍힌 쪽이 있었는지가 여기서 나온다. 그 뒤 `regress --update` (교차검증의 수가 달라졌으면 그것부터 알린다 — 4.8 의 순서 고정).
6. 스캐너로 찍은 표본으로 회귀 기준을 하나 더 잡을지 정한다 (DATA.md 의 스캐너 절).

**돌려줄 수치** (이름·번호·파일명 없이 수치만): 스캐너로 찍은 쪽 수와 방향별 수, `align_failed`·`unknown_form`·`blank` 의 수, 빈 쪽으로 간 것 중
빈 쪽이 아니었던 것, 쪽당 처리 시간, 다시 스캔 실험의 유사도(붙잡힌 쪽의 최소, 같은 날 다른 종이의 최대)와 놓친 쪽 수,
전체 묶음에서 `duplicate` 로 잡힌 쪽 수와 그중 진짜였던 것, 파일이 접수 폴더에 떨어지고 화면에 뜰 때까지의 시간, PDF 가 "복구 필요"로 읽힌 횟수.

## 12. 지시서와 달라진 점 (구현 뒤)

**4절에서 벗어난 것**
- **4.6 서명에서 표 밖 필드도 지운다** (지시서는 인쇄만). 합성 글씨는 사람마다 획이 같아, 같은 날 모든 일보의 머리 칸(날짜 줄·차량번호·작성자)이
  화소까지 같았다 — 그 칸들이 서명 질량의 58–66 %, 같은 날의 다른 종이가 0.81 까지 올라가 기준 0.80 을 넘었다 (`--low-cells` 0.810,
  `--meta-fields --mix-pages` 0.814). 단계 3 의 "멈추고 묻는다"에 따라 물었고, 사람이 "표 밖 필드를 지운다"로 정했다 (기준은 0.80 그대로).
  지운 뒤: 같은 날 다른 종이 최대 0.594(기본)·0.645(낮은 칸)·0.771(메타 필드 + 섞인 쪽), 다시 찍은 쪽 최소 0.998 (흔들기·JPEG 45·90° 돌림).
  실제 다시 스캔으로는 재지 않았다 (8절 4) — ADR 0020.
- **1절 (다)·4.6 의 근거 수치를 바로잡는다** (tasks/0008 1절 라): "흔들어 다시 정합한 같은 종이 최소 0.91"은 한 번 뽑은 값이었다. 지금의 서명으로
  세 번씩 다시 재면 중앙 0.99 지만 다시 스캔의 2–3 % 가 0.80 아래다 (순하게 최소 0.70, 거칠게 최소 0.28). 같은 날 다른 종이는 최대 0.59, 다른 날은 0.85 까지.
  기준 0.80 은 그대로 (합성은 같은 날 다른 종이가 0.77 까지) — ADR 0020.
- **4.7 접수의 순서**: 지시서는 "복사 → 확인 → 접수 폴더에서 치운다 → 등록"이었다. 그 사이에 끊기면 보관 폴더에만 있고 DB 에 없는 파일이 남는다
  → "복사(임시 이름 `.part` → 이름 바꾸기) → 해시 확인 → 등록·커밋 → 치운다". 끊기면 다음 바퀴에 같은 바이트라 `_already` 로 가고, 끊긴 접수가 남긴
  보관 사본은 다시 쓴다.
- **4.7 다 쓰였나 — JPEG**: "이미지는 디코딩"만으로는 모자랐다 — OpenCV 4.9 는 잘린 JPEG 도 디코딩한다. JPEG 는 끝 표시(FF D9)까지 있어야 다 쓰인 것이다.
- **4.2 "받은 날"**: 받은 시각(UTC)을 그 컴퓨터의 날짜로 바꾼 것이다 (UTC 날짜가 아니다 — 아침에 스캔하면 UTC 로는 전날일 수 있다).
- **4.3 쪽 ID 의 표기**: 대상은 `<문서 ID>-p<쪽>` 하나로 맞춘다 (`-p01` 도 받아 `-p1` 로 적는다 — 같은 쪽이 두 대상이 되지 않게).
- **4.1 등록**: 여러 쪽 TIFF 는 등록에서 `failed` 다 (첫 쪽만 디코딩되어 둘째 쪽부터 말없이 빠졌다).
- **4.1 잠금 파일의 자리**: `WORK_ROOT` 가 아니라 **DB 파일 옆**(SQLite 가 아니면 `WORK_ROOT`) — 작업 폴더가 달라도 DB 가 같으면 같은 잠금이다
  (기본 설정에서는 둘이 같다).
- **4.9 홈**: 할 일에 오류 쪽·실패 문서·다시 처리 대기 수를 더했다. 결정을 저장하면 작업 스레드를 깨운다 (다음 폴링을 기다리지 않는다).

**6절 — 시험 시간**
- 기본 `pytest` 를 main 의 1.25배 안에 두려고 무거운 시험을 `slow` 표시로 떼어 CI 의 `slow` 작업으로 돌린다 (단계 2 에서 만든 `fuzz` 표시를
  `slow` 로 바꿨다): 다시 처리의 불변식 흔들기(종류마다 한 번 + 세 시드 × 40번), 합성 접수 시나리오(`tests/test_synth_intake.py`), 정확히 돌린 쪽의
