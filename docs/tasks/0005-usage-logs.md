## 1. 왜 하는가

하루치 묶음의 절반이 아직 DB 에 들어가지 않는다. 3일치 83쪽 중 40쪽이 "분류만 하는" 양식이다:
중기운행일보(살수차 등 같은 서식) 30쪽, 로우더 작업일보(갱외) 6쪽, 점보 작업일보 4쪽. 셋 다 **장비 한 대의 하루**를 적는 일보다.
2단계(통합 DB)의 가동 시간 분류가 쓸 재료가 여기에 있다.

실제 양식을 보고 알게 된 것 (3일치 40쪽을 눈으로 본 것):

- 중기운행일보와 점보 작업일보는 **같은 짜임**이다: 머리(장비명·운전자·서명) / 작업 표(작업위치·작업내용·운행시간·비고, 다섯 줄 남짓 + 합계 줄) /
  계기 칸(시작·종료·총) / 정비 및 특이사항.
- **계기 칸**에는 가동 시간계의 값을 소수 한 자리로 적는다 (예: 시작 1234.5, 종료 1243.6). "총"은 거의 비어 있다.
  - 같은 장비의 **어제 종료 값이 오늘 시작 값과 같다.** 계기를 이틀 이상 적은 장비 네 대에서 이어졌다 (한 군데는 글씨가 흐려 확실하지 않다).
    물질수지의 횟수 교차검증처럼, 여기에도 검산이 있다.
  - 계기 값 대신 **시각**을 적은 쪽이 있다 (12:00 / 13:00, 점으로 08.00 / 17.00). 계기가 없는 장비다.
  - 중기운행일보·점보 작업일보 34쪽 중 계기 값을 적은 것이 12쪽, 시각을 적은 것이 3쪽, 나머지는 빈 칸이다.
- **작업 표는 자유롭게 쓴다.** 작업내용 칸에 시간대를 적기도 하고("05:00~08:00 …"), 운행시간 칸에 사람 이름이나 횟수를 적기도 하고,
  비고에 같이 일한 사람 이름을 적고, 윗줄과 같다는 표시(〃)를 쓴다. 칸의 뜻대로 나눠 읽을 수 없다.
- 로우더 작업일보는 짜임이 다르다: 왼쪽에 작업량 표(구분 7행 × 갑·연근·소계, 칸마다 "하단: _ 대 / 저광장: _ 대"가 인쇄되어 있다),
  오른쪽에 가동시간(오전·오후·연근의 시각 범위), 연료·오일 주입, 일일점검, 계기(시작·종료·가동시간). 제목 앞 괄호에 장비를 손으로 적는다.
  작업량 표는 대부분 비어 있고, 표 위에 걸쳐 메모를 쓰기도 한다.

그래서 이번에 DB 로 가져갈 것은 **장비·운전자·날짜·계기(또는 시각)** 와 **작업량 표의 숫자**다. 작업 표의 글씨는 칸 단위로 남기되(`doc_field`)
뜻으로 풀지 않는다 — 텍스트 인식이 생긴 뒤의 일이다.

```bash
minedocscan template preview <site>/templates/<양식>          # 셀·필드·이름·형식을 기준 이미지 위에 그려서 확인 (WORK_ROOT 에 PNG)

minedocscan report                                            # 가동 기록: 쪽 수, 계기 있음/시각/빈 칸, 계기 검산(이어짐 / 어긋남 / 비교할 전날 없음)

minedocscan review serve --queue readings --reviewer jp       # 계기 칸: 쪽마다 시작·종료·총을 한 번에. 1234.5 또는 08:00
minedocscan review serve --queue usage-check --reviewer jp    # 계기가 이어지지 않는 장비·날짜: 어제의 종료 칸과 오늘의 시작 칸을 같이 본다
```

## 3. 범위

**이번에 한다**
- 0004 에서 남은 손질, 차량번호 숫자 모델에 실제 숫자를 섞어 학습하는 선택 기능 (단계 1)
- 값의 형식: 정수 / 소수 / 시각 / 시각 범위 / 계기-또는-시각 — 템플릿에 적고, 입력 화면과 검증이 따른다 (단계 2)
- 새 종류의 업무 기록 "장비 가동 일보": 핸들러 `usage`, 표의 역할로 양식의 차이를 흡수한다 (단계 3)
- 검산: 쪽 안(총 = 종료 − 시작, 소계 = 합)과 날짜 사이(어제의 종료 = 오늘의 시작) (단계 4)
- 검수 대기열 `readings`, `usage-check` (단계 5)
- 템플릿을 만드는 도구와 합성 양식 두 종 (단계 6)

**이번에 하지 않는다**
- 소수·시각을 기계가 읽는 것. 숫자 모델은 지금처럼 정수 칸만 읽는다. 다음 지시서(0006)에서 계기의 연속성을 후보로 삼아 읽는다
- 작업 표(작업위치·작업내용·운행시간·비고)를 뜻으로 푸는 것. 텍스트 인식도
- 관리 계열 양식(선광 작업일지, 경비 근무일지, 전기 안전일지 등), 점검표의 여백 행 규칙 — 양식을 보고 따로 정한다
- 가동 시간의 분류(가동 / 대기 / 정비 …). 2단계의 일이다. 여기서는 적힌 값과 그 차이만 남긴다
- 판정 규칙(정합·체크·잉크·덩어리)의 변경. `null` 백엔드의 회귀 수치는 바뀌면 안 된다

## 4. 이미 정한 것

### 4.1 값의 형식은 템플릿이 정한다

- 손으로 쓰는 칸·필드에 선택 항목 `format`:

  | format | 적는 것 | DB 에 남는 표기 (정규화) |
  |---|---|---|
  | `integer` | 정수 (`handwritten_number` 의 기본) | `7` (앞의 0 을 뗀다 — 지금과 같다) |
  | `decimal` | 소수 | `1234.5` (앞의 0 을 떼고, 쓴 소수 자릿수는 그대로) |
  | `time` | 시각 | `08:00` (24시간, 두 자리씩) |
  | `time_range` | 시각 범위 | `08:00~17:00` |
  | `reading` | 계기 값 또는 시각 | 숫자면 `decimal` 처럼, 콜론이 있으면 `time` 처럼 |
  | (없음) | 글자 (`handwritten_text` 의 기본) | 지금과 같다 |

- 정규화와 검증은 한 곳에 둔다. 검수 저장, 정답 내보내기, 평가, 핸들러가 전부 그것을 쓴다. 형식에 맞지 않는 입력은 저장 전에 거절한다 (서버에서도).
- **계기 칸의 규칙** (검수 화면의 안내와 `docs/DATA.md` 에 같은 문장으로): 계기 값은 숫자 그대로(`1234.5`), 시각은 콜론으로(`08:00`).
  종이에 점으로 쓴 시각(08.00)도 시각이면 콜론으로 입력한다. 숫자인지 시각인지는 사람이 정한다 — 코드는 콜론만 본다.
- 형식이 `integer` 가 아닌 칸은 지금의 숫자 모델에 보내지 않는다. 잉크가 있으면 검수 대기다.

### 4.2 양식의 차이는 템플릿의 "표의 역할"로 흡수한다

- 핸들러는 하나(`usage`)다. 템플릿의 표(region)마다 `role` 을 적는다:

  | role | 그 표의 칸 | 가는 곳 |
  |---|---|---|
  | `meter` | 시작·종료·총 (열 이름 `start`, `end`, `total`) | `eq_usage_daily` 의 계기·시각 |
  | `shifts` | 근무 구분(행) × 시각 범위 | `eq_usage_daily` 의 `shifts` (JSON), 가동 분 합 |
  | `tally` | 구분(행 메타 `item`) × 근무조·장소(열·행 메타) 의 정수 | `prod_tally` |
  | `activities` | 작업 표의 글자 칸 | `doc_field` 에만. 글씨가 있는 줄의 수만 `eq_usage_daily.activity_rows` 에 |

- 새 양식이 이 네 가지의 조합이면 코드를 고치지 않는다 (원칙 1). 로우더 작업일보의 "하단 / 저광장" 은 인쇄된 줄마다 템플릿 행을 나눠 정의한다.
- 표가 아닌 필드: 장비명(`meta_key: equipment`), 운전자(`meta_key: operator`), 서명(`signature`), 날짜의 월·일(0004), 연료·오일·특이사항(글자, `doc_field` 에만).

### 4.3 가동 기록은 쪽 하나에 한 행이다

- `eq_usage_daily`: 쪽(`page_id`)이 키. 날짜, 양식, 장비명(쪽 메타의 최종 값), 장비 ID(4.5), 운전자,
  계기 시작·종료·총(숫자), 시각 시작·종료(계기 칸에 시각을 적은 경우), 근무 시각 범위들, 작업 줄 수, 서명 유무,
  **가동 시간과 그 근거**, 기계 값 열(`*_raw`), 상태, 출처 필드.
- 가동 시간(`hours`)은 적힌 값에서 계산한 것이고, 무엇으로 계산했는지를 `hours_basis` 에 남긴다:
  `meter`(종료 − 시작) > `total`(총 칸) > `clock`(시각 종료 − 시작) > `shifts`(범위의 합) > 없음. 위에 있는 것이 있으면 그것을 쓴다.
  **추정하지 않는다** — 값이 없으면 NULL 이다.
- 한 장비가 하루에 두 장을 낼 수 있다 (근무조마다). 합치지 않는다. 합치는 것은 읽는 쪽(2단계)의 일이다.
- 최종 값은 검수를 적용한 필드 행에서 만든다. 기계 값은 검수가 건드리지 않는다 (ADR 0008). 불변식(저장 직후의 DB = 같은 검수 파일로 새로 돌린 DB)이 새 테이블 전부에 성립한다.

### 4.4 검산은 보여 주는 것이다. 고치지 않는다 (ADR 0006)

- 쪽 안: `총 = 종료 − 시작` (셋 다 숫자일 때), `소계 = 합` (`tally` 표의 소계 열·소계 행 — 템플릿이 어느 칸이 소계인지 적는다).
- 날짜 사이 — **계기의 연속성**: 같은 장비의, 계기 값이 있는 바로 앞 기록의 종료와 이 기록의 시작을 비교한다.
  결과: `match` / `gap`(시작이 더 크다 — 빠진 날이 있거나 잘못 적었다) / `overlap`(시작이 더 작다) / `first`(앞 기록 없음) / `unknown`(장비를 모른다, 값이 검수 대기다).
  차이(시간)와 사이에 낀 날 수를 같이 남긴다.
- 결과는 `xcheck_usage` 에 (한 행 = 검산 하나: 종류, 쪽, 비교한 값 둘, 차이, 결과, 비교 상대의 쪽). 허용 오차는 0.05 (소수 한 자리의 반올림).
- 어긋난 것을 맞춰 넣지 않는다. 앞날의 종료로 오늘의 시작을 채우지도 않는다. 대기열에서 사람이 두 칸을 같이 본다.
- 검수를 저장하면 그 장비의 앞뒤 기록의 검산이 바로 다시 계산된다 (교차검증과 같은 방식 — 날짜가 아니라 장비 단위).

### 4.5 장비는 마스터와 맞춘다. 지어내지 않는다

- 장비명은 쪽 메타 `equipment` 다. 0004 의 틀을 그대로 쓴다: 검수 > 라벨 > 기계가 읽은 값(분류기 — `recognizer train --meta-key equipment`), 출처는 `doc_page_meta`.
- 장비 ID(`eq_equipment`)는 사이트 팩의 대응표로 정한다: `site.toml` 의 `[equipment.aliases]` (적힌 이름 → 장비 키). 표에 없으면 ID 는 NULL 이고 이름만 남는다.
  비슷한 이름으로 맞추지 않는다 (원칙 4).
- 연속성 검산의 "같은 장비"는 ID 가 있으면 ID, 없으면 적힌 이름이 같은 것이다. 이름이 없는 쪽은 `unknown`.

### 4.6 템플릿은 여전히 데이터이고 저장소 밖이다

- 실제 세 양식의 템플릿은 사이트 팩에서 만든다 (8절). 이 PR 에는 합성 양식만 들어간다.
- 합성 양식은 실제와 같은 짜임으로 만든다: 낮은 계기 칸, 소수점·콜론·물결표, 계기 대신 시각을 적은 장비, 빈 계기, 작업 표에 걸친 메모,
  하루에 두 장을 낸 장비, 며칠 빠진 장비, 계기를 잘못 적은 날. 합성 글씨는 자체 획으로 (OpenCV 판과 무관 — 0003·0004).

### 4.7 정답은 기계 값을 보지 않고

- `readings` 대기열은 기계 값이 없다(읽는 모델이 없다). 다음 지시서에서 모델이 생겨도 이 대기열은 기계 값을 보여 주지 않는다 (ADR 0008).
- 앞날의 종료 값도 보여 주지 않는다 — 보여 주면 그 값을 따라 적는다. 두 값을 같이 보는 것은 `usage-check` 에서만.

### 4.8 스키마 버전 6

- `eq_usage_daily`, `prod_tally`, `xcheck_usage`. 마이그레이션은 만들지 않는다 (ADR 0005).

## 5. 단계

### 단계 1 — 손질

할 일
- 학습을 중간에 끊으면 모델 폴더에 임시 폴더(`.<이름>.tmp-<pid>`)가 남고 `recognizer list` 에 깨진 모델로 나온다 →
  목록에서 빼고, 다음 학습을 시작할 때 주인 없는 임시 폴더를 치운다.
- `[recognize.meta]` 에 모델 이름이 아닌 항목(예: `auto_accept_conf`)을 쓰면 조용히 무시된다 → 설정 오류로 알린다 (메타 모델의 기준은 카드에서만 온다).
- 차량번호 숫자 모델에 실제 숫자를 섞는 선택 기능: `recognizer train --meta-key vehicle_no --extra-digits DIR`.
  `DIR` 은 0003 의 `export-crops`(운반 횟수 칸) 폴더이고, 그 칸의 숫자열을 CTC 학습에만 더한다 (후보 목록·기준에는 쓰지 않는다. `test` 줄이 있으면 거절).
  배경: 실제 일보 30쪽으로 돌려 보니 합성 숫자는 0.99 로 읽는데 실제 차량번호는 20쪽 중 7쪽만 맞았다 (같은 20쪽에서 분류기는 13쪽).
  실제 숫자를 본 적이 거의 없기 때문이다. 섞은 것이 나은지는 사람이 수치로 본다 (8절).
- `docs/tasks/README.md` 의 0004·0005 상태.

수용 기준
- 임시 폴더가 있어도 `recognizer list` 가 그것을 내지 않고, 같은 이름으로 다시 학습이 된다.
- `[recognize.meta] auto_accept_conf = 0.9` 는 한 줄 오류로 끝난다.
- `--extra-digits` 로 학습한 모델의 카드에 더한 셀 수가 적히고, 규격이 다른 폴더·`test` 가 섞인 폴더는 거절한다. 주지 않으면 결과가 전과 같다.

### 단계 2 — 값의 형식

할 일
- `forms/template.py`: 칸(열)과 필드의 `format` (4.1). 종류와 맞지 않으면(`printed` 에 format 등) 템플릿 오류.
- 정규화·검증 모듈 하나 (`normalize(format, 입력) -> 표기 | 오류`). 받아 주는 입력의 예: `8:00`, `08:00`, `0800` → `08:00`;
  `8-17`, `08:00~17:00`, `0800-1700` → `08:00~17:00`; `1234.5`, `01234.5` → `1234.5`. 24:00 이후, 60분 이상은 오류. 범위의 끝이 시작보다 이르면 다음 날로 본다 (연근).
- 검수: `review/store.save` 와 서버가 형식에 맞지 않는 값을 거절한다 (400, 무엇이 틀렸는지). 화면은 형식마다 입력 가능한 글자와 안내를 바꾼다.
  지금의 숫자 칸 동작(`integer`)은 그대로다.
- `export-answers`, `eval` 은 정규화한 표기로 비교한다. `export-crops` 의 `labels.jsonl` 에 `format`.
- 핸들러: `integer` 가 아닌 형식의 칸은 인식기에 보내지 않는다 (4.1).

수용 기준
- 형식마다 받아 주는 입력과 거절하는 입력의 표가 테스트에 있고, 같은 값의 다른 표기가 같은 정규화 결과를 낸다.
- 형식이 없는 기존 템플릿(합성·실제)의 결과가 전과 같다.
- 잘못된 형식의 값은 검수 파일에 한 줄도 남지 않는다.

### 단계 3 — 장비 가동 일보 (`usage` 핸들러)

할 일
- `handlers/usage.py`, 표의 역할(4.2), `eq_usage_daily`·`prod_tally` (4.3), `hours`·`hours_basis`.
- 계기 칸의 값 유무는 잉크로 정한다. 표의 칸이지만 낮고 글씨가 넘는 것은 운반 칸과 같다 — 덩어리 배정(`imaging/blobs.py`)을 그대로 쓴다. 임계값을 새로 만들지 않는다.
- `tally` 표의 정수 칸은 지금의 숫자 인식 경로(`by_kind`, 자동 적재 표)를 그대로 탄다.
- 장비명·운전자: 쪽 메타 (4.5). `equipment` 는 새 키일 뿐이다 — `page-fields` 대기열, `export-crops --meta`, `recognizer train --meta-key equipment`,
  `eval --meta` 가 코드 변경 없이 되어야 한다. 안 되는 곳이 있으면 키 이름에 묶인 코드다 — 고친다.
- `[equipment.aliases]` → `equipment_id`. 마스터에 없는 키를 가리키면 사이트 팩을 읽을 때 오류.
- `on_review`: 그 쪽의 `eq_usage_daily`·`prod_tally` 를 최종 필드 행에서 다시 만든다. 메타 필드(장비명·운전자)의 검수도.
- `report`: 가동 기록 — 양식별 쪽 수, 계기 있음 / 시각 / 빈 칸 / 검수 대기, `hours_basis` 별 수, 장비 ID 가 정해진 쪽 수.

수용 기준 (합성 데이터, `oracle` 백엔드와 검수로)
- 합성 가동 일보 두 종이 `loaded` 이고, 검수로 정답을 전부 넣으면 `eq_usage_daily`·`prod_tally` 가 합성 정답과 같다.
- 계기 대신 시각을 적은 쪽은 계기 열이 NULL 이고 시각 열이 차며 `hours_basis = clock` 이다. 둘 다 없으면 `hours` 가 NULL 이다.
- 하루에 두 장을 낸 장비가 두 행으로 남는다.
- 대응표에 없는 장비명은 `equipment_id` 가 NULL 이고 이름은 남는다.
- 불변식: 임의의 검수(계기·작업량·장비명 포함)를 저장한 직후의 DB = 같은 검수 파일로 새로 돌린 DB. 새 테이블 포함.
- 다른 양식의 결과와 `null` 의 회귀 수치가 그대로다.

### 단계 4 — 검산

할 일
- `validate/usage.py`: 쪽 안의 검산과 계기의 연속성 (4.4) → `xcheck_usage`. 마무리 단계(`finalize`)에서 전체를, 검수 저장 뒤에는 그 장비 것만 다시.
- 템플릿: `tally` 표에서 어느 열·행이 소계인지 (`subtotal: true` 같은 메타).
- `report`: 검산 종류별·결과별 수, 날짜별.

수용 기준 (합성 데이터)
- 합성 정답대로 검수하면: 이어지는 장비는 전부 `match`, 며칠 빠진 장비는 `gap` 과 사이에 낀 날 수, 계기를 잘못 적은 날은 `gap`/`overlap` 과 차이,
  첫 기록은 `first`, 시각을 적은 장비는 연속성 검산이 없다.
- 계기 값 하나를 검수로 고치면 그 쪽과 그 **다음** 기록의 검산이 바로 바뀌고, 불변식이 성립한다.
- 장비명을 검수로 바꾸면 예전 장비와 새 장비 양쪽의 연속성이 다시 계산된다.
- 어긋난 쪽의 `eq_usage_daily` 값은 바뀌지 않는다 (검산이 값을 고치지 않는다).
- `총` 이 적힌 쪽에서 `총 ≠ 종료 − 시작` 이면 그 검산만 어긋남이고 `hours` 는 4.3 의 순서대로다.

### 단계 5 — 검수 대기열

할 일
- `readings`: 계기 표(`meter`)에 잉크가 있는 쪽. 항목 = 쪽 하나(시작·종료·총을 한 번에, 빈 칸은 Enter). 날짜 → 쪽 순서. 기계 값·앞날의 값 없음 (4.7).
  `--audit N` (0004 와 같은 뜻: 상태와 상관없는 표본).
- `usage-check`: `xcheck_usage` 가 `gap`·`overlap`·쪽 안 어긋남인 것. 항목 = 검산 하나: 비교한 두 칸(다른 쪽이면 두 쪽)의 크롭과 지금 값, 차이. 고칠 칸을 입력한다.
- `page-fields`: `equipment` 키의 후보 목록 = `[equipment.aliases]` 의 이름 + 라벨·검수에 나온 값.
- `review stats` 에 형식별·대기열별 수.

수용 기준
- `readings` 응답에 기계 값과 다른 쪽의 값이 없다. 한 쪽의 세 칸이 한 번의 저장으로 남는다.
- `usage-check` 에서 한 칸을 고치면 그 검산이 대기열에서 빠지고(또는 여전히 어긋나면 남고) 진행 수가 맞다.
- 형식에 맞지 않는 입력은 화면에서도 서버에서도 저장되지 않는다. (브라우저에서 확인하고 PR 본문에 적는다.)

### 단계 6 — 템플릿 도구와 합성 양식

할 일
- `minedocscan template preview <템플릿 폴더> [--scan FILE --page N]`: 기준 이미지(또는 정합한 스캔) 위에 칸·필드의 테두리, 이름, 종류·형식·역할, 행 키를 그린 PNG.
  기본 위치는 `WORK_ROOT/template-preview/`. 실제 양식에는 이름이 인쇄·기재되어 있으므로 저장소 안이면 거절한다.
- `minedocscan template check <템플릿 폴더>`: 로드 오류, 겹치는 칸, 쪽 밖의 칸, 역할에 필요한 열 이름(`start`/`end`/`total` 등) 누락, 형식과 종류의 불일치를 목록으로.
- `tools/synth.py`: 가동 일보 두 종(작업 표 + 계기 / 작업량 표 + 근무 시각 + 계기)의 선택 기능 (4.6). 기본 합성 데이터는 바이트까지 그대로.
  합성 획에 소수점·콜론·물결표.
- `docs/SITE_PACK.md`: 가동 일보 템플릿을 쓰는 법 — 표의 역할, 형식, 인쇄된 줄로 행 나누기, 소계 표시, `[equipment.aliases]`. 합성 템플릿을 예로.

수용 기준
- 합성 템플릿의 `preview` 가 칸 수만큼 테두리를 그리고, 일부러 망가뜨린 템플릿에서 `check` 가 그 오류를 전부 낸다.
- 같은 씨앗의 합성 가동 일보가 OpenCV 5.0 과 하한 판에서 거의 같다 (0003·0004 와 같은 기준).

여기까지 끝나면 PR 을 연다.

## 8. 사람이 할 일 (실데이터가 있는 컴퓨터에서)

PR 이 합쳐진 뒤, 순서대로.

1. 사이트 팩에 세 양식의 템플릿을 채운다 (지금은 표가 없는 분류 전용이다): 중기운행일보, 점보 작업일보, 로우더 작업일보.
   `template preview` 로 칸이 맞는지 보고 `template check` 로 확인한다. 장비명·운전자 필드에 `meta_key`.
2. `site.toml` 에 `[equipment.aliases]` — 일보에 적는 이름과 점검표의 장비를 잇는다. 모르는 것은 비워 둔다.
3. `minedocscan run DB_scans --fresh` (스키마 6) → `regress --update` (새 양식의 정합 통과율과 괘선 오차가 기준에 들어간다. 기존 항목은 그대로여야 한다).
4. `review serve --queue page-fields` — 장비명·운전자. 며칠치를 입력한 뒤 `recognizer train --meta-key equipment --cv 5` (운전자 모델은 일보 것과 같이 학습해도 된다).
5. `review serve --queue readings` — 계기 값. 그다음 `report` 의 계기 검산과 `--queue usage-check`.
6. (0004 에서 이어서) 차량번호: `--extra-digits` 를 준 것과 안 준 것, `--reader choice` 를 `eval --meta` 로 비교한다.

**돌려줄 수치** (이름·번호 없이 수치만): 양식별 쪽 수와 정합 통과율, 계기 칸이 있는 쪽 / 시각을 적은 쪽 / 빈 쪽의 수, 장비 수,
연속성 검산의 결과별 수와 어긋난 것의 원인(빠진 날 / 잘못 적음 / 다른 장비), 한 시간에 입력한 쪽 수, 작업량 표에 값이 있는 칸의 비율,
차량번호 세 방식의 정확도.

## 12. 지시서와 달라진 점 (구현 뒤)

4절(이미 정한 것)을 바꾼 것은 없다. 4절이 정하지 않은 자리를 다음처럼 채웠다.

**순서**
- 합성 가동 일보 두 종(`tools/synth_usage.py`)과 손글씨 획의 소수점·콜론·물결표·붙임표를 **단계 3** 에서 만들었다 — 단계 3·4·5 의 수용 기준이

- 단계 2 의 손질 둘을 단계 3 커밋에 넣었다: 아직 적재되지 않은 쪽의 칸도 검수에 적힌 문맥(양식·표·칸)으로 형식을 찾아 거절한다
  (전에는 그대로 파일에 남았다), `/api/reviews` 의 `review_id` 를 같이 쓰는 저장 시각으로 다시 만든다.

**값 유무 (단계 3 "덩어리 배정을 그대로 쓴다")**
- 읽지 않는 칸(소수·시각)은 덩어리 배정 **또는** 잉크 비율 중 하나라도 "있음"이면 검수 대기다. 긴 계기 값 두 개가 칸 폭의 절반보다 가까우면
  RLSA 가 한 덩어리로 묶고, 폭이 1.6칸을 넘으면 메모로 판정해 두 칸이 다 "빈 칸 자동 적재"가 된다 — 값이 조용히 사라진다(합성 300 px 칸에서
  실제로 일어났다). 두 판정 모두 기존 것이고 새 임계값은 없다. 정수 칸(작업량)은 운반 칸과 같이 덩어리 배정만 쓴다 (메모를 값으로 세지 않게).
- 작업 표(activities)와 표 밖 필드는 잉크 비율(기존 `text_ink_min`)이다. 세로획뿐인 글씨("1")는 괘선 지우기가 지워 빈 칸이 된다 — 기존 한계.

**템플릿**
- 인쇄되지 않은 나눔 선 `grid.split_ys`·`split_xs` 를 더했다. 4.2 의 "인쇄된 줄마다 템플릿 행을 나눠 정의한다"를 `ys` 에 선을 더해 하면
  정합 판정(표마다 괘선 오차의 중앙값)이 없는 괘선을 찾다가 쪽을 `align_failed` 로 만든다. 나눔 선은 칸만 자르고 정합·괘선 지우기에는 쓰지 않는다.
- 계기 표는 열 이름 `start`·`end`·`total` 외에 **행 키**로도 받는다 (세로로 놓인 계기 칸). `total` 은 없어도 된다.
- 작업 표(activities)의 합계 줄에 `subtotal: true` 를 쓸 수 있다 — 글씨 있는 줄의 수에서 뺀다 (4.2 의 표에는 tally 만 있었다).
- 행 키가 겹친다는 템플릿 오류는 키 값 대신 행 번호를 찍는다 (점검표의 행 키는 장비 번호다 — 7절).
- `Template.problems()` 로 읽을 때의 오류를 전부 모은다. 읽을 때는 여전히 첫 오류에서 멈춘다. `template check` 는 여기에 표·열·행 이름 겹침,
  필드 bbox, 너무 좁은 칸, 쪽 밖, 겹치는 칸, page_size 를 더한다 — 기존 템플릿을 새로 거절하게 될 검사는 읽을 때 넣지 않았다.

**테이블**
- `eq_usage_daily.reading_kind`(meter | clock | mixed | empty | pending | none)를 더했다 — 리포트의 "계기 있음 / 시각 / 빈 칸 / 검수 대기"와
  `readings`·검산이 쓴다. 출처 칸은 `start_field_id`·`end_field_id`·`total_field_id` 셋.
- `eq_usage_daily.equipment_id` 에 외래 키를 걸지 않았다 — 마스터 행(`eq_equipment`)은 점검표 쪽을 적재할 때 생기므로 가동 일보만 돌린 DB 에는 없다.
  ID 는 같은 UUID 규칙(`forms/equipment.equipment_id`)이다.
- `[equipment.aliases]` 의 오류는 설정 오류(ConfigError, 한 줄)이고 몇 번째 항목인지만 알린다 (이름·장비 키를 찍지 않는다).

**규칙의 해석**
- 가동 시간: 앞선 근거에 **모르는 칸**(잉크는 있는데 값이 없다 — 검수 대기)이 있으면 뒤의 근거로 내려가지 않고 NULL 이다. 예: 시작이 검수 대기인데
  근무 시각이 있으면, 그 근무 시각으로 정하지 않는다 — 검수 뒤에 근거가 바뀌기 때문이다.
- 가동 시간의 "섞임"(9절)은 시작·종료로만 가른다 — 총(가동시간)은 길이라 시각 옆에 수로 적혀도 섞인 것이 아니고 `total` 근거가 된다.
  "읽을 수 없음" 검수는 기계의 값 유무를 그대로 두므로, 기계가 빈 칸이라 한 칸이라도 모르는 칸으로 친다 (빈 칸으로 치면 다음 근거로 내려간다).
- 연속성: "앞 기록을 얼마나 멀리까지 찾을지 — 제한 없음"(9절)은 계기 값이 없는 기록(시각·빈 칸)을 건너뛰는 것으로 했다. 바로 앞 계기 기록의
  종료를 모르면(검수 대기, 시작만 적혔다), 같은 날 시작 값을 모르는 다른 장이 있으면, 날짜를 모르면 더 앞을 찾지 않고 `unknown` 이다 —
  일부만 검수한 중에 가짜 `gap` 이 생기지 않게, 있는 날을 빠진 날로 탓하지 않게.
- `usage-check` 의 "끝남" = 지금 맞는 것(고쳐서 맞게 됐다, 고쳐서 검산이 없어졌다) + 비교한 칸이 전부 그 검산의 항목에서 저장되었고 지금 값이
  그때와 같은 것(확인). 화면은 고친 칸만 저장하고, 아무것도 고치지 않고 저장하면 칸 전부를 "적힌 대로" 확인한다. 이 대기열의 검수는 note 에
  검산 id 를 남기고, 같은 초에 같은 칸을 두 검산의 확인으로 저장해도 둘 다 남게 review_id 에 note 를 넣는다 (note 가 없으면 예전과 같은 id) —
  한 칸(종료)이 그 쪽의 총 검산과 다음 기록의 연속성에 같이 걸리기 때문이다.
  빠진 날 때문의 `gap` 처럼 진짜 어긋남은 확인하고 넘어가며, 어긋남은 `xcheck_usage` 와 리포트에 그대로 남는다.
- `review stats` 의 "대기열별"은 대기열마다 끝난 수 / 모집단이다 (기본 설정으로). 검수 기록에 대기열 이름을 남기지는 않는다.

**코드 정리**
- 운반 핸들러의 정수 칸 처리를 `handlers/base.number_row` 로 뽑아 작업량 칸과 같이 쓴다 (결과 같음 — `null` 리포트 비교).
- 장비 마스터 함수(`equipment_id`, `layout`, `is_equipment_row`)를 `forms/equipment.py` 로 옮겼다 (사이트 팩이 대응표를 검사하려면 핸들러를
  가져오지 않아야 한다 — 순환). `handlers/inspection` 은 그대로 내보낸다.
