## 1. 왜 하는가

지금 인식 백엔드는 `null` 과 `oracle` 뿐이다. 손으로 쓴 값은 전부 검수 대기로 간다.
운반 횟수는 한두 자리 숫자이고, 같은 값이 일보와 행렬 두 곳에 적혀 교차검증으로 바로 확인된다. 첫 인식기로 가장 작고 효과가 바로 보인다.

실제 숫자 칸을 보고 알게 된 것 (3일치에서 값이 있다고 판정된 칸 60개를 눈으로 본 것. 표본이 작다):

- 칸은 낮고 넓다 (200 dpi 에서 높이 28–30 px, 폭 약 100 px). **글씨가 칸보다 크다.** 위아래 괘선을 넘어 쓴다.
  지금 파이프라인이 인식기에 넘기는 크롭(칸 그대로, 여유 0)에서는 숫자가 잘린다.
- 그래서 **이웃 칸의 글씨가 이 칸으로 넘어온다.** 값이 있다고 판정된 칸의 약 5분의 1은 이 칸의 숫자가 아니었다:
  X 표, 덧칠해 지운 것, 윗칸 숫자의 아랫부분, 칸 위에 걸쳐 쓴 메모.
- 값은 1–16 근처이고 두 자리가 드물지 않다. 흘려 쓰고, 연하고, 쓰는 사람이 여럿이다.

인식기는 "이 칸의 숫자는 무엇인가"와 함께 "이 칸에 숫자가 있기는 한가"를 답해야 한다.

## 2. 끝났을 때 되는 일

```bash
pip install -e ".[train]"                                           # 학습할 컴퓨터에서만 (torch). 현장 PC 는 필요 없다

minedocscan review export-crops ~/crops --split train --kind handwritten_number --include-illegible
minedocscan recognizer train --crops ~/crops --name digits-v1       # CPU 에서 몇 분. → <site>/models/digits-v1/
minedocscan recognizer eval  --crops ~/crops --model digits-v1 --split val --errors   # 검증 날짜의 성적 + 틀린 칸 모아 보기

# 설정: [recognize.by_kind] handwritten_number = "digits",  [recognize.digits] model = "digits-v1"
minedocscan run DB_scans --fresh                                    # 숫자 칸은 digits, 나머지는 null
minedocscan eval --answers answers-test.json --target raw --only-listed --split test   # 정확도, 자동 적재율, 자동 적재 오류율
minedocscan report                                                  # 횟수 일치율(기계 값 기준)이 0/0 이 아니게 된다
```

## 4. 이미 정한 것

### 4.1 인식기에 넘기는 크롭은 규격 하나로 정의하고, 학습과 추론이 같은 구현을 쓴다

- 규격(`CropSpec`): 해상도(`aligned` = 200 dpi 정합 이미지 | `source` = 원본), 배율(템플릿 좌표 대비), 여유(칸 둘레).
- `review export-crops` 가 내보낸 PNG 와 파이프라인이 인식기에 넘기는 배열은 **같은 셀이면 화소까지 같다.**
  학습 때 본 그림과 운용 때 보는 그림이 다르면 평가셋의 수치가 운용에서 재현되지 않는다.
- 백엔드가 원하는 규격을 선언한다. 선언하지 않은 백엔드(`null`, `oracle`)는 지금과 같은 크롭을 받는다.
- 숫자 모델의 기본 규격: 원본 해상도, 1.5배, 여유 = 행 높이의 절반(최소 8 px) — `export-crops` 의 기본값과 같다.
  어떤 규격이 나은지는 사람이 검증 날짜의 수치로 비교한다 (8절). 그래서 `aligned`·`source` 둘 다 파이프라인에서 되어야 한다.
- 모델은 자기가 학습한 규격을 모델 카드에 적어 두고, 백엔드는 그 규격을 그대로 선언한다. 설정으로 따로 주지 않는다.

### 4.2 학습은 torch, 추론은 ONNX 파일을 OpenCV 로

- 학습은 선택 의존성 `[train]` (torch, onnx). 추론은 이미 있는 `opencv-python-headless` 의 `cv2.dnn` 으로 한다 — **현장 PC 에는 새 의존성이 없다.**
- 그래서 모델은 OpenCV 가 읽을 수 있는 층만 쓴다: 합성곱, 배치 정규화, ReLU, 풀링. 순환층·어텐션은 쓰지 않는다.
- torch 를 import 하는 코드는 학습 모듈 안에만 둔다. `pip install -e ".[dev]"` 만 한 환경에서 `pytest` 와 `minedocscan run`(digits 백엔드 포함)이 돈다.
- 사전 확인 (2026-10-03, torch 2.14 + onnx, OpenCV 4.13, CPU 2스레드):
  - 합성곱 4층 + CTC, 약 14만 파라미터, ONNX 파일 약 550 KB. torch 출력과 `cv2.dnn` 출력의 차이 1.4e-5. 셀 하나에 0.6 ms.
  - `torch.onnx.export` 는 `onnx` 패키지가 있어야 한다.
  - 배치 차원을 동적으로 내보내면 `cv2.dnn` 에서 여러 장을 한 번에 넣었을 때 출력 모양이 달랐다. 한 장씩 넣어도 충분히 빠르므로 배치 1 로 고정해도 된다.
  - 이웃 칸 글씨·X 표가 섞인 합성 셀에서, 세로 방향을 **최대 풀링**으로 합치는 구조는 300 스텝(배치 64, 약 40초)에 정확도 0.998 이었다.
    같은 자리를 학습되는 합성곱으로 바꾼 구조는 2,100 스텝까지 값 있는 칸 정확도가 0.2 에서 움직이지 않았다. 구조는 맡기지만 여기서 시작하면 된다.
  - 작업 환경에서 `download.pytorch.org` 는 막혀 있었다. PyPI 의 `torch` 는 설치된다 (리눅스는 약 5 GB). CI 는 CPU 전용 인덱스를 쓴다.

### 4.3 읽는 것은 숫자열이고, 답은 세 가지다

- 출력 문자: `0`–`9`. 자릿수는 고정하지 않는다 (CTC). 처음 보는 조합(예: 학습에 없던 23)도 읽을 수 있어야 한다 — 값 전체를 분류 항목으로 두지 않는다.
- 답의 종류
  - **숫자열** — 앞의 0 을 뗀 십진수 문자열 (`07` → `7`). 검수가 저장하는 형태와 같다.
  - **빈 칸** (`""`) — 잉크는 있지만 이 칸의 값이 아니다: X 표, 지운 것, 이웃 칸에서 넘어온 획, 메모.
  - **거절** (`?`) — 숫자인 것 같지만 읽을 수 없다. 검수의 `illegible` 로 학습한다.
- 신뢰도는 그 답의 확률(같은 문자열로 접히는 경로의 합)이고 검증 날짜에서 온도 하나로 보정한다. 후보(`candidates`)에 상위 몇 개를 확률순으로 남긴다.

### 4.4 자동 적재의 규칙

기준값 `t` = 그 모델의 자동 적재 기준 (4.6).

| 인식기의 답 | 신뢰도 ≥ t | 그 밖 |
|---|---|---|
| 숫자열, 범위 안 | 그 값으로 자동 적재 | 값 있음 + 검수 대기 (읽은 값은 `value_raw` 에 남긴다) |
| 숫자열, 범위 밖 | 검수 대기 | 검수 대기 |
| 빈 칸 | **값 없음으로 자동 적재** | 값 있음 + 검수 대기 |
| 거절 | 검수 대기 | 검수 대기 |

- 범위는 현장의 것이다: `site.toml` 의 `[haul] trips_max` (없으면 검사하지 않는다). 코드에 숫자를 적지 않는다.
- "값 없음으로 자동 적재"는 기계의 판단이다: `has_value_raw = 0`, `value_raw = ""`, `backend = "digits"`, `confidence` = 빈 칸의 확률.
  잉크만 본 판정이 틀린 것(실제 칸의 약 5분의 1)을 인식기가 바로잡는다. `evaluate_presence` 의 정밀도가 오르는 것으로 확인한다.
  반대로 진짜 값을 빈 칸으로 지워 버리면 자동 적재 오류로 센다 (4.6).
- 인식기가 값을 **만들어 내지는 않는다**: 잉크 판정이 "값 없음"인 칸은 지금처럼 인식기에 가지 않는다.
- 검수가 있으면 검수가 이긴다. 기계 값은 그대로 남는다 (ADR 0008). 불변식(저장 직후의 DB = 같은 검수 파일로 새로 돌린 DB)은 `digits` 에서도 성립해야 한다.

### 4.5 모델은 사이트 팩에 둔다. 저장소에는 넣지 않는다

- 현장의 손글씨로 학습한 것은 그 현장의 데이터다: `<site>/models/<이름>/` 에 `model.onnx`, `card.json`, `train-log.jsonl`.
- 고르는 법: `[recognize.digits] model = "<이름>"` (설정 파일) 또는 `site.toml` 의 같은 항목. 설정 파일이 이긴다.
  백엔드를 골랐는데 모델이 없으면 시작할 때 오류로 멈춘다 — 조용히 `null` 로 물러나지 않는다.
- 모델 카드에 적는 것: 이름, 만든 때, 코드 버전, 규격(4.1), 입력 크기, 문자, 구조와 학습 인자, 씨앗, 학습 데이터 요약(분할별 셀 수·날짜 수·값별 개수·합성 셀 수),
  검증 성적, 온도, 자동 적재 기준과 그 근거(임계값별 표), 라이브러리 버전, `model.onnx` 의 SHA-256.
  **이미지, 이름, 차량번호, 검수자 식별자는 적지 않는다.**
- 예외 하나: **합성 셀만으로 학습한 시험용 모델**은 `tests/fixtures/` 에 둘 수 있다 (1 MB 이하, 다시 만드는 명령을 옆에 적는다).
  torch 없는 환경에서 추론 경로를 시험하기 위해서다. `.gitignore` 가 `*.onnx` 와 `/models/` 를 막고 있으므로 그 한 파일에만 예외를 둔다.

### 4.6 test 는 마지막에 한 번 보는 것이다

- 학습 명령은 `labels.jsonl` 에 `split` 이 `test` 인 줄이 하나라도 있으면 거절한다.
- 검증(`val`)은 **train 날짜 안에서 날짜 단위로** 떼어 낸다 (같은 날의 일보와 행렬에 같은 값이 적힌다 — ADR 0009 와 같은 이유).
  어느 날짜가 검증인지는 날짜와 소금값으로 정해진다. 기본 20 %.
- 학습을 언제 멈출지, 온도, 자동 적재 기준, 규격·구조의 비교는 전부 검증 날짜로 한다.
- 자동 적재 기준을 고르는 규칙: 검증 날짜에서 **자동 적재 오류율**(자동 적재된 칸 중 정답과 다른 비율)이 목표(기본 1 %) 이하인 가장 낮은 임계값.
  검증 칸이 수백 개면 오류 한두 개로 수치가 흔들린다. 그래서 비율에는 분자·분모와 구간(윌슨 95 %)을 같이 낸다.
  목표를 만족하는 임계값이 없으면 "자동 적재 없음"(기준 1.0 초과)으로 두고 그렇게 알린다.
- 우선순위: 설정의 `[recognize.digits] auto_accept_conf` > 모델 카드의 기준 > `[pipeline] auto_accept_conf`.

### 4.7 내보낸 것, 만든 것은 저장소 밖에

- 학습 산출물과 "틀린 칸 모아 보기"에는 현장의 글씨가 들어 있다. 대상이 git 작업 트리 안이면 거절한다 (`--allow-in-repo` 로만 — 시험용 모델을 만들 때).
- 로그와 오류 메시지에 셀 값을 찍지 않는다. 값별 개수 같은 집계는 된다.

## 5. 단계

### 단계 1 — 손질

할 일
- `review/static/index.html`: 후보 단축키를 `ev.code`(`Digit1`–`Digit9`)로 본다. macOS 에서 Option+숫자는 `ev.key` 가 `™` 같은 문자로 와서 후보가 선택되지 않는다.
- `review export-crops`: `--scale` 은 0 초과 6 이하, `--pad` 는 0 이상. 벗어나면 오류로 끝내고 아무것도 쓰지 않는다.
  (지금은 `--scale 0` 이 1×1 PNG 를 쓰고 "크롭 40개를 썼습니다", 종료 코드 0 이다.)
- `review export-crops`: 파일 이름에 `:` 을 쓰지 않는다. 지금은 `<field_id>.png` 인데 `field_id` 에 `:` 이 있어 Windows 에서 쓸 수 없다.
  이름을 읽는 쪽은 `labels.jsonl` 의 `file` 만 본다 (이름에서 `field_id` 를 되살리지 않는다).
- 손상 PDF 의 처리 방침을 설정으로: `[pipeline] damaged_pdf = "fail" | "warn"` (환경변수 `MINEDOCSCAN_DAMAGED_PDF`). 기본은 지금처럼 `fail`.
  - `warn`: 라이브러리가 복구해서 연 PDF 를 그대로 처리한다. `doc_document.warning` 에 남기고, 실행 요약과 `report` 에 건수와 목록이 나온다. 그것만으로는 종료 코드가 1 이 되지 않는다.
  - 열 수조차 없는 파일은 어느 쪽이든 `failed`.
  - 검수 화면·크롭 내보내기처럼 원본을 다시 여는 곳도 같은 방침을 따른다.
  - 이유: 스캐너(R10)가 만드는 PDF 가 멀쩡한데도 "복구 필요"로 읽히는지 아직 모른다 (8절 2). 그렇다면 코드를 고치지 않고 설정으로 넘어갈 수 있어야 한다.
- 검수 화면(`haul-numbers`, `mismatch`)에 안내 한 줄: "X 표·지운 칸·이웃 칸에서 넘어온 글씨는 비워 두고 Enter (빈 칸). 숫자인데 읽을 수 없으면 ?".
  같은 규칙을 `docs/DATA.md` 에 적는다. 이 규칙이 4.3 의 "빈 칸"과 "거절"의 정답이 된다.
- `docs/tasks/README.md` 의 0002·0003 상태.

수용 기준
- `key: '™', code: 'Digit2', altKey: true` 인 키 입력으로 둘째 후보가 들어간다. 숫자 네 자리는 그대로 쳐진다. (브라우저에서 확인하고 PR 본문에 적는다.)
- `--scale 0`, `--scale -1`, `--scale 7`, `--pad -1` 은 종료 코드가 0 이 아니고 출력 폴더에 PNG 가 없다.
- 내보낸 파일 이름에 `< > : " / \ | ? *` 가 없다. 줄 수 = PNG 수는 그대로다.
- 끝을 자른 합성 PDF: `fail` 이면 지금과 같다 (`failed`, 종료 코드 1). `warn` 이면 처리되고 `warning` 이 남고 요약에 나오며 종료 코드 0.
  쓰레기 바이트 파일과 0바이트 파일은 `warn` 에서도 `failed`.

### 단계 2 — 인식기에 넘기는 크롭을 한 가지로, 종류별로 백엔드 고르기

할 일
- `CropSpec` 과 "셀 하나를 규격대로 뜨는 함수"를 한 곳에 둔다 (`imaging/` 아래). `review/crops.py`, `review/export.py`, 파이프라인이 그것을 부른다.
- `Recognizer` 는 선택 속성으로 규격을 선언한다. `handlers/base.py` 의 `recognize()` 는 `o.crop` 대신 그 규격의 크롭을 넘긴다.
  핸들러가 크롭을 직접 만들지 않는다. `PageContext` 가 원본 쪽에 닿는 데 필요한 것(원본 경로, 쪽 번호, 호모그래피, 렌더링 해상도)을 가진다.
- 원본 쪽은 쪽마다 한 번만 렌더링한다 (지금 쪽당 약 1초에, 300 dpi 렌더링 약 0.15초가 더해지는 정도여야 한다).
- 종류별 백엔드: `[recognize] backend` 는 기본, `[recognize.by_kind]` 로 필드 종류(`handwritten_number`, `handwritten_text`)마다 다르게.
  파이프라인은 여전히 `Recognizer` 하나만 안다 — 종류를 보고 나눠 주는 것도 `Recognizer` 다. `--answers`(오라클)는 지금처럼 전부를 덮는다.
- `export-crops` 의 `labels.jsonl` 에 규격을 한 덩어리로 적는다 (지금의 `resolution`, `out_scale`, `pad`, `bbox` 는 유지).

수용 기준 (합성 데이터)
- 같은 셀에 대해 `export-crops` 가 쓴 PNG 와 파이프라인이 인식기에 넘긴 배열이 화소 단위로 같다. `source` 와 `aligned` 두 규격 모두.
- 규격을 선언하지 않은 백엔드에서는 리포트와 기존 테스트가 그대로다.
- 가짜 백엔드 둘을 등록하고 `by_kind` 로 나누면 숫자 칸은 한쪽만, 나머지는 다른 쪽만 받는다. `doc_field.backend` 에 각자의 이름이 남는다.

### 단계 3 — 어려운 합성 셀

지금의 합성 양식은 칸이 크고(242×72) 숫자가 한가운데에 깨끗하게 있다. 실제는 1절과 같다.

할 일
- 칸 하나의 크롭을 규격대로 만드는 생성기 (`tools/` 아래). 한 장에 들어가는 것:
  가운데 칸의 값(없을 수도 있다) · 위·아래·옆 칸의 글씨가 괘선을 넘어 들어온 것 · 괘선 · X 표와 덧칠 · 칸 위에 걸쳐 쓴 메모 · 스캔 효과.
  정답(숫자열 | 빈 칸)을 안다. 칸의 크기와 여유는 인자로 받는다 — 실제 크롭의 규격에 맞춰 만들 수 있게.
- 같은 씨앗이면 같은 셀이 나온다.
- `tools/synth.py` 에 선택 기능: 칸이 낮은 운반 양식(행 높이 30 px 근처)과 거친 숫자·X 표. **기본 합성 데이터는 그대로 둔다** (기존 테스트 불변).

수용 기준
- 같은 씨앗으로 두 번 만든 셀이 화소까지 같다.
- 만든 셀의 구성(값 있음·빈 칸·X 표·이웃 글씨 있음의 비율)이 인자대로다.
- 선택 기능으로 만든 낮은 칸의 양식이 `oracle` 백엔드로 CER 0 이다 (인식기가 아니라 파이프라인을 확인하는 것).

### 단계 4 — 모델과 학습

할 일
- `pyproject.toml` 에 `[train]` (torch, onnx). `src/minedocscan/recognize/digits/` — 학습 코드(torch)와 추론 코드(torch 없음)를 파일로 나눈다.
- `review export-crops --include-illegible`: `illegible` 도 내보낸다 (기본은 지금처럼 뺀다). `labels.jsonl` 의 `verdict` 로 구분한다.
- `minedocscan recognizer train --crops DIR --name NAME [--synthetic N] [--seed S] [--val-share 0.2] [--target-auto-error 0.01]`
  - 데이터: `DIR` 아래의 `labels.jsonl` 과 PNG. `test` 가 섞여 있으면 거절 (4.6). 규격이 한 가지가 아니면 거절.
    `value` → 숫자열, `empty` → 빈 칸, `illegible` → 거절.
  - 검증 날짜를 떼고(4.6), 나머지 실제 셀 + 합성 셀(단계 3, 실제 크롭의 규격으로)로 학습한다. 실제 셀이 0 개여도(합성만) 돈다.
  - 실제 셀에는 약한 변형(이동·크기·기울기·밝기·흐림)을 준다. 좌우 뒤집기는 하지 않는다.
  - CPU 에서 몇 분 안에 끝나는 크기. 진행은 표준 오류로, 스텝별 수치는 `train-log.jsonl` 로.
  - 끝나면 온도와 자동 적재 기준을 검증 날짜에서 정하고(4.6) ONNX 로 내보낸 뒤, **내보낸 파일을 OpenCV 로 다시 읽어** 검증 성적을 계산해 카드에 적는다
    (torch 로 계산한 수치가 아니라 운용에서 쓸 경로의 수치).
  - 산출물은 `<site>/models/NAME/` (4.5). 같은 이름이 있으면 덮어쓰지 않고 멈춘다.
- `minedocscan recognizer list` — 사이트 팩의 모델과 카드 요약.

수용 기준 (torch 가 있는 환경, `pytest -m train`)
- 합성 셀만으로 CPU 에서 2분 안에 학습한 모델이, 따로 뽑은 합성 셀 2,000개에서 값 있는 칸 정확도 0.97 이상, 빈 칸(X 표·이웃 글씨 포함) 0.97 이상.
- 같은 입력에 대해 torch 출력과 OpenCV 출력의 차이가 1e-3 미만이고 읽은 문자열이 전부 같다.
- `test` 줄이 섞인 폴더, 규격이 섞인 폴더는 거절한다. 검증 날짜와 학습 날짜가 겹치지 않는다.
- 카드에 4.5 의 항목이 다 있고, 이미지·검수자 식별자가 없다.
- torch 가 없는 환경에서 `recognizer train` 은 무엇을 설치하라는 안내와 함께 끝난다 (트레이스백이 아니라).

### 단계 5 — 추론 백엔드 `digits` 와 자동 적재 규칙

할 일
- `recognize/digits/` 의 백엔드: 모델 카드를 읽어 규격·문자·온도·기준을 정하고 `cv2.dnn` 으로 추론한다. `register("digits", …)`.
  답은 4.3, 신뢰도와 후보도 4.3.
- `handlers/haul.py` (그리고 숫자 칸을 다루는 기본 핸들러): 4.4 의 표. `machine_final()` 과 `on_review()` 가 같은 규칙을 쓴다 — 검수를 되돌렸을 때 기계 상태가 그대로 재현되어야 한다.
- 모델이 선언한 종류(`handwritten_number`)가 아닌 칸이 오면 읽지 않고 검수 대기로 돌려준다.
- `info`: 고른 백엔드와 모델(이름, 규격, 자동 적재 기준, 학습 셀 수).
- 시험용 모델: 합성 셀로 학습한 것을 `tests/fixtures/` 에 (4.5). 다시 만드는 명령을 README 한 줄로.

수용 기준 (합성 데이터, **torch 없이**)
- 시험용 모델로 합성 3일치를 돌리면: 값 있는 숫자 칸의 정확도 0.95 이상, 자동 적재된 칸 중 틀린 것 1 % 이하,
  `report` 의 횟수 일치율(기계 값 기준)이 0/0 이 아니다. (학습된 모델이므로 "정답과 정확히 같다"를 요구하지 않는다. 문턱은 합성 셀에 대한 것이다.)
- X 표를 그린 합성 칸: 잉크 판정은 값 있음이지만 값 없음으로 자동 적재된다. 그 칸들을 `empty` 로 검수해 두고 재면
  `evaluate_presence` 의 정밀도가 `null` 일 때보다 높고 재현율은 떨어지지 않는다.
- 범위 밖의 값(`trips_max` 초과)은 신뢰도가 높아도 검수 대기다.
- 불변식: `digits` 백엔드로 돌린 DB 에 임의의 검수를 저장한 직후와, 같은 검수 파일로 새로 돌린 DB 가 같다.
- `null`·`oracle` 의 결과는 전과 같다. 실데이터 회귀가 보는 수치(`null`)는 바뀌지 않는다.
- 모델 경로가 틀리면 `run` 이 시작할 때 무엇이 없는지 말하고 끝난다.

### 단계 6 — 평가와 임계값

할 일
- `minedocscan recognizer eval --crops DIR --model NAME [--split val|test|train] [--errors [DIR]]` — 파이프라인을 돌리지 않고 크롭에서 바로.
  - 정확도: 전체, 값 있는 칸, 빈 칸. 값별 표(정답 값마다 개수와 정확도). 많이 틀린 쌍(정답 → 읽은 값) 상위 몇 개.
  - 신뢰도 구간별 정확도(보정이 맞는지), 임계값별 자동 적재율과 자동 적재 오류율(분자·분모·구간).
  - `illegible` 칸 중 자동 적재될 것의 수 (0 에 가까워야 한다).
  - `--errors`: 틀린 칸을 한 장에 모은 그림(정답과 읽은 값을 옆에 적는다). 기본 위치는 `WORK_ROOT`. 4.7 의 거절 규칙.
  - `--split val` 은 학습 때와 같은 규칙으로 검증 날짜를 고른다. `--split test` 는 `test` 로 내보낸 폴더에만.
- `minedocscan eval`: 결과에 **자동 적재 오류율** — 자동 적재된 칸(값이든 빈 칸이든) 중 정답과 다른 비율. 분자·분모와 같이, 필드 종류별로도.
- `report`: 백엔드별 필드 수와 자동·대기 수.

수용 기준 (합성 데이터)
- 손으로 셀 수 있는 작은 예에서 정확도·자동 적재율·자동 적재 오류율·구간이 맞다.
- **크롭 단위 평가와 파이프라인 단위 평가가 같은 칸에서 같은 답을 낸다**: 같은 합성 3일치를 `run` 한 뒤의 `value_raw` 와,
  그 칸을 `export-crops` 로 내보내 `recognizer eval` 이 읽은 값이 칸마다 같다. (4.1 이 지켜지는지의 최종 확인이다.)
- `--errors` 대상이 git 작업 트리 안이면 거절한다.

여기까지 끝나면 PR 을 연다.

## 6. 시험

- 전부 합성 데이터. 실제 문서의 이미지나 값을 테스트에 넣지 않는다.
- 기본 `pytest`(torch 없음)는 지금처럼 통과하고, 시간이 지금의 1.3배를 넘지 않는다. 학습이 필요한 테스트는 `train` 표시로 나누고 torch 가 없으면 건너뛴다.
- CI 에 torch 를 설치한 작업을 하나 더한다 (CPU 전용 인덱스, Python 한 버전이면 된다): `pytest -m train`.
  시험용 모델을 다시 만들어도 단계 5 의 문턱을 넘는지를 이 작업이 확인한다 (바이트가 같을 필요는 없다).
- 마지막에 깨끗한 환경에서 한 번: 새 가상환경에 `pip install .`(torch 없음) → `pytest`, 그리고 `synth` → `run`(digits, 시험용 모델) → `eval` → `review serve` 를 명령줄로.
  torch 가 있는 환경에서 `export-crops` → `recognizer train` → `recognizer eval` → 설정 변경 → `run --fresh` → `eval` 을 처음부터 끝까지 한 번.

## 8. 사람이 할 일 (실데이터가 있는 컴퓨터에서)

PR 이 합쳐진 뒤, 순서대로.

1. `pip install -e ".[train]"`, 그리고 `minedocscan run DB_scans --fresh` (스키마 4).
2. **R10 으로 스캔한 PDF 를 한 번 넣어 본다.** 멀쩡한 파일이 `failed`("복구가 필요했습니다")로 나오면 `[pipeline] damaged_pdf = "warn"` 으로 바꾸고 알려 준다 —
   그 스캐너의 파일이 늘 그렇다면 기본값을 바꿔야 한다.
3. 정답 입력을 이어서 한다 (`review serve --queue haul-numbers`). X 표·지운 칸·이웃 칸 글씨는 **빈 칸**, 숫자인데 못 읽겠으면 `?`.
   이미 X 표를 `?` 로 넣었다면 그대로 둬도 된다 (거절로 학습된다. 다만 그 칸은 자동 적재되지 않고 검수 대기로 남는다).
4. `review export-crops ~/crops --split train --kind handwritten_number --include-illegible`
5. `recognizer train --crops ~/crops --name digits-v1` → `recognizer eval … --split val --errors`. 틀린 칸을 눈으로 본다.
   정답이 300셀쯤만 있어도 한 번 돌려 본다. 수치가 거칠다는 것만 알고.
6. 규격 비교: `export-crops --res aligned --scale 1` 로 한 벌 더 내보내 `digits-v1-aligned` 를 학습하고 검증 성적을 비교한다 (원본 해상도가 실제로 나은가).
7. 고른 모델을 설정에 넣고 `run DB_scans --fresh` → `eval --answers answers-test.json --target raw --only-listed --split test` → `report`.
   `test` 는 여기서 처음 본다. 본 뒤에 모델을 다시 고르지 않는다.
8. `regress` — `null` 로 도는 기준은 그대로여야 한다.

**돌려줄 수치** (이미지 없이 수치만): 학습·검증·test 셀 수와 날짜 수, 값 있는 칸과 빈 칸의 정확도, 값별 표, 많이 틀린 쌍,
고른 임계값에서의 자동 적재율과 자동 적재 오류율(분자·분모), 값 유무의 정밀도·재현율(`null` 대비), 횟수 일치율(기계 값 기준),
두 규격의 비교, 학습에 걸린 시간, 틀린 칸을 보고 느낀 점(어떤 글씨에서 틀리는가).

## 9. 열린 질문과 기본값

| 질문 | 기본값 |
|---|---|
| 자동 적재 오류율의 목표 | 1 % (검증 날짜 기준). 과제 책임자가 정한다 |
| 검증으로 떼는 날짜의 비율 | train 날짜의 20 % |
| 모델 입력의 규격 | 원본 해상도, 1.5배, 여유 = 행 높이의 절반 |
| 합성 셀을 얼마나 섞을지 | 실제 셀과 반반(배치 기준). 실제 셀이 1,000개를 넘으면 사람이 수치로 다시 정한다 |
| 횟수의 범위(`trips_max`) | 사이트 팩에 없으면 검사하지 않는다. 합성 사이트 팩에는 넣어 둔다 |
| 후보를 몇 개 남길지 | 5개 |
| 손으로 쓴 낱자 숫자를 모아 합성 셀을 만드는 기능(글자 조각 폴더) | 이번에는 만들지 않는다. 실제 성적을 본 뒤 정한다 |

## 11. 끝나고 보고할 것

- 단계별로 무엇을 만들었고 무엇을 만들지 않았는지. 수용 기준 중 충족하지 못한 것이 있으면 그것부터.
