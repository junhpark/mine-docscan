# 0023. PDF 는 PDFium(pypdfium2)으로 읽는다 — 크기는 PyMuPDF 와 같은 규칙, 손상은 끝 표시로

상태: 채택 (2026-10). 작업 지시서 [tasks/0009](../tasks/0009-release.md) 1절 나, 4.3 가, 9절.

## 상황

- PDF 를 읽던 `pymupdf` 1.28 은 **AGPL-3.0 또는 Artifex 의 상용 라이선스**다. 이 프로그램은 독립 소프트웨어로 등록해 묶어서 배포한다 —
  AGPL 의 조건(소스 공개 등)이 그 형태와 맞는지 모른다 (법률 판단은 기관의 일). 다른 직접 의존성은 MIT·BSD·Apache-2.0 이고 `psycopg` 는
  LGPL-3.0(선택 의존성, 동적 연결)이다.
- 대안 `pypdfium2`(PDFium — Apache-2.0 또는 BSD-3-Clause)로 실제 3일치(83쪽)를 재 보았다 (1절 나):
  - 같은 200 dpi 회색조로 83쪽 모두 같은 크기. 화소의 평균 차 2.0 (최대 2.8), 16 넘게 다른 화소가 쪽마다 3.2 %(중앙, 최대 4.5 %) —
    스캔 그림을 늘리는 방식이 다르다. 렌더링 시간은 같다 (9.9초 대 10.2초).
  - 같은 사이트 팩으로 끝까지: 83쪽 모두 적재, 필드 10,274개 중 값 유무가 바뀐 것 19개(수 칸 5, 글자 칸 12, 서명 2), 상태가 바뀐 것 16개,
    운반 행 8·교차검증 8행. 괘선 오차의 평균 0.886 → 0.910 px. 바뀐 쪽이 맞는지는 모른다 (정답이 없다).
  - `render(scale=200/72)` 는 크기를 올림으로 정해 **합성 A4 쪽이 1654 → 1655 px** 이 된다 (1654.0000000000002 의 올림).
    지시서는 PyMuPDF 가 반올림한다고 보았으나 재 보니 **0.001 을 봐주는 올림**이다: ceil(x − 0.001) — 1000.001 → 1000, 1000.0011 → 1001,
    1165.36 → 1166 (반올림이면 1165). 300 dpi 로 스캔한 A4(2480 px → 595.2 pt → 1653.33)는 PyMuPDF 로 1654, 반올림이면 1653 이다.
  - **전송 중 잘린 PDF**(실제 묶음을 50 %·90 %·99.9 % 로 자름): PyMuPDF 는 셋 다 "복구해서" 0쪽으로 열고, PDFium 은 셋 다 열지 않는다.
    셋 다 파일 끝에 `%%EOF` 가 없다. 실제 PDF 30개(하루치 묶음 3, 점검표 27)는 모두 마지막 1 KB 안에 `%%EOF` 가 있다.
  - `pypdfium2` 의 `save` 는 매번 다른 `/ID` 를 쓴다 — 합성 PDF 를 그것으로 만들면 같은 seed 의 바이트가 달라진다 (문서 ID 가 바뀐다).

## 결정

1. **PDF 는 PDFium 으로 읽는다** (`imaging/io.py` 한 곳). `pymupdf` 는 런타임에도 개발에도 의존성이 아니다.
2. **그림의 크기 = ceil(쪽의 pt × dpi / 72 − 0.001)** — PyMuPDF 와 같은 규칙 (`imaging/io.page_px`). 그 크기의 8비트 회색조 비트맵을
   만들어 PDFium 이 쪽을 맞춰 그린다 (`FPDF_RenderPageBitmap`, 주석 포함, 회색조). 합성 쪽은 1654×2339 그대로이고, 실제 스캔의 그림 크기도
   PyMuPDF 로 읽던 때와 같다 (지시서의 "round" 와 다르다 — 지시서 0009 12절).
3. **손상 = 열리지 않거나, 파일의 마지막 1 KB 에 `%%EOF` 가 없다.** `[pipeline] damaged_pdf = "fail"`(기본)은 그 문서를 실패로,
   `"warn"` 은 열 수 있으면 열고 경고를 한 줄 남긴다 (열 수 없으면 `fail` 과 같다). 접수 폴더의 "다 쓰였나"도 같은 검사다 — 끝 표시가 없는
   PDF 는 "아직 쓰이는 중"이다 (JPEG 의 끝 표시 `FF D9` 와 같은 생각, ADR 0019).
4. **파일은 바이트로 읽어 넘긴다** — 한글 경로를 라이브러리에 넘기지 않는다 (윈도우). PDFium 은 스레드에 안전하지 않다 — 지금의 `PDF_LOCK`
   그대로, 쪽·문서는 잠금 안에서 직접 닫는다.
5. **합성 PDF 는 라이브러리 없이 쓴다** (`tools/pdfwrite`): 쪽마다 그림 하나, JPEG 바이트는 `DCTDecode` 그대로, 무손실은 화소를 zlib 으로
   (`FlateDecode`), `/ID`·만든 시각 없이 — 같은 seed 면 바이트까지 같다. 시험이 쪽을 떼어 붙이는 것도 스트림을 그대로 옮긴다.
6. 제3자 라이선스는 `scripts/licenses.py` 가 배포판 단위의 SPDX 표현으로 검사한다 (허용 목록 밖이면 CI 가 실패 — AGPL 인 `pymupdf` 를
   다시 넣으면 막힌다).

## 이유

- 라이선스: 묶어서 배포하는 등록 소프트웨어에 AGPL 을 두는 것은 사람이 정할 위험이다. PDFium 은 그 질문을 없앤다. 법률 판단이 달라
  `pymupdf` 를 쓰기로 하면(상용 라이선스를 사거나 AGPL 의 조건을 받아들인다) 이 결정을 되돌린다 (9절).
- 크기: 정합은 호모그래피로 배율을 흡수하지만 그림의 크기가 1 px 다르면 합성의 기대값(템플릿 좌표계)이 흔들리고 실데이터의 회귀 수치가
  더 바뀐다. PyMuPDF 와 같은 규칙이면 크기는 그대로이고 바뀌는 것은 그림을 늘리는 방식(1절 나)뿐이다. 합성 쪽의 pt 는 화소에서 나왔으므로
  정확히 되돌아간다.
- 손상: PDFium 은 PyMuPDF 의 `is_repaired` 같은 신호를 주지 않는다. 객체의 중간에서 잘린 파일은 열지 않지만, 객체는 다 있고 상호 참조표·
  끝만 잘린 파일은 상호 참조표를 다시 세워 연다 (합성: 상호 참조표 앞에서 자른 파일이 6쪽 그대로 열렸다). 끝 표시는 실제 PDF 모두에 있고
  잘린 파일에는 없다 — 그래서 열리는지와 끝 표시를 둘 다 본다. 열리지만 끝이 없는 파일(끝 표시를 빼먹는 스캐너)은 `warn` 으로 받는다.
- 합성의 바이트: 문서 ID 는 파일의 해시다. 같은 seed 의 바이트가 실행마다 다르면 시험의 문서 ID 가 운에 따라 바뀐다 (0003 의 `no_new_id`).

## 결과

- 실데이터의 값 유무가 조금 바뀐다 (위의 19/10,274) — 회귀 기준은 사람이 실데이터로 다시 잡는다 (8절 1). 합성 묶음의 바이트는 한 번 바뀌고,
  정답과 같아야 하는 시험(oracle 의 CER 0, 체크 판정, 교차검증의 기대값, 접수 시나리오의 견줄 묶음)은 그대로 통과한다. 합성의 전과 후는
  지시서 0009 의 12절.
- PyMuPDF 로 "복구해서" 열리던 파일은 이제 열리지 않는다 — 그 문서는 실패이고 원본을 다시 받는다.

## 버린 것

- `render(scale)` 를 쓰고 1 px 를 잘라 맞추기 — 크기의 규칙이 라이브러리의 올림에 기댄다. 비트맵의 크기를 우리가 정하는 편이 분명하다.
- 반올림(지시서의 규칙) — 합성은 같지만 실제 스캔 일부(소수가 0.001–0.5 인 길이)가 PyMuPDF 때보다 1 px 작아진다.
- PDFium 의 저장(`save`)으로 합성 PDF 를 쓰고 `/ID` 를 지우기 — 저장 형식이 판마다 다를 수 있다. 쪽마다 그림 하나인 PDF 는 직접 쓰는 것이
  짧고 결정적이다.
- `%%EOF` 를 파일의 맨 끝에서만 찾기 — 스캐너·전송이 끝에 줄바꿈·NUL 을 붙인다. 마지막 1 KB 면 실제 파일 모두를 받고 잘린 파일을 모두 거른다.
