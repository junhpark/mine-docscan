# 0008. 검수 기록은 추가 전용 파일이 원본이고, 기계 값과 최종 값은 따로 두며, 정답은 눈가림으로 옮겨 적는다

상태: 채택 (2026-10). 작업 지시서 [tasks/0001](../tasks/0001-review-tool.md) 4절의 결정을 기록으로 남긴 것.

## 상황

운반 횟수 인식기를 고르려면 정답이 필요한데 밖에서 구할 수 없어 검수 도구로 직접 만든다 (ADR 0007).
사람이 입력한 값은 다시 만들 수 없는 유일한 데이터인데, 지금 구조에서는 `WORK_ROOT` 를 지우면 DB 와 함께 사라지고,
파이프라인을 다시 돌리면 `upsert` 가 행을 덮어쓴다. 또 검수값으로 인식기를 평가하려면 검수가 기계의 값을 지워 버리면 안 된다.

## 결정

1. **검수 기록의 원본은 사이트 팩의 추가 전용 파일이다** (`<site>/reviews/reviews.jsonl`).
   한 줄 = 한 건, 고치는 것도 새 줄, 지우거나 덮어쓰지 않는다. 한 필드의 유효한 값은 가장 최근 줄이다.
   DB 의 `doc_review` 는 이 파일의 사본이고, 파이프라인과 검수 서버는 시작할 때 파일을 읽어 들인다.
   저장 순서는 파일 먼저(flush), 그다음 DB. 키는 `field_id` 라 같은 파일이면 언제 돌려도 같다.
2. **기계 값과 최종 값을 따로 둔다.** `value_raw`·`confidence`·`backend`·`has_value_raw`·`trips_raw` 는 언제나 기계의 것이다.
   검수는 `value_final`·`has_value`·`trips` 만 바꾼다. 검수된 셀도 재실행 때 인식기를 돌린다.
   업무 테이블은 최종 값에서 만들고, 저장 직후의 DB 는 같은 파일로 처음부터 돌린 DB 와 같아야 한다 (테스트로 고정).
3. **정답 만들기는 눈가림 옮겨 적기다.** 정답을 만드는 대기열(`haul-numbers`, `mismatch`)에서는 기계가 읽은 값을 보여 주지 않는다.
   검수자는 종이에 적힌 그대로 입력하고, 두 문서가 달라도 각각 적힌 대로 적는다. 어느 쪽이 맞는지는 정하지 않는다 (ADR 0006).
   운영용 대기열(`pending`)에서는 기계 값을 미리 채워 Enter 만으로 확인할 수 있게 한다.

## 이유

- 파일이 원본이면 `WORK_ROOT` 는 계속 "언제든 지울 수 있는 곳"으로 남고(DATA.md), 스키마가 바뀌어도 마이그레이션 없이 DB 를 다시 만들 수 있다 (ADR 0005).
  추가 전용이라 동기화 앱이나 중단된 쓰기로 깨져도 마지막 줄 하나만 잃는다.
- 기계 값을 보존해야 "새 인식기의 `value_raw` 대 검수값"을 비교할 수 있다. 검수가 기계 값을 덮으면 평가셋이 평가 대상을 지우는 셈이다.
- 기계 값을 보여 주면 사람은 그 값을 확인하는 쪽으로 기운다. 정답에 인식기의 편향이 섞인다.

## 대가

- 같은 종이를 다시 스캔하면 문서 해시가 달라져 다른 필드가 된다. 검수가 이어지지 않는다 — 받아들인다.
- 파일이 공유 드라이브에 있으면 한 번에 한 사람만 입력해야 한다. 다중 사용자 입력은 만들지 않았다.
- 템플릿을 고쳐 셀 좌표가 바뀌면 옛 검수의 `bbox` 와 어긋난다. 적용은 하되 `review stats` 가 건수를 보여 준다.
- `illegible` 은 값을 바꾸지 않고 `pending` 으로 둔다. 기계의 (자신 없는) 값이 업무 행에 남는다. 다시 보는 대기열은 아직 없다.
