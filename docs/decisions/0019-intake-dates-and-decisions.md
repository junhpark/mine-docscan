# 0019. 접수: 날짜 없는 문서는 기다리고, 문서의 결정은 추가 전용 파일에 남겨 다시 처리로 적용한다

상태: 채택 (2026-10). 작업 지시서 [tasks/0007](../tasks/0007-intake.md) 4.1–4.3, 4.7–4.8. [ADR 0008](0008-review-records.md)(검수 기록)과
같은 방식이다.

## 상황

정리된 묶음 폴더(파일명에 날짜, 바로 선 쪽, 종이마다 한 번)에 `run` 을 치는 것으로 검증해 왔다. 현장에서는 스캐너의 저장 폴더에 파일이 떨어진다.

- 스캐너가 붙이는 이름은 날짜 규칙에 맞지 않는다. 실제 하루치(28쪽)를 그런 이름으로 넣으면 28쪽 전부 `loaded`, 업무 행 1,773행이
  `work_date` NULL 로 들어갔고 경고가 없었다. 날짜는 분류보다 먼저 필요하다 (그날 유효한 판만 후보 — ADR 0010).
- 스캔한 날은 작업한 날이 아니다 (다음 날 아침에, 또는 며칠 치를 모아서). 파일의 시각으로 날짜를 정할 수 없다.
- 사람이 정할 것(날짜, 버리기, "다시 스캔한 것이 아니다")이 생겼다. DB 는 언제든 지우고 다시 만들 수 있어야 한다.

## 결정

1. **문서는 등록되고, 날짜가 있어야 처리된다.** 등록 = 해시와 쪽 수(열리지 않으면 날짜와 상관없이 `failed`). 처리 = 분류·정합·적재.
   문서의 날짜는 문서의 결정 > 문서 라벨(ISO 날짜만) > 파일명 규칙. 없으면 `needs_date` — 쪽·필드·업무 행 없이 기다린다. 업무 테이블에
   날짜 없는 행이 생기지 않는다. 쪽의 날짜는 쪽의 결정 > 문서의 결정 > 쪽 라벨 > 문서 라벨 > 파일명 (`pagemeta.page_date` 한 곳).
2. **결정은 검수처럼 추가 전용 파일이 원본이다**: 검수 파일 옆의 `decisions.jsonl` (한 줄 = 결정 하나, 지우거나 덮어쓰지 않는다).
   종류는 `date`(문서·쪽) · `discard`·`restore`(문서·쪽) · `keep`(쪽 — 4.6). 유효한 결정은 대상마다·묶음마다 파일에서 가장 뒤의 것.
   `doc_decision` 은 그 사본이다 — 파이프라인이 시작할 때 파일을 비춘다 (쓰는 트랜잭션 안에서 읽는다; 유효한 결정이 바뀐 문서에는 다시
   처리를 요청한다). 여러 결정을 한 번에 저장할 때는 전부 검사한 뒤에야 쓴다.
3. **결정은 업무 테이블을 직접 고치지 않는다.** 저장 = 파일에 한 줄 → `doc_decision` → 그 문서의 다시 처리 요청(`work_requested` +1).
   처리가 그 문서의 행을 지우고(자식부터 — `store.db.PAGE_TABLES`) 결정을 적용해 다시 만든다. 화면·명령·`--fresh` 가 같은 길을 지난다.
   다시 처리 대기는 상태가 아니라 요청 번호(`work_requested > work_done`)다 — 처리하는 도중에 온 요청이 사라지지 않는다.
4. **처리는 쪽마다 커밋한다** (`BEGIN IMMEDIATE`, WAL, busy timeout 30초). 지울 때 그 문서가 있던 날짜·장비를 같은 트랜잭션에서 다시
   계산하므로 어느 커밋 뒤에 끊겨도 DB 는 처리 중인 그 문서만 빼고 맞다 (그 문서는 `received` — 다시 처리된다).
5. **순서에 기대지 않는다.** 같은 내용의 DB 가 같은 결과를 내도록: 교차검증의 자리 배정은 쪽의 순서(문서의 순서 — 보관 경로의 성분,
   접수한 문서는 뒤 — `store/order.py`)와 필드의 자리로 읽고, 계기의 연속성은 쪽 ID 까지 견주고, 같은 날의 점검 행은 쪽의 순서가 뒤인
   쪽이 이긴다. **불변식**: 문서를 몇 번을 어떤 순서로 다시 처리하든 지금의 DB = 같은 파일·같은 검수·같은 결정으로 처음부터 만든 DB.
6. **회귀 검사(`regress`)도 결정은 읽는다** — 날짜와 버리기는 무엇을 적재하는가의 일부다. 검수는 지금처럼 읽지 않는다.
7. **접수 폴더**: 다 쓰인 파일만(수정 시각 + 열린다), 보관 폴더의 `intake/<해-달>/<받은 시각>-<문서 ID>/` 로 복사하고 해시를 다시 확인해
   등록한 **뒤에** 접수 폴더의 것을 치운다. 같은 바이트는 `_already`, 읽을 수 없는 것은 `_failed`. 지우지 않는다.
   `archive_root` 는 `intake/` 아래에만 쓴다. 받은 시각은 폴더 이름에 있어 DB 를 지우고 보관 폴더를 다시 돌려도 같다.
8. **파이프라인은 한 번에 하나다** (run·watch·serve 의 작업 스레드): DB 옆의 작은 SQLite 파일에 배타 트랜잭션 — 죽은 프로세스의 잠금이 남지
   않는다. 결정·검수의 저장은 잠금과 상관없다.

## 이유

- 날짜를 모르는 쪽을 적재하면 그 행은 교차검증에서 빠지고 아무도 모른다. 기다리게 하면 홈에 뜬다 — 사람이 종이의 날짜를 한 번 넣으면 된다.
- 결정을 업무 테이블에 바로 쓰면 DB 를 지우고 다시 만들 때 사라지고, 검수·교차검증과 어긋난다. 파일이 원본이고 적용은 다시 처리 하나라
  "처음부터 만든 DB 와 같다"가 결정까지 선다 (합성 흔들기: 결정과 검수를 섞어 세 시드 × 40번, 그때마다 같았다).
- 문서 하나가 한 트랜잭션이면(30쪽에 30–70초) 그동안 화면의 저장이 기다린다. 쪽 하나면 1–2초.
- 접수 폴더에서 먼저 치우고 등록하면(지시서의 처음 순서) 그 사이에 끊길 때 보관 폴더에만 있고 DB 에 없는 파일이 남는다 — 등록·커밋 뒤에
  치우면 끊겨도 다음 바퀴에 `_already` 로 간다.

## 하지 않는 것

- `run --date`: 날짜가 한 번의 실행에만 있으면 그 뒤의 검수·다시 처리에서 사라진다. 파일명에 넣거나 `doc date` 로.
- 손으로 쓴 월·일로 날짜를 정하기: 대조에만 쓴다 (메타 모델의 실데이터 수치가 나온 뒤에 다시).
- 결정으로 쪽 하나만 다시 처리하기: 문서를 통째로 다시 처리한다 (30쪽에 1분 안쪽, 규칙이 하나).
