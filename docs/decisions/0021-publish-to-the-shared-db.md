# 0021. 작업 DB 는 SQLite 그대로, 통합 DB(PostgreSQL)에는 문서·날짜 단위 지문으로 결과의 사본을 싣는다

상태: 채택 (2026-10). [ADR 0005](0005-sqlite-first.md)의 보완 — "운영에서는 PostgreSQL 로 옮긴다"를 "옮기지 않고 싣는다"로.
작업 지시서 [tasks/0008](../tasks/0008-export.md) 1절 (나), 4.8.
고침 (2026-10, [tasks/0009](../tasks/0009-release.md) 4.1·4.2 — 싣기의 판 2): 사이트 표식 — `pub_meta` 의 `site`(4·10), `--rebuild` 는 `pub_meta` 가
있을 때만(9), 조각으로 나눈 전체 훑기와 처음 싣기·싣기의 메모리·가동 일보의 더러운 범위(7), 키 충돌로 넘어간 전체 싣기를 전체 훑기로 세기(7),
멈춘 서버의 상한(7), 비밀번호는 pgpass(8).

## 상황

2단계(통합 DB — 현장 서버의 PostgreSQL)가 이 저장소의 업무 테이블을 읽어 가야 한다. ADR 0005 는 "연결과 자리표시자만 바꾸면 되는
PostgreSQL 어댑터"를 남겨 두었다. 재 보니:

- `schema.sql` 은 PostgreSQL 16 에서 그대로 돈다 (33문 중 실패 0). 실제 3일치(83쪽, 16,293행)를 1.6초에 실었다.
- 그러나 **되읽으면 두 열이 다르다**: PostgreSQL 의 `REAL` 은 4바이트, `INTEGER` 는 32비트다 (SQLite 는 8바이트·64비트).
- 조회문은 그대로 돌지 않는다: DB 를 부르는 곳 154곳(24파일)이 `?` 자리표시자와 sqlite3 의 행 객체에 기대고, `SUM(비교식)` 4곳,
  트랜잭션·`PRAGMA`·`sqlite_master` 를 직접 만지는 곳 32곳. 0007 이 만든 처리 단위(쪽마다 커밋, `BEGIN IMMEDIATE`, WAL, DB 옆의 잠금 파일,
  홈의 `PRAGMA data_version`, `--fresh` 로 지우고 다시 만든다)는 전부 로컬 SQLite 파일을 전제로 한다.
- 이어받은 요구사항은 "외부 네트워크 없이 로컬에서 돈다. DB 도 로컬"이다. 서버가 꺼져도 스캔과 검수는 돌아야 한다.
- 지우고 다시 만드는 DB 를 다른 프로그램이 직접 읽게 둘 수 없다.

## 결정

1. **작업 DB 는 SQLite 그대로 둔다.** 통합 DB 에는 결과의 사본을 싣는다 (`publish/`). 대상에 쓰는 곳은 그 모듈 하나다 —
   "DB 쓰기는 `store.db.upsert()` 만"은 작업 DB 의 규칙이다.
2. **표의 정의는 `schema.sql` 한 곳에서 나온다.** 메모리의 SQLite 에 올려 `PRAGMA table_info`·`index_list` 로 대상의 DDL 을 만든다 (글자를 파싱하지
   않는다). 형을 넓힌다 (`REAL` → `DOUBLE PRECISION`, `INTEGER` → `BIGINT`). 기본 키·UNIQUE·인덱스는 걸고 **외래 키는 걸지 않는다** — 문서 단위로
   갈아 끼우고, 맞는지는 작업 DB 가 원본이다.
3. **싣는 표와 열은 한 곳에** (`store/db.py` 의 `PUBLISH_TABLES`·`PUBLISH_SKIP_COLUMNS`, 0007 의 불변식 시험이 같이 쓴다). 싣는 열은 작업 DB 의 열에서
   시각·요청 번호·로컬 경로(`created_at`·`received_at`·`work_requested`·`work_done`·`source_path`)를 뺀 것 — 내용이 같아도 `--fresh` 마다 달라진다.
   싣지 않는 표: `doc_page_sig`(안에서만), `doc_review`·`doc_decision`(원본은 파일), `meta_schema`.
4. **범위 셋과 지문.** 문서(`doc_document` 의 행 + 그 문서의 쪽을 가리키는 행 전부), 날짜(`xcheck_haul`·`eq_assignment_obs`), 통째(`eq_equipment`).
   싣는 표의 모든 행이 셋 중 하나에 들어야 한다 — 아니면 싣지 않고 수로 알린다. 지문 = 범위의 행을 정해진 순서(표, 기본 키)와 표현(JSON, 실수는
   정확한 표현)으로 이은 것의 SHA-256. 대상의 상태 표 `pub_state` 에 범위마다 지문, `pub_meta` 에 스키마 버전과 **싣기의 판**, 그리고
   **사이트 이름**(판 2 부터 — tasks/0009 4.1 다).
5. **지문이 다른 범위만, 한 트랜잭션으로 갈아 끼운다.** 지울 것을 먼저 다 지우고 넣는다 (같은 키의 행이 문서 사이를 옮겨 다닌다 — 점검의 이기는 쪽,
   일보의 자리). 작업 DB 에 없는 범위는 지운다. 끊기면 대상은 싣기 전 그대로다 — 읽는 쪽은 반쯤 바뀐 문서를 보지 않는다.
6. **불변식**: 싣기가 끝나면 싣는 표마다 대상의 행 = 작업 DB 의 행 (싣는 열 전부, 행의 순서와 무관, 실수까지 정확히). 실을 수 없는 값(NUL 문자)이 있는
   범위는 건너뛰고 대상의 옛 행을 지운다 — 불변식은 그 범위를 뺀 나머지에 선다.
7. **언제**: `publish` 명령(늘 전부, 한 트랜잭션), 그리고 `watch`·`serve` 의 바퀴 끝(엑셀 다음) — 더러운 범위(처리·검수가 건드린 문서, 지워진 문서,
   더러운 날짜와 그 날짜에 쪽이 있는 문서 전부 — 작업 DB 와 대상 양쪽에서)와 전체 훑기의 조각 하나. 가동 일보의 칸을 검수하면 그 장비의 모든 날짜가
   아니라 다시 계산한 연속성 행이 **바뀐** 쪽의 날짜·문서만 더럽다 (tasks/0009 4.2 다 — 합성 복제 한 해치에서 계기 칸 하나의 검수가 252일 → 2일). 장비 마스터(`eq_equipment`)를
   바꾼 처리는 "전부"로 — 새 조각 바퀴를 시작한다 (4.1 바).
   - **키가 부딪치면**(더러운 범위만 실었는데 빠뜨린 범위가 그 키를 쥐고 있었다 — `IntegrityError`, SQLSTATE `23…`) 되돌리고 같은 연결에서 조각 없는
     전체 싣기(한 트랜잭션)로 다시 한다. 그것이 성공하면 **전체 훑기를 마친 것으로 센다** — 돌던 조각 바퀴도 끝나고 마지막 전체 훑기의 시각이 그때다
     (tasks/0009 4.1 바·4.2 가 — `Result.fell_back`, `Sweep.complete`).
   - **바퀴 끝의 전체 훑기는 조각으로** (tasks/0009 4.2 가 — `sweep.Sweep`, 자동 내보내기와 같이 쓴다): 시작할 때와 `sweep_minutes` 마다 한 바퀴를
     시작하고 작업 바퀴마다 한 조각씩 끝까지 간다. 조각 = 달 하나(앞 글자가 `YYYY-MM-` 인 날짜와 그 날짜에 쪽이 있는 문서 — 달의 목록은 바퀴를
     시작할 때 작업 DB 의 달과 대상에만 있는 달을 합친다), 마지막에 날짜 없는 조각(달의 꼴인 날짜에 쪽이 없는 문서 — 대상에만 있는 문서 키도 —,
     달의 꼴이 아닌 날짜 키). 통째 범위는 늘 같이 본다. 조각을 한 바퀴 다 돌면 전체 훑기와 같다 (흔들기 시험). 대상의 날짜 비교는 `COLLATE "C"`
     (ICU 정렬 규칙에서는 `'2030-01-31' < '2030-01-~'` 가 거짓이라 대상에만 있는 날짜를 못 찾았다). 한 해 규모(합성 복제 약 125만 행)에서 한 번에
     훑으면 바퀴 하나가 21초(처음 싣기 49초)였고 그동안 접수가 선다 — 조각 하나는 최대 2.4초 (`docs/test-report/scale-2026-10-09.json`).
   - 그래서 **자동 싣기의 처음 싣기도 조각으로** 가고, 다 돌 때까지 대상에는 일부만 있다 (홈: "처음 훑는 중 n/N") — 한 번에 다 실어야 하면 `publish`
     명령. 대상의 표를 새로 만든 더러운 바퀴(`Result.created` — 누가 표를 지웠다)도 새 조각 바퀴를 시작한다. `watch --once` 는 다음 바퀴가 없으므로
     할 때가 된 전체 훑기를 그 바퀴에 한 번에 한다.
   - **메모리** (4.2 나): 지문은 범위 하나씩 낸다 (문서는 하나씩, 날짜 범위는 한 달 치씩). 바뀐 범위는 (종류, 키, 지문)만 들고 넣을 때 그 범위의 행을
     다시 읽는다 — 한 트랜잭션은 그대로. 처음 싣기의 최대 메모리 1,298 MB → 8 MB (기준선을 뺀 것, 같은 복제 DB), 시간은 1.07배 (행을 두 번 읽는다).
   - 실패하면 그 바퀴의 싣기만 건너뛰고(접수·처리·엑셀은 계속, 조각은 다음 바퀴에 그대로) `retry_seconds` 동안 다시 연결하지 않는다. 연결한 뒤에도
     기다림에 끝이 있다 — 트랜잭션마다 `lock_timeout`·`statement_timeout`, 연결에 TCP keepalive (PR #15 검토: 대상의 잠금 하나가 작업 스레드 전체를
     멈췄다). 서버가 멈춰 버리면(연결은 살아 있는데 서버의 프로세스가 돌지 않는다 — 153초까지 기다렸다) 그 둘이 작동하지 않으므로 우리 쪽에도 상한을
     둔다: 문장 하나마다 `statement_timeout_s` + 30초에 `cancel_safe(5초)`, 그래도 돌아오지 않으면 그 연결의 소켓에 `shutdown()` (다른 스레드에서
     `close()` 하지 않는다 — libpq 가 쓰는 중이다. 윈도우에서는 `shutdown()` 이 기다리는 `select` 를 깨우지 않아 그 소켓의 I/O 를 `CancelIoEx` 로 5초
     동안 되풀이해 취소한다) → `connection_lost` (tasks/0009 4.1 라·4.4).
8. **비밀값**: 대상의 URL 은 환경변수 `MINEDOCSCAN_PUBLISH_URL` 로만 받는다 (설정 파일에 적으면 오류). 어디에도 찍지 않는다 — 로그·요약·오류·`info`·홈에는
   호스트·DB·스키마만, 드라이버의 오류 글은 싣지 않는다 (예외의 종류만). 비밀번호는 URL 에 넣지 않고 libpq 의 pgpass 에 둔다 — 프로그램은 바꿀 것이
   없다, libpq 가 연결할 때 읽는다 (tasks/0009 4.5 다, [ADR 0024](0024-offline-bundle-and-task-scheduler.md)).
9. 스키마 버전이나 싣기의 판이 다른 대상에는 싣지 않고 `publish --rebuild` 를 알린다. `--rebuild` 는 이 프로그램이 만든 표만 지운다 (`CASCADE` 하지 않는다 —
   2단계의 뷰가 걸려 있으면 그렇다고 알리고 멈춘다). 그리고 대상에 `pub_meta` 가 있을 때만 지운다 — `pub_meta` 가 없는데 이름이 같은 표가 있으면
   이 프로그램이 만든 표가 아니므로 지우지 않고 알린다 (`not_ours`, 싣기도 같다). 둘 다 없으면 그냥 만든다.
10. **사본의 주인** (tasks/0009 4.1 다): 사이트 팩의 `site.toml` 에 **적힌** `[site] name` 이 대상의 `pub_meta` 의 `site` 와 다르면 싣지 않는다
   (`other_site`, 종료 코드 2 — `--check` 도, 자동 싣기는 그 바퀴의 실패). 글에 두 이름을 찍지 않는다. 이름이 없는 사이트 팩으로는 싣지 않는다
   (폴더 이름으로 대신하지 않는다 — 폴더를 옮기면 바뀌고, 두 사이트 팩의 폴더가 다 `site` 일 수 있다). 바꿔 실으려면 `--rebuild`.
   실제 DB 를 실어 둔 스키마에 합성 묶음의 작업 폴더로 싣자 문서 3·날짜 3 범위가 묻지 않고 합성 행으로 바뀐 것을 막는다 (URL 이 환경변수에 있는
   PC 에서 설명서의 합성 예제를 돌리면 일어난다).

## 이유

- 작업 DB 를 옮기면 현장 PC 가 서버에 기대게 되고(서버가 꺼지면 스캔이 멈춘다), 0007 의 처리 단위와 불변식을 다시 증명해야 한다. 싣기는 한 방향이라
  작업 DB 의 어떤 규칙도 바꾸지 않는다.
- 문서 하나(30쪽)의 행을 읽어 지문을 내는 데 약 50 ms 다 — 바뀐 문서만 갈아 끼우고 전체는 가끔 훑으면 된다. 합성 30일치: 첫 싣기, 바뀐 것이 없을 때의
  전체 훑기, 문서 하나가 바뀌었을 때의 시간은 지시서 0008 12절.
- 외래 키를 걸면 문서 단위로 갈아 끼울 때 순서와 지연 제약을 맞춰야 하고, 작업 DB 와 다른 규칙(대상만의 거절)이 생긴다. 맞는지는 작업 DB 가 원본이다.

## 버린 것

- **작업 DB 를 PostgreSQL 로 옮기기** — 위의 이유. 2단계의 설계가 정해진 뒤 다시 볼 수 있다.
- **행 단위 upsert 로 싣기** — 지워진 행(다시 처리·버리기·날짜 바꾸기)을 알 길이 없다. 범위 단위로 갈아 끼우면 지워진 것이 저절로 빠진다.
- **대상에 싣는 쪽의 DDL 을 따로 적기** — 두 곳이 어긋난다. `schema.sql` 한 곳에서 만든다.
- **사본의 주인을 폴더 이름으로 정하기** (tasks/0009 4.1 다) — 폴더를 옮기면 바뀌고, 두 사이트 팩의 폴더가 다 `site` 일 수 있다. 적힌 `[site] name` 만.
- **멈춘 서버의 연결을 다른 스레드에서 닫기**(`close()`·PQfinish, 4.1 라) — libpq 가 그 연결을 쓰는 중이다. 소켓만 `shutdown()` 하고 드라이버가 예외를 내게 한다.

## 대가

- 대상은 사본이다 — 2단계가 직접 입력한 값은 2단계의 표에 적고 뷰로 합친다 (이 프로그램이 갈아 끼우는 표에 쓰지 않는다 — ROADMAP "2단계와의 접점").
- 이름·차량번호가 대상으로 간다 (`doc_field`, `doc_page_meta`, `prod_haul`, `eq_assignment_obs` …). 현장의 서버라는 전제이고, 전용 계정으로 그 스키마에만
  쓴다 (DATA.md).
- 싣기의 표현·범위·표와 열의 목록을 바꾸면 싣기의 판을 올리고 대상을 `--rebuild` 해야 한다. 판 2(사이트 표식)가 그렇다 — 판 1 로 실어 둔 대상은
  `--rebuild` 한 뒤에 싣는다 (tasks/0009 8절 4).
- 자동 싣기가 처음 실을 때는 조각을 다 돌 때까지 대상에 일부만 있다 (`poll_seconds` 3초면 13조각에 40초쯤). 다 돌았는지는 홈의 마지막 전체 훑기
  시각으로 본다.
- 사이트 팩의 `[site] name` 을 바꾸면 대상은 `--rebuild` 다. 평가셋의 분할 소금값이 그 이름을 기본으로 쓰므로 바꾸기 전에 `[eval] split_salt` 에
  지금 값을 적는다 ([DATA.md](../DATA.md), `minedocscan info` 가 알린다).
