# 0021. 작업 DB 는 SQLite 그대로, 통합 DB(PostgreSQL)에는 문서·날짜 단위 지문으로 결과의 사본을 싣는다

상태: 채택 (2026-10). [ADR 0005](0005-sqlite-first.md)의 보완 — "운영에서는 PostgreSQL 로 옮긴다"를 "옮기지 않고 싣는다"로.
작업 지시서 [tasks/0008](../tasks/0008-export.md) 1절 (나), 4.8.

## 상황

2단계(통합 DB — 현장 서버의 PostgreSQL)가 이 저장소의 업무 테이블을 읽어 가야 한다. ADR 0005 는 "연결과 자리표시자만 바꾸면 되는
PostgreSQL 어댑터"를 남겨 두었다. 재 보니:

- `schema.sql` 은 PostgreSQL 16 에서 그대로 돈다 (33문 중 실패 0). 실제 3일치(83쪽, 16,293행)를 1.6초에 실었다.
- 그러나 **되읽으면 두 열이 다르다**: PostgreSQL 의 `REAL` 은 4바이트, `INTEGER` 는 32비트다 (SQLite 는 8바이트·64비트).
- 조회문은 그대로 돌지 않는다: DB 를 부르는 곳 154곳(24파일)이 `?` 자리표시자와 sqlite3 의 행 객체에 기대고, `SUM(비교식)` 4곳,
  트랜잭션·`PRAGMA`·`sqlite_master` 를 직접 만지는 곳 32곳. 0007 이 만든 처리 단위(쪽마다 커밋, `BEGIN IMMEDIATE`, WAL, DB 옆의 잠금 파일,
  홈의 `PRAGMA data_version`, `--fresh` 로 지우고 다시 만든다)는 전부 로컬 SQLite 파일을 전제로 한다.
- 이어받은 요구사항은 "외부 네트워크 없이 로컬에서 돈다. DB 도 로컬"이다. 서버가 꺼져도 스캔과 검수는 돌아야 한다.
- 지우고 다시 만드는 DB 를 다른 프로그램이 직접 읽게 둘 수 없다.

## 결정

1. **작업 DB 는 SQLite 그대로 둔다.** 통합 DB 에는 결과의 사본을 싣는다 (`publish/`). 대상에 쓰는 곳은 그 모듈 하나다 —
   "DB 쓰기는 `store.db.upsert()` 만"은 작업 DB 의 규칙이다.
2. **표의 정의는 `schema.sql` 한 곳에서 나온다.** 메모리의 SQLite 에 올려 `PRAGMA table_info`·`index_list` 로 대상의 DDL 을 만든다 (글자를 파싱하지
   않는다). 형을 넓힌다 (`REAL` → `DOUBLE PRECISION`, `INTEGER` → `BIGINT`). 기본 키·UNIQUE·인덱스는 걸고 **외래 키는 걸지 않는다** — 문서 단위로
   갈아 끼우고, 맞는지는 작업 DB 가 원본이다.
3. **싣는 표와 열은 한 곳에** (`store/db.py` 의 `PUBLISH_TABLES`·`PUBLISH_SKIP_COLUMNS`, 0007 의 불변식 시험이 같이 쓴다). 싣는 열은 작업 DB 의 열에서
   시각·요청 번호·로컬 경로(`created_at`·`received_at`·`work_requested`·`work_done`·`source_path`)를 뺀 것 — 내용이 같아도 `--fresh` 마다 달라진다.
   싣지 않는 표: `doc_page_sig`(안에서만), `doc_review`·`doc_decision`(원본은 파일), `meta_schema`.
4. **범위 셋과 지문.** 문서(`doc_document` 의 행 + 그 문서의 쪽을 가리키는 행 전부), 날짜(`xcheck_haul`·`eq_assignment_obs`), 통째(`eq_equipment`).
   싣는 표의 모든 행이 셋 중 하나에 들어야 한다 — 아니면 싣지 않고 수로 알린다. 지문 = 범위의 행을 정해진 순서(표, 기본 키)와 표현(JSON, 실수는
   정확한 표현)으로 이은 것의 SHA-256. 대상의 상태 표 `pub_state` 에 범위마다 지문, `pub_meta` 에 스키마 버전과 **싣기의 판**.
5. **지문이 다른 범위만, 한 트랜잭션으로 갈아 끼운다.** 지울 것을 먼저 다 지우고 넣는다 (같은 키의 행이 문서 사이를 옮겨 다닌다 — 점검의 이기는 쪽,
   일보의 자리). 작업 DB 에 없는 범위는 지운다. 끊기면 대상은 싣기 전 그대로다 — 읽는 쪽은 반쯤 바뀐 문서를 보지 않는다.
6. **불변식**: 싣기가 끝나면 싣는 표마다 대상의 행 = 작업 DB 의 행 (싣는 열 전부, 행의 순서와 무관, 실수까지 정확히). 실을 수 없는 값(NUL 문자)이 있는
   범위는 건너뛰고 대상의 옛 행을 지운다 — 불변식은 그 범위를 뺀 나머지에 선다.
7. **언제**: `publish` 명령(전체), 그리고 `watch`·`serve` 의 바퀴 끝(엑셀 다음) — 더러운 범위만(처리·검수가 건드린 문서, 지워진 문서, 더러운 날짜와
   그 날짜에 쪽이 있는 문서 전부 — 작업 DB 와 대상 양쪽에서). 키가 부딪치면 같은 바퀴에 전체 훑기로. 전체 훑기는 시작할 때와 `sweep_minutes` 마다.
   실패하면 그 바퀴의 싣기만 건너뛰고(접수·처리·엑셀은 계속), `retry_seconds` 동안 다시 연결하지 않는다. 연결한 뒤에도 기다림에 끝이 있다 —
   트랜잭션마다 `lock_timeout`·`statement_timeout`, 연결에 TCP keepalive (PR #15 검토: 대상의 잠금 하나가 작업 스레드 전체를 멈췄다).
8. **비밀값**: 대상의 URL 은 환경변수 `MINEDOCSCAN_PUBLISH_URL` 로만 받는다 (설정 파일에 적으면 오류). 어디에도 찍지 않는다 — 로그·요약·오류·`info`·홈에는
   호스트·DB·스키마만, 드라이버의 오류 글은 싣지 않는다 (예외의 종류만).
9. 스키마 버전이나 싣기의 판이 다른 대상에는 싣지 않고 `publish --rebuild` 를 알린다. `--rebuild` 는 이 프로그램이 만든 표만 지운다 (`CASCADE` 하지 않는다 —
   2단계의 뷰가 걸려 있으면 그렇다고 알리고 멈춘다).

## 이유

- 작업 DB 를 옮기면 현장 PC 가 서버에 기대게 되고(서버가 꺼지면 스캔이 멈춘다), 0007 의 처리 단위와 불변식을 다시 증명해야 한다. 싣기는 한 방향이라
  작업 DB 의 어떤 규칙도 바꾸지 않는다.
- 문서 하나(30쪽)의 행을 읽어 지문을 내는 데 약 50 ms 다 — 바뀐 문서만 갈아 끼우고 전체는 가끔 훑으면 된다. 합성 30일치: 첫 싣기, 바뀐 것이 없을 때의
  전체 훑기, 문서 하나가 바뀌었을 때의 시간은 지시서 0008 12절.
- 외래 키를 걸면 문서 단위로 갈아 끼울 때 순서와 지연 제약을 맞춰야 하고, 작업 DB 와 다른 규칙(대상만의 거절)이 생긴다. 맞는지는 작업 DB 가 원본이다.

## 버린 것

- **작업 DB 를 PostgreSQL 로 옮기기** — 위의 이유. 2단계의 설계가 정해진 뒤 다시 볼 수 있다.
- **행 단위 upsert 로 싣기** — 지워진 행(다시 처리·버리기·날짜 바꾸기)을 알 길이 없다. 범위 단위로 갈아 끼우면 지워진 것이 저절로 빠진다.
- **대상에 싣는 쪽의 DDL 을 따로 적기** — 두 곳이 어긋난다. `schema.sql` 한 곳에서 만든다.

## 대가

- 대상은 사본이다 — 2단계가 직접 입력한 값은 2단계의 표에 적고 뷰로 합친다 (이 프로그램이 갈아 끼우는 표에 쓰지 않는다 — ROADMAP "2단계와의 접점").
- 이름·차량번호가 대상으로 간다 (`doc_field`, `doc_page_meta`, `prod_haul`, `eq_assignment_obs` …). 현장의 서버라는 전제이고, 전용 계정으로 그 스키마에만
  쓴다 (DATA.md).
- 싣기의 표현·범위·표와 열의 목록을 바꾸면 싣기의 판을 올리고 대상을 `--rebuild` 해야 한다.
