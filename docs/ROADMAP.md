### 첫 대상 현장에서의 수치 (인식 백엔드 없이)

입력: 일일 점검표 27일치 + 하루치 묶음 3일치 = 문서 30건, 110쪽. 기준 파일은 그 현장의 사이트 팩에 있다.

| 항목 | 값 |
|---|---|
| 양식 분류 | 110쪽을 6종으로 분류 (셀 정의가 있는 3종 70쪽, 분류 전용 3종 40쪽) |
| 정합 | 70/70 통과. 괘선 오차 최대 4 px |
| 점검표 ✓ 판정 | 675행 중 유 288 / 무 286 / 판정 불가 101 (판정 불가 중 100은 점검을 하지 않은 4일치) |
| 교차검증 (값 유무) | 일치 564 / 불일치 36 |
| 배차 관측 | 30건 중 인쇄된 머리글과 다른 것 8건 |
| 오라클 백엔드 | 점검내역 CER 0.0, 행 자동 적재율 0.83 (나머지는 ✓ 판정 불가 행) |
| `null` 백엔드 | 행 자동 적재율 0.27 (점검내역이 빈 행만 자동) |
| 속도 | 쪽당 약 1초 (CPU) |

✓ 판정의 정답은 아직 없다. 유/무 수치는 판정 결과이지 정확도가 아니다.
이 수치는 PDF 를 PyMuPDF 로 읽던 때의 것이다 — PDFium 으로 바꾼 뒤(tasks/0009 단계 3)의 회귀 기준은 사람이 실데이터로 다시 잡는다 (0009 8절 1, 예상은 ADR 0023).
교차검증의 불일치 36건은 읽기 오류와 현장의 기재 차이가 섞여 있고, 아직 사람이 분류하지 않았다.

## 1단계의 남은 일

순서는 의존 관계 때문이다: 평가셋이 있어야 인식기를 고를 수 있고, 인식기가 있어야 교정이 의미가 있다.
숫자 정답은 밖에서 구할 수 없으므로(아래 M2) 검수 도구를 앞당겨 만들어 정답을 직접 만든다 (ADR 0007).

### M1. 양식 넓히기
- 분류 전용 3종(중기운행일보, 점보 작업일보, 로우더 작업일보)의 셀 정의: 코드(핸들러 `usage`, 값의 형식, 검산, 대기열, 템플릿 도구)는
  [tasks/0005](tasks/0005-usage-logs.md) 와 [tasks/0006](tasks/0006-print-layer-and-variants.md) 에서 했다. 남은 것은 사이트 팩의 템플릿·인쇄 층·
  판 B 와 대응표, 계기·근무 시각 입력 — 사람의 일. 순서는 tasks/0006 8절 (분류 전용으로 돌리기 → `print-layer` → `add-region` → 열·행·필드 →
  판 B 는 `variant`), 그다음 0005 8절의 나머지
- 실제 가동 일보에서 막힌 것 — 칸 안의 인쇄(인쇄 층), 같은 날 섞여 쓰이는 인쇄 판, 가동 시간 칸의 입력 → [tasks/0006](tasks/0006-print-layer-and-variants.md) (완료 — ADR 0017·0018).
  실데이터 수치(인쇄 층을 켜기 전과 뒤의 검수 대기 칸, 판마다 고른 쪽)는 8절의 사람이 할 일
- 인쇄 층을 운반·점검표 양식에 켜기 — 숫자 정답이 생긴 뒤 `regress`·`eval` 로 판단한다 (tasks/0006 4.4). 켜려면 코드도 고쳐야 한다
  (지금은 역할이 있는 표의 칸에만 쓴다)
- 소수·시각(계기 값)을 기계가 읽기 → [tasks/0011](tasks/0011-reading-decimals-and-times.md) (대기). 0006 1절은 하루 10칸 안팎이라 미뤘다 — 0011 은 길·규칙·모델을
  합성으로 만들고, 현장의 자동 적재 기준은 가동 일보의 정답이 쌓인 뒤 실데이터로 정한다 (ADR 0012, 0011 8절)
- 묶음 PDF 에 아직 템플릿이 없는 양식(관리 계열: 선광 작업일지, 경비 근무일지, 전기 안전일지 등) 추가
- 여백 행에 손으로 추가한 장비의 처리 규칙 (지금은 `doc_field` 에만 남는다)
- 완료 기준: 묶음 PDF 의 `unknown_form` 0쪽, 새 양식마다 정합 통과율과 괘선 오차를 회귀 기준에 추가

### M2. 평가셋과 최소 검수 도구
스캔과 같은 기간의 현장 입력 엑셀은 구할 수 없다(2026-10 확인). 숫자 정답은 직접 만든다.

- **최소 검수 도구** — 구현 ([tasks/0001](tasks/0001-review-tool.md) 단계 1–5, ADR 0008): 셀 크롭을 보여 주고 값을 키보드로 입력 →
  `reviews.jsonl` 에 남고 `doc_field` 가 `reviewed` 로 바뀐다. 검수한 값이 곧 정답이고 학습 데이터다. 교차검증 불일치 칸은 두 문서의 크롭을 같이 보여 준다.
  남은 것: 페이지 필드(차량번호·작성자) 검수로 수동 라벨 대체(단계 6), 실데이터로 써 보고 고칠 점 (tasks/0001 7절)
- **숫자 셀(운반 횟수) 정답**: 묶음 PDF 전체를 돌려 값이 있는 셀에서 날짜별로 고르게 표본을 뽑아 입력한다.
  한두 자리 숫자라 셀당 수 초. 첫 목표 1,500셀 (3일치에서 값이 있는 셀이 214개였다). 도구는 전부 갖춰졌다 (tasks/0002) — 남은 것은 사람의 입력이다
- **평가셋 고정**: 날짜 단위 `test`/`train`, 소금값으로 고정 (ADR 0009). `export-answers --split`, `export-crops --split`
- **정답 없이 보는 지표**: 교차검증 일치율 — 구현 (`report` 의 `xcheck_agreement`, 기계 값 기준 / 최종 값 기준, 분모 포함).
  정확도는 아니지만(둘 다 같게 틀릴 수 있다) 정답을 만들기 전에도 인식기를 비교할 수 있다.
  두 양식 모두 합계 행·열이 없어 합계 검산은 쓸 수 없다
- **가지고 있는 엑셀(다른 기간)**: 짝 정답으로는 못 쓴다. 횟수의 범위·분포 확인(그럴듯한 값인가)에만 쓴다
- **점검표 텍스트**: 정답이 있는 27일치로 한다. 같은 27일치의 상용 OCR 결과(셀에 배정된 엑셀)도 가지고 있으므로 기준선은 그것으로 계산한다
  (새로 호출하지 않는다. "상용 OCR + 선행 셀 배정"의 성적이다). 선행 연구팀의 나머지 자료는 지금 요청하기 어려워 계획에 넣지 않는다. 더 필요하면 검수 도구로 넓힌다
- **✓ 판정 정답**: 같은 도구로 표본을 확인한다 → [tasks/0004](tasks/0004-page-fields-and-checks.md) 단계 6. **도구는 들어갔다** —
  `review serve --queue checks --n 300` (행 하나 = 유·무 두 칸, 기계 판정 숨김, `1`/`2`/`Enter`/`?`) → `eval --checks`. 남은 것은 사람의 입력이다
- 완료 기준: 양식·필드 종류별 표본 수와 기준선 수치가 표로 정리되고, `eval` 이 그 정답으로 돈다

### M3. 인식 백엔드
- 숫자 전용 인식기 (횟수는 대부분 한두 자리) — 가장 작고 효과가 바로 교차검증으로 드러난다 → [tasks/0003](tasks/0003-digit-recognizer.md).
  **코드는 들어갔다** (합성 셀에서 문턱 통과). 남은 것: 실데이터 검수 → `recognizer train` → 검증 날짜에서 규격(원본 vs 정합) 비교 →
  test 한 번 → 위 "첫 대상 현장에서의 수치" 에 인식기 줄을 더한다 (지시서 8절의 사람이 할 일)
- 표 밖 필드: 차량번호, 작성자, 월·일 → [tasks/0004](tasks/0004-page-fields-and-checks.md). **코드는 들어갔다** (합성 메타 필드에서 문턱 통과,
  ADR 0013·0014). 숫자는 읽고 닫힌 목록에서 고르고(차량번호가 바뀐 짝에서도 숫자로 읽는지 시험), 이름은 분류기로 고른다. 남은 것: 20일치 정답 →
  `--cv 5` 학습 → 표본 감사 → `eval --meta --split test` (지시서 8절)
- 손글씨 텍스트: 로컬에서 학습·추론하는 비전-언어 모델. 같은 평가셋에서 기준선보다 좋을 때 교체한다
- 백엔드는 전부 로컬에서 돈다. 외부 API 백엔드는 만들지 않는다 (현장은 외부 네트워크 없이 운용)
- 원본 해상도 크롭: 경로는 만들었다 (`CropSpec(res="source")`, 숫자 모델의 기본). 원본(300 dpi)이 정합 이미지(200 dpi)보다 나은지는
  실데이터의 검증 날짜에서 두 규격으로 따로 학습해 비교한다
- 완료 기준: 평가셋에서 백엔드별 CER·필드 정확도·자동 적재율 비교표. 채택한 백엔드가 기준선 이상

### M4. 교정
- 문구 DB: 행(장비)·열별로 반복되는 문구를 모아 후보를 내고 편집거리 제한 안에서 고른다.
  후보는 가진 정답 27일치와 검수값에서 만든다 (선행 연구의 장비별 사전은 받게 되면 더한다)
- 후보 목록을 주고 고르게만 하는 언어모델 교정기. 선행 연구의 미세조정 모델은 가중치를 가지고 있지 않아 지금은 평가할 수 없다
  (받게 되더라도 기반 모델의 사용 허락이 비상업 조건이므로 배포 범위 확인 필요 — PRIOR_WORK.md)
- 숫자 불변 검사: 교정 전후의 숫자열이 다르면 교정을 버린다. 수량·등록번호는 교정기가 바꾸지 못한다
- 완료 기준: 교정 전후 CER 비교. 교정이 틀린 값을 만든 건수(과교정)를 따로 센다

## 2단계와의 접점

- **읽는 곳은 통합 DB(PostgreSQL)의 실은 표다** (ADR 0021). 작업 DB(SQLite)는 현장 PC 의 것이고 지우고 다시 만든다 — 직접 읽지 않는다.
  `publish` 가 `[publish] schema`(기본 `minedocscan`)에 싣는 표: 업무 테이블(`insp_daily`·`prod_haul`·`prod_tally`·`eq_usage_daily`·`eq_assignment_obs`·
  `eq_equipment`·`xcheck_haul`·`xcheck_usage`)과 출처(`doc_document`·`doc_page`·`doc_field`·`doc_page_meta`). 열은 작업 DB 와 같고 시각·요청 번호·로컬 경로
  (`created_at`·`received_at`·`work_requested`·`work_done`·`source_path`)만 빠진다. 형은 넓혀(`DOUBLE PRECISION`·`BIGINT`) 외래 키 없이 만든다.
- **실은 표는 이 프로그램이 갈아 끼운다 — 2단계는 읽기만 한다.** 문서·날짜 단위로 지우고 다시 넣으므로(한 트랜잭션 — 반쯤 바뀐 문서는
  보이지 않는다) 거기에 쓴 행은 갈아 끼울 때 지워지거나(`--rebuild` 면 표째) 이 프로그램의 행과 키가 부딪친다. 직접 입력한 값은 **2단계의 표**에
  적고 뷰로 합친다 (`insp_daily.entry_source` 는 이 프로그램에서 늘 `scan`). 뷰는 걸어도 된다 — `publish --rebuild` 는 이 프로그램이 만든 표만
  지우고(`CASCADE` 하지 않는다), 뷰가 걸려 있어 지우지 못하면 그렇다고 알리고 멈춘다. 스키마 버전이나 싣기의 판이 바뀌면 싣지 않고 `publish --rebuild` 를 알린다.
- 실은 표는 작업 DB 그대로라 **검수 대기인 기계 값도 들어 있다** (엑셀과 다르다 — 엑셀은 확정된 값만 싣는다, ADR 0022). 확정된 값만 쓰려면
  업무 행의 `review_status`(`auto`·`reviewed`)를 본다. `xcheck_*` 의 값에도 검수 대기 값이 끼어 있을 수 있다 — 견준 업무 행·칸의 상태를 같이 본다.
  출처는 `source_field_id`(가동 기록은 `start_field_id`·`end_field_id`·`total_field_id`, 계기 검산은 `field_a`·`field_b`)로 `doc_field` 까지
  거슬러 올라간다.
- 이름·차량번호가 대상으로 간다 (`doc_field`, `doc_page_meta`, `prod_haul`, `eq_assignment_obs` …). 현장의 서버, 그 스키마에만 쓰는 전용 계정이 전제다 (DATA.md).
- `xcheck_*` 를 날짜별로 계속 쌓아 물질수지 불일치의 추이를 보여 준다. 조정 규칙은 2단계에서 정한다.
- 노드를 잇는 교차검증을 늘린다: 채광 → 선광 → 출하, 장비 가동 ↔ 운반 실적.
- **가동 기록** (tasks/0005): `eq_usage_daily` 는 쪽 하나에 한 행이다 — 한 장비가 하루 두 장을 내면 두 행이고, 합치는 것은 2단계의 일이다.
  `hours` 는 적힌 값에서 계산한 것이고 근거(`hours_basis`: meter > total > clock > shifts)를 같이 읽는다 — 근거가 다른 값을 같은 것으로 더하지
  않는다. 가동 시간의 분류(가동·대기·정비)는 여기서 하지 않는다. 계기의 어긋남(`xcheck_usage`)은 고치지 않고 보여 주기만 한다.
  작업량(`prod_tally`)의 소계 칸은 적힌 대로 남아 있다 — 합칠 때는 `is_subtotal` 을 뺀다.
